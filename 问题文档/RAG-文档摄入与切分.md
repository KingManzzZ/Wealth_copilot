### P0-1 · PDF 页眉被当成标题，导致章节跨页断裂

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 用户使用中察觉「标题和内容切开」→ 审查导出真实 chunk 后定位根因 |
| **代码引入** | 2026-10-10（初始提交），已存在约 5 天 |
| **严重度** | 🔴 最高（检索不准的最大单一原因） |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 解析 → 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:163-176` |

#### 🔍 现象

- 「存款保险制度的限额是多少」检索 top-8 中，**3 个块的面包屑是书名**，而它们的正文其实属于别的章节。
- 「第一章 人民币主要讲了什么」的 **top-1 是目录页表格**，真正的章节内容排不进去。

#### 🧪 证据

PDF 每页的页眉「金融知识普及读本 (第二版)」被 Docling 识别为 H2 标题，实测成为 **57 个块的面包屑**：

```
57  金融知识普及读本 (第二版)      ← 页眉
19  三、 结息和计息方式
15  (三) 金融机构应履行的义务
```

页眉一旦被当成标题，就会**重置标题栈**，把原本连续的一节切成若干段：

```
第 128 页  # 金融知识普及读本 (第二版)        ← 页眉被当标题
           记录等。- 4郾 查询信用报告的记录:...  ← 面包屑 = 书名（错误）
```

该块正文属于「(一) 查询机关」一节，但 `heading_path` 是书名。**只有页眉前的那一段带着真标题，之后每页的片段都丢失了章节上下文**——这就是「标题和内容被切开」的直接机制。

#### 🎯 根因

切分器把 Markdown 里的 `#` **无条件当作可信的结构信号**，没有对标题本身做业务层校验。而 PDF 解析器的产物中，页眉/页脚天然会被识别为标题——这是所有 PDF→Markdown 管线的共性噪声。

具体到代码：`chunker.py:165-176` 只判断了 `#` 的数量，没有任何"这个标题是否合理"的检查。

#### ✅ 解决方案

加一道**标题准入闸门**。因为需要预先知道标题出现频次（页眉的特征是"反复出现"），在 `_parse_sections` 之前做一次预扫描。

新增 `src/wealth_rag/ingestion/heading_rules.py`：

```python
"""标题层级识别与噪声治理规则。"""
from __future__ import annotations

import re
from collections import Counter

# 标题归一化时剔除的字符（空白、括号、版次、标点）
_NORM_DROP_RE = re.compile(r"[\s()（）\[\]【】·、,，.。:：;；\-—_/\\]|第|版")

def norm_title(text: str) -> str:
    """标题归一化：用于频次统计与相似度比较，不做展示。"""
    return _NORM_DROP_RE.sub("", text or "")


def count_headings(lines: list[str], heading_re: re.Pattern) -> Counter:
    """预扫描：统计各标题文本出现次数（用于识别页眉）。"""
    counter: Counter = Counter()
    for line in lines:
        m = heading_re.match(line.strip())
        if m:
            counter[norm_title(m.group(2))] += 1
    return counter


def is_running_header(
    title: str,
    doc_title: str,
    heading_freq: Counter,
    min_count: int = 3,
) -> bool:
    """页眉判定：与文档标题高度相似，且在文中反复出现。

    针对「金融知识普及读本 (第二版)」这类每页重复的书名/页眉。
    """
    norm = norm_title(title)
    if not norm:
        return False
    doc = norm_title(doc_title)
    similar = bool(doc) and (norm in doc or doc in norm)
    return similar and heading_freq.get(norm, 0) >= min_count
```

在 `chunker.py` 的 `chunk()` 入口预扫描，并在 `_parse_sections` 内**丢弃**页眉行（不是当正文，而是彻底删掉，让上下文跨页延续）：

```python
def chunk(self, markdown, doc_id, source_path, doc_title):
    lines = markdown.split("\n")
    self._heading_freq = count_headings(lines, _HEADING_RE)
    self._doc_title = doc_title
    sections = self._parse_sections(markdown)
    ...

# _parse_sections 内，标题判定分支：
if m and len(m.group(1)) <= self.cfg.heading_max_level:
    title = m.group(2).strip()
    # 【新增】页眉：丢弃该行，不建节、不并入正文
    if is_running_header(title, self._doc_title, self._heading_freq,
                         self.cfg.running_header_min_count):
        flush_para()
        i += 1
        continue
    ...
```

新增配置（`config.yaml` → `chunking`）：

```yaml
chunking:
  running_header_min_count: 3   # 标题重复 ≥N 次且近似 doc_title → 判为页眉并丢弃
```

```powershell

python docs\audit\search_probe.py           # 存款保险查询的 top-8 不应再含页眉块
```

验收：`heading_path` 等于书名的块数应从 **57 → 0**；深度分布应出现更多层级。

#### 💡 学习要点

1. **上游产物的"结构信号"不可信。** 解析器说这是标题，不代表业务上它是标题。结构性元数据必须在下游做校验。
2. **页眉/页脚是 PDF 解析的经典噪声**，特征鲜明（反复出现、与文档标题相似、通常很短），可以用"频次 + 相似度"两个信号稳定识别。
3. **丢弃噪声 ≠ 降级为正文。** 页眉若降级为正文，会把书名插进段落中间污染正文；正确做法是**整行删除**，让上下文自然跨越页面边界。

### P0-2 · 目录页整体入库并抢占首位

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（真实检索实测，6 条查询 × top-8） |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🔴 高 |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:179-186` |

#### 🔍 现象

查询「第一章 人民币主要讲了什么」返回 **top-1 = 目录页表格**（`score=0.7994`，`rerank=0.6657`，全场最高）。「人民币防伪特征有哪些」的 top-2 也是它。

#### 🧪 证据

```
[1] score=0.7994 rerank=0.6657 type=table page=4
    heading_path = 目摇 摇 录
    raw_text >>> | 第一章摇 | 人民币 ……  | 1 | | 第一节摇 | 人民币概述 …… | 3 | ...
```

另有 1 个 2 字符的目录页码残块（`raw_text = '66'`）。

**目录页字面包含了全书所有章节标题**，因此任何涉及章节名的查询都会命中它——而且因为它"覆盖全"，稠密向量与 BM25 都会给出高分。

#### 🎯 根因

切分器把目录页当作**普通正文**处理，没有任何"这段是元数据不是内容"的识别。

目录页的本质是**结构索引**，不是**知识内容**。它与正文共享同一套词汇（章节名），但完全不承载答案。索引它等于人为制造了一个"对任何章节查询都高分、但永远答不对"的干扰项。

#### ✅ 解决方案

两层拦截：

**(a) 标题层**：识别目录标题，进入「跳过模式」，直到出现通过校验的非目录标题。

```python
# heading_rules.py
_CONTENTS_TITLE_RE = re.compile(
    r"^(目\s*录|目\s*次|目\s*錄|contents|table\s+of\s+contents)$", re.I
)

def is_contents_title(title: str) -> bool:
    return bool(_CONTENTS_TITLE_RE.match(re.sub(r"[\s\u3000]+", "", title or "").strip()))
```

```python
# chunker.py：_parse_sections 内
if is_contents_title(title):
    flush_para()
    self._in_contents = True
    i += 1
    continue
if self._in_contents:
    # 遇到下一个真实标题才离开目录区；最多吞 128 行（对齐 RAGFlow remove_contents_table）
    if <该行不是目录条目且通过标题校验>:
        self._in_contents = False
    else:
        i += 1
        continue
```

**(b) 表格层**：目录在本 PDF 里是 Markdown 表格，需在表格识别处过滤。判据是"多数行含省略号引导符或行尾页码"：

```python
# heading_rules.py
_TOC_ENTRY_RE = re.compile(r"[…\.·]{3,}|\d{1,3}\s*$")

def looks_like_toc_table(rows: list[list[str]]) -> bool:
    """目录表格判定：多数行呈现「标题 …… 页码」形态。"""
    if len(rows) < 3:
        return False
    hits = sum(1 for r in rows if _TOC_ENTRY_RE.search(" ".join(r)))
    return hits >= max(3, int(len(rows) * 0.6))
```

在 `chunker.py:_parse_sections` 的表格分支里：

```python
if self._is_table_start(lines, i):
    flush_para()
    rows = []
    while i < n and lines[i].strip().startswith("|"):
        rows.append(lines[i].strip())
        i += 1
    # 【新增】目录表格直接丢弃
    if looks_like_toc_table([self._split_row(r) for r in rows]):
        continue
    current.blocks.append(_Block("table", "\n".join(rows), page))
    continue
```

新增配置：

```yaml
chunking:
  drop_contents: true           # 删除目录区块（标题 + 目录表格）
```

#### ✔️ 验证

`docs/audit/dump_chunks.py` 输出的块列表中不应再有 `heading_path = 目摇 摇 录`；目录页块数应从 **2 → 0**。

#### 💡 学习要点

1. **区分"结构信息"与"内容信息"。** 目录、索引、页眉、页码都是文档的**导航元数据**，检索语料里应当剔除——它们与正文共享词汇，却永远不是答案。
2. **"覆盖全"的噪声最危险。** 目录页覆盖所有章节，因此对任何章节类查询都会得高分。这类干扰项不能靠提高阈值解决，必须**在入库前移除**。
3. **同一类噪声要多个入口拦截。** 目录既有标题形态也有表格形态，只堵一处会漏。

### P0-3 · 标题未进入证据文本

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 用户使用中察觉「标题和内容切开」→ 审查对比 `text` / `raw_text` 后定位 |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🔴 高（用户感知最直接） |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 切分 / 数据建模 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:80-98`、`84-86` |

#### 🔍 现象

检索返回的证据正文**完全没有标题**。实测 48/48 条结果的 `raw_text` 都不含自身标题。

#### 🧪 证据

- `raw_text` 含自身标题的块：**仅 1/722 = 0.14%**
- `parent_text` 含标题的块：**0/335**

根因在 `chunker.py:80-98`——面包屑只拼进了 `embed_text`：

```python
prefix = f"{breadcrumb}\n" if breadcrumb else ""
...
embed_text = (prefix + piece.embed_text).strip()   # 标题 → 只进嵌入文本
Chunk(
    text=embed_text,          # 含面包屑 ✓（嵌入/稀疏/重排用到）
    raw_text=piece.raw_text,  # 不含标题 ✗（返回给 LLM 的证据）
    ...
    parent_text=parent_text,  # 不含标题 ✗（上下文扩展）
)
```

而 `chunker.py:84-86` 组装父块时也只拼 `b.content`，不含标题。

> **重要澄清**：**嵌入侧与 BM25 侧其实用到了标题，这部分设计是对的**。丢的是「证据侧」——即 `cli.py:120` 展示的、`README.md:143` 示例里 `hit.raw_text` 返回的、后续 LLM 编排拿到的那份文本。

#### 🎯 根因

**同一份数据承担了两种职责，但只满足了一种。**

`text` 的职责是"给检索模型用"（需要标题提供上下文），`raw_text` 的职责是"给人/LLM 看"（需要标题说明这是什么）。设计时只考虑了前者，后者被当作"去掉前缀的纯净文本"——但"纯净"恰恰意味着**丢失了定位信息**。

这也说明：**"标题和内容切开"往往不是切分粒度问题，而是字段职责设计问题**。标题并没有被切走，它一直在 `heading_path` 里，只是没有出现在该出现的字段中。

#### ✅ 解决方案

在 `chunk()` 组装阶段补回标题：

```python
leaf = sec.heading_path[-1] if sec.heading_path else ""
body = piece.raw_text.strip()

# text：用于嵌入 / 稀疏 / 重排（含完整面包屑，保持现状）
embed_text = (prefix + piece.embed_text).strip()

# raw_text：用于返回给 LLM 的证据，补回叶子标题（Markdown 语义，便于阅读）
raw_text = f"## {leaf}\n\n{body}" if leaf else body

# parent_text：父块（节全文）含自身面包屑
parent_text = None
if parent_id:
    parent_body = "\n\n".join(b.content for b in sec.blocks).strip()
    parent_text = f"{prefix}{parent_body}" if prefix else parent_body
```

**设计说明**：

- `raw_text` 用**叶子标题**（`## 再平衡策略`）而非整条面包屑，避免与末尾的 `parent_text` 重复；完整层级仍保留在 `heading_path` 与 `citation` 中供溯源。
- `parent_text` 用**完整面包屑**，因为父块是「节全文」，需要自描述。
- 用 Markdown 的 `##` 而非纯文本，是因为下游 LLM 对 Markdown 结构的理解更好。

#### ✔️ 验证

```powershell
python docs\audit\dump_chunks.py    # 看「raw_text 不含自身标题」的计数
```

验收：该指标应从 **720/722 → 接近 0**（目标：标题覆盖率 > 95%）。

#### 💡 学习要点

1. **一条数据的不同用途要有不同字段。** 检索用 `embed_text`（含上下文前缀）、展示/生成用 `display_text`（含可读标题）、过滤/溯源用 metadata。混用一个字段必然顾此失彼。
2. **"信息丢失"要先怀疑字段设计，再怀疑算法。** 本例中标题一直在 `heading_path` 里，只是没被写进返回字段——排查时应该先比对"同一数据的各个字段分别装了什么"。
3. **改动成本与收益可以极不对称。** 这个问题的修复不到 20 行代码，却是用户最直接感知的问题。

| 元信息 | 内容 |

| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（用真实解析器复现摄入，得到 708 块与库中一致） |
| **代码引入** | 2026-10-10（初始提交），但**触发条件是解析器行为** |
| **严重度** | 🔴 高 |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 解析 → 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:166-174` |

#### 🔍 现象

面包屑几乎没有层级。实测 `heading_path` 深度分布：**深度 1 占 98.3%（710/722）**。

#### 🧪 证据

用真实解析器复现摄入，得到 **708 块（与库中一致）**，同时发现：

```
== Markdown 标题总数 561，层级分布 {2: 561} ==
```

**PDF 解析出的 561 个标题全部是 H2。** 而 `chunker.py:170-172` 的层级栈逻辑本身是**正确的**：

```python
while stack and stack[-1][0] >= level:
    stack.pop()
stack.append((level, title))
```

但 `level` 恒为 2，栈永远只存一个元素，所以深度恒为 1。

**关键对比证据**：同一份代码处理 `data/samples/01_资产配置基础.md`（层级完整的 Markdown）时，能正确产出三层面包屑：

```
资产配置基础 > 二、战略与战术资产配置 > 2.2 再平衡策略
```

因此**问题出在解析层（标题层级信息丢失），不在切分层**。

#### 🎯 根因

**把上游能力当作保证。** 切分器的层级恢复逻辑完全依赖 Markdown 的 `#` 数量，而不同解析引擎对这些信号的处理差异极大：

| 解析通道 | 实测标题层级 |
| :--- | :--- |
| Docling（PDF 默认优先） | 全部 H2（`{2: 561}`） |
| PyMuPDF（`pdf_engine: auto` 的回退路径） | H3~H6 混合（`{1:1, 2:2, 3:1, 4:2, 5:3, 6:14}`） |

两个通道都拿不到正确的层级，且失败方式完全不同。**真正的层级信息其实存在于标题文本自身**（「第一章」>「第一节」>「一、」>「（一）」），只是代码没有去读它。

#### ✅ 解决方案

核心思路：**从标题文本自身解析层级**，不依赖 Markdown 的 `#` 数量。这是 RAGFlow `TitleChunker` + `BULLET_PATTERN` 的做法。

在 `heading_rules.py` 中定义语义层级规则（按顺序匹配，首个命中即返回，层级越小越顶层）：

```python
_CN_NUM = r"零一二三四五六七八九十百千0-9"

_LEVEL_RULES: list[tuple[int, re.Pattern]] = [
    # 篇 / 编 / 部分 / 章
    (1, re.compile(rf"^第[{_CN_NUM}]+\s*(分?编|部分|篇|卷|章)")),
    # 节
    (2, re.compile(rf"^第[{_CN_NUM}]+\s*节")),
    # 一、 二、 三、
    (3, re.compile(r"^[一二三四五六七八九十]+\s*[、.．]")),
    # （一）（二）
    (4, re.compile(r"^[（(]\s*[一二三四五六七八九十]+\s*[)）]")),
    # 2.1 三级点号（注意：必须排在 1. / 1、 之前）
    (4, re.compile(r"^[0-9]{1,2}\s*\.\s*[0-9]{1,2}\s*[^0-9.]")),
    # 2.1.1 四级点号
    (5, re.compile(r"^[0-9]{1,2}\s*\.\s*[0-9]{1,2}\s*\.\s*[0-9]{1,2}")),
    # 1. / 1、 / 1）
    (5, re.compile(r"^[0-9]{1,2}\s*[、.．]\s*\S")),
    # （1）（2）
    (6, re.compile(r"^[（(]\s*[0-9]{1,2}\s*[)）]")),
    # 第X条（条文视为叶子层）
    (7, re.compile(rf"^第[{_CN_NUM}]+\s*条")),
]


def semantic_level(title: str) -> int | None:
    """从标题文本推断层级；无法判断返回 None。"""
    t = (title or "").strip()
    for level, pattern in _LEVEL_RULES:
        if pattern.match(t):
            return level
    return None
```

在 `chunker.py:166-174` 改为**语义层级优先**：

```python
m = _HEADING_RE.match(line.strip())
if m and not is_running_header(...):
    title = m.group(2).strip()
    md_level = len(m.group(1))
    sem = semantic_level(title)
    # 语义层级优先：Docling 把标题全压成 H2 时仍能还原层次
    level = sem if sem is not None else md_level
    ...
```

**同时把文档标题压入栈底**，让每个块都带上文档上下文（顺带解决 P0-5 的容器标题问题）：

```python
stack: list[tuple[int, str]] = [(0, doc_title)] if doc_title else []
```

于是面包屑从 `第一章 人民币` 变成 `金融知识普及读本 > 第一章 人民币 > 第一节 人民币概述`。

> ⚠️ **权衡提示**：给所有块加同一个文档标题前缀，会给稠密向量引入**常量成分**，轻微压缩区分度。建议做成开关（`chunking.include_doc_title: true`）并用评估集实测，不要凭直觉决定。
>
> ⚠️ **规则顺序有讲究**：`2.1` 的规则必须排在 `1.` 之前，否则 `2.1` 会被误判为「第 2 项」。

#### ✔️ 验证

```powershell
python docs\audit\diagnose_breadcrumb.py    # heading_path 深度分布
python docs\audit\test_chunker_rules.py     # 观察 PDF 产出的标题层级分布
```

验收：深度 ≥2 的块占比应显著上升；深度恒为 1 的现象消失。

#### 💡 学习要点

1. **不要把上游能力当作保证。** 任何依赖外部组件输出的逻辑，都要问一句"如果它给出的是退化的结果，我会怎样"。
2. **内容自身往往自带结构。** 中文文档的编号体系（第X章/节/条、一、、（一）、1.1）是**比样式更可靠**的层级来源——样式会丢，编号不会。
3. **多路径实现要有统一的语义约定。** 同一份代码走 Docling 和走 PyMuPDF 得到完全不同的层级，说明"层级"这个概念在两个通道间没有统一的契约。
4. **正则规则的顺序即优先级**，写层级规则时要把更具体的模式放在更宽泛的模式之前。

### P0-5 · 纯容器标题被丢弃与面包屑歧义

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（真实解析复现 + 导出 heading_path 聚合统计） |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🟠 中高 |
| **状态** | ✅ 已修复（后续由 P0-8 彻底解决） |
| **所属环节** | 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:200` |

#### 🔍 现象

- 章节容器标题（如「第二节 人民币防伪与反假」）**在索引中完全不存在**（0 块）。
- 一个 `heading_path` 同时指向 6 部不同的法律。

#### 🧪 证据

**(a) 容器标题被丢弃。** `chunker.py:200`：

```python
return [s for s in sections if s.blocks]
```

标题下若没有直接正文（下一个标题紧随其后），整个 section 被丢弃。实测：

| `heading_path` | 块数 | 说明 |
| :--- | :--- | :--- |
| `第二节摇 人民币防伪与反假` | **0** | 纯容器标题，**整个消失** |
| `第一节摇 人民币概述` | 1 | 仅 65 字符的引子 |
| `第一章 人民币` | 1 | 内容是第 14 页「第四套人民币面额」碎片，**标题与内容错配** |

**(b) 面包屑高度歧义。** 该 PDF 附录收录了多部法律，它们共享同一套章节标题：

```
6  第一章摇 总摇 摇 则     ← 分别来自《反洗钱法》(p224)、《中国人民银行法》(p206)、
                            《商业银行法》(p212)、《征信业管理条例》(p230) …
```

**一个 `heading_path` 指向 6 部不同法律。** 在深度恒为 1、又不含书名的情况下，面包屑既没有层级也没有区分力。

#### 🎯 根因

**(a) 遍历时只保留"有内容"的节点**，忽略了容器节点对**子节点路径的贡献**。`第一章 人民币` 自身没有正文，但它是所有子节的父级——丢掉它，子节就失去了章节归属。

**(b) 面包屑的作用域只到"文档"为止**，没有意识到**一个文档内部可能包含多份独立文书**。合订本（法律汇编、年报合集、论文集）是常见形态，此时"第一章"在不同文书里是完全不同的东西。

#### ✅ 解决方案

**(a) 靠 P0-4 的「文档标题压栈底 + 语义层级」自动解决。** 语义层级让「第一章」(level 1) 与「第一节」(level 2) 不再互相弹栈，容器标题会**作为后续子节点的面包屑前缀**保留下来，即使它自身不产出块。这比"给容器标题硬造一个空块"更干净——空块会引入无信息的向量。

**(b) 给面包屑加文书作用域。** 两条措施：

1. **检测合订本文书边界并重置栈**：当出现「第X章」且上一行是形如 `中华人民共和国[\u4e00-\u9fff]+法` 或 `[\u4e00-\u9fff]+条例` 的独立行时，视为新文书：

```python
# heading_rules.py
_DOCUMENT_TITLE_RE = re.compile(
    r"^(中华人民共和国[\u4e00-\u9fff]{2,20}(法|条例|办法|规定|通则)"
    r"|[\u4e00-\u9fff]{2,20}(条例|办法|规定))$"
)

def is_document_start(line: str) -> str | None:
    """返回文书名；不是文书起始行则返回 None。"""
    t = (line or "").strip()
    m = _DOCUMENT_TITLE_RE.match(t)
    return t if m else None
```

```python
# _parse_sections 内，在标题判定之前先判断文书边界
doc_name = is_document_start(line)
if doc_name:
    flush_para()
    stack = [(0, doc_title), (1, doc_name)]   # 重置层级栈，压入新文书
    current = _Section(heading_path=[t for _, t in stack])
    sections.append(current)
    i += 1
    continue
```

这样 `第一章 总则` 会变成 `金融知识普及读本 > 反洗钱法 > 第一章 总则`，歧义即消。

2. **替代方案（更彻底）**：把文书名提取为**独立字段** `document_section`，与 `heading_path` 分开存储，检索时可作为 Qdrant payload filter 使用。比塞进面包屑更干净，也不污染嵌入向量。

#### ✔️ 验证

统计「单一 `heading_path` 覆盖的最大块数」：`第一章 总则` 不应再是 6 块共享同一个面包屑。容器标题（如 `第二节 人民币防伪与反假`）应出现在其子块的面包屑中。

#### 💡 学习要点

1. **树形结构里，"没有自身内容"的节点不能简单丢弃**——它对子节点的**路径**有贡献。处理层级数据时要区分"节点自身的数据"和"节点作为路径一部分的价值"。
2. **面包屑的作用域要显式定义。** 到文档为止？到章为止？还是到"独立文书"？作用域没定义清楚，就会出现"同一个面包屑指向不同实体"的歧义。
3. **合订本是真实且常见的文档形态**，尤其在法律、标准、年报领域。设计文档模型时应当假设"一个文件 ≠ 一份文书"。

### P0-6 · 正文句子被误判为标题

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（导出全部 `heading_path` 后人工核查异常值） |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🟠 中高 |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:165-166` |

#### 🔍 现象

面包屑里出现正文句子，语义连贯的正文被错误切碎：

| `heading_path` | 性质 |
| :--- | :--- |
| `机制。` | 正文句子片段（page 197） |
| `防伪特征:` | 正文逗号前片段（page 22） |
| `旅游购物报关单办理。` | 正文句子 |
| `盂固定人像水印` | OCR 乱码 + 正文 |
| `2郾 办理程序` | 编号被当成顶级标题 |

#### 🧪 证据

根因：`chunker.py:165-166` **只要 Markdown 里是 `#` 就无条件当标题**，没有任何启发式校验：

```python
m = _HEADING_RE.match(line.strip())
if m and len(m.group(1)) <= self.cfg.heading_max_level:
```

解析器（尤其是基于版面分析/OCR 的）会**用字体大小、加粗等视觉特征猜测标题**，正文中的强调句、独立成行的短句很容易被误判。

#### 🎯 根因

**只有正例规则，没有负例规则。** 判定逻辑是"像标题"（有 `#`），缺少"不像标题"的排除条件。任何基于启发式的分类都需要两侧的规则，否则假阳性无法收敛。

#### ✅ 解决方案

引入 RAGFlow `not_title()` 思路的伪标题过滤。新增规则：

```python
# heading_rules.py
_SENT_PUNCT_RE = re.compile(r"[,;，。；！!：:]")
_ARTICLE_RE = re.compile(rf"^第[{_CN_NUM}]+\s*条")


def not_title(text: str) -> bool:
    """True = 这不是标题，而是正文（照 RAGFlow not_title 思路，中文友好）。"""
    t = (text or "").strip()
    if not t:
        return True
    # 第X条 一律当标题（法条场景）
    if _ARTICLE_RE.match(t):
        return False
    # 过长 → 多半是正文
    if len(t.split()) > 12:
        return True
    # 中文长句且不含空格 → 正文
    if " " not in t and len(t) >= 32:
        return True
    # 含句读标点 → 正文
    return bool(_SENT_PUNCT_RE.search(t))
```

在标题判定处接入。**注意**：判定为正文时，要把该行的 `#` 前缀**剥掉**再当正文，否则噪声符号会进入索引：

```python
if m:
    title = m.group(2).strip()
    if is_running_header(...) or not_title(title):
        # 伪标题 → 降级为正文（剥掉 # 标记）
        if not buf:
            buf_page = page
        buf.append(title)
        i += 1
        continue
    ...  # 正常建节
```

新增配置：

```yaml
chunking:
  title_rules: true             # 启用中文标题层级识别与伪标题过滤
```

> ⚠️ **注意负例规则的误伤**：`not_title` 的「含标点即正文」会误伤形如「一、什么是资产配置?」这类**带问号的标题**。应对方针：若文本命中 `_LEVEL_RULES`（即 `semantic_level(t) is not None`），**豁免标点检查**，直接认定为标题。

#### ✔️ 验证

`docs/audit/diagnose_breadcrumb.py` 的高频 `heading_path` 列表中不应再出现以 `。` / `:` / `，` 结尾的条目。

#### 💡 学习要点

1. **启发式分类必须同时有正例和负例规则。** 只有"像什么"没有"不像什么"，假阳性就没有收敛机制。
2. **降级处理要清理痕迹。** 把伪标题降级为正文时，必须剥掉 `#` 标记——否则会把 Markdown 噪声带进索引和嵌入。
3. **负例规则本身也会误伤**，需要为正例（强结构信号，如「一、」「第X条」）设置豁免通道。

### P1-1 · PDF 乱码字符污染索引，破坏关键词匹配

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（导出真实 chunk 文本发现乱码，追溯至分词影响） |
| **代码引入** | 2026-10-10；2026-10-14 曾做清洗（`sanitize_markdown`）但覆盖不全 |
| **严重度** | 🟠 中高 |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 解析 |
| **代码位置** | `src/wealth_rag/ingestion/parser.py:48-66`、`199-223` |

#### 🔍 现象

PDF 文本中混入大量由 CID→Unicode 映射错误产生的乱码汉字：`摇`、`郾`、`也`、`冶`、`页`、`盂`、`藔`。它们**插入在词与词之间**，破坏分词与关键词匹配。

#### 🧪 证据

索引中的实际文本：

```
"第一章摇 总摇 摇 则"
"三、 结息和计息方式"
"1郾 办理程序"
"白银也 2015页 74 号"          ← 应为「银发〔2015〕74 号」
```

当用户查询「第一章 总则」时：

| 来源 | jieba 分词 + 中文 2-gram 结果 |
| :--- | :--- |
| 查询「第一章 总则」 | `第一` / `一章` / `总则` |
| 索引「第一章摇 总摇 摇 则」 | `第一` / `一章` / `章摇` / `总摇` / `摇` / `则` |

**`总则` 这个词在索引中根本不存在**，BM25 无法命中。

`parser.py` 现有清洗只覆盖两类情况：

- `sanitize_markdown`（`:48-66`）：只处理「同一汉字连续 ≥5 次」的乱码串；
- `strip_chars` / `_detect_bad_fonts`（`:199-223`）：只在 **PyMuPDF 通道**生效，基于字体统计。

**Docling 通道产出的一次性乱码字符没有任何清洗。**

#### 🎯 根因

**PDF 文本提取本质是"字形 → 编码"的逆映射，映射表损坏就会产生系统性错误字符。**

这类乱码与"重复字符噪声"（`sanitize_markdown` 处理的类型）在形态上完全不同：

| 类型 | 形态 | 现有处理 |
| :--- | :--- | :--- |
| 重复型 | 同一汉字连续 ≥5 次（装饰边框） | ✅ 已处理 |
| 替换型 | 特定汉字**系统性地**出现在不该出现的位置 | ❌ 未处理 |

`_garbage_chars` 的字体统计思路本可覆盖替换型，但它被**限定在 PyMuPDF 通道内**，而该 PDF 实际走的是 Docling 通道。

#### ✅ 解决方案

**(a) 通用的乱码字符归一化**（推荐）：扩展 `parser.py`，对**所有解析通道**统一做出口清洗。

```python
# parser.py
#: 已知的 CID 映射错误字符（本项目实测）。建议做成配置项，便于按语料调整。
_DEFAULT_GARBLED = "摇郾也冶页盂藔"

def normalize_garbled(markdown: str, garbled: str) -> str:
    """把乱码字符替换为分隔空格，恢复词边界。

    「第一章摇 总摇 摇 则」→「第一章 总 则」
    「1郾 办理程序」      →「1 办理程序」
    """
    if not garbled:
        return markdown
    cls = "".join(re.escape(c) for c in sorted(set(garbled)))
    out = re.sub(f"[{cls}]+", " ", markdown)
    # 折叠多余空格与行首空格
    out = re.sub(r"[ \t]{2,}", " ", out)
    return "\n".join(ln.strip() if ln.strip() else ln for ln in out.split("\n"))
```

在 `DocumentParser.parse` 的出口统一调用（目前 `sanitize_markdown` 只在非 md/txt 分支调用，应一并覆盖并调整顺序）：

```python
markdown = sanitize_markdown(markdown)
markdown = normalize_garbled(markdown, self.settings.parsing.garbled_chars)
```

新增配置：

```yaml
parsing:
  garbled_chars: "摇郾也冶页盂藔"   # PDF CID 映射错误产生的乱码字符，替换为空格
```

> ⚠️ **风险与建议**：字符表是语料相关的。若某个字（如「也」「页」）在该 PDF 中是合法正文用字，会被误删。
> 建议先用统计脚本确认这些字在语料中的分布（正常字体 vs 乱码字体），再固化字符表——`parser.py` 里已有的 `_garbage_chars` 正是这套逻辑，**把它从 PyMuPDF 通道提取成共用工具即可**，而不是手工维护字符表。

**(b) 顺带修复标题识别**：归一化后 `第一章摇 总则` → `第一章 总则`，P0-4 的标题正则才能真正匹配上。

> **依赖关系**：本条是 P0-4 / P0-6 的**前置修复**——乱码不清理，标题正则匹配率会很低。

#### ✔️ 验证

```powershell
python docs\audit\test_chunker_rules.py    # 测试 3 观察标题文本是否已归一化
```

建议新增一条诊断：对同一查询分别在「含乱码」与「归一化后」的索引上跑 BM25，比较命中率。

#### 💡 学习要点

1. **PDF 文本提取是逆映射，不是 OCR 意义上的"识别"**。CID→Unicode 映射表损坏会产生**系统性、非随机**的错误字符——同一个字形永远映射到同一个错字。
2. **噪声有不同类型，处理手段不能复用。** "重复型"靠正则去重，"替换型"要靠字体/分布统计识别，两者形态和判据都不同。
3. **通道隔离是隐患。** 清洗逻辑只挂在 PyMuPDF 分支上，导致换到 Docling 分支就完全裸奔——**出口清洗应当放在所有分支汇合之后**。
4. **乱码会同时破坏多种下游能力**：分词（BM25 失配）、正则（标题识别失败）、嵌入（语义被噪声稀释）。修一处收益是多处的。

### P1-2 · 短块与噪声块入库

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（统计块长度分布与极短块内容） |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🟡 中 |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py` 出口（无后处理） |

#### 🔍 现象

30 个块的正文短于 40 字符，其中包含完全无信息的块。

#### 🧪 证据

| 正文 | 长度 | `heading_path` | 性质 |
| :--- | :--- | :--- | :--- |
| `续表` | 2 | `三、 结息和计息方式` | 表格跨页标记 |
| `66` | 2 | `目摇 摇 录` | 目录页码残块 |
| `<!-- image -->` | 14 | `1郾 住房商业性贷款` | 图片占位符 |
| `期货交易的基本特征可以归纳为以下几个方面:` | 21 | `(二) 期货交易的特点` | 标题下只有引子句 |

最后一行是典型的「标题与内容切开」：标题块只剩一句引言，真正的 1–6 条特征全在子标题块里。

#### 🎯 根因

**缺少切分产物的出口质量检查。** 切分器只负责"按规则切"，没有任何"切出来的东西是否有价值"的判断。

更深一层：这些短块的成因**各不相同**，处置方式也不应相同：

| 成因 | 正确处置 |
| :--- | :--- |
| 页眉把章节切断（P0-1） | 修根因，短块自然消失 |
| 目录页码残块（P0-2） | 过滤掉 |
| 图片占位符 | 过滤掉 |
| 容器标题的引子句 | **合并**进相邻块，不能丢 |

#### ✅ 解决方案

在 `chunk()` 出口加一道后处理，**过滤噪声 + 合并短块**：

```python
# heading_rules.py
_NOISE_ONLY_RE = re.compile(
    r"^(?:<!--.*?-->|续表|<!--\s*formula-not-decoded\s*-->|[\d\s.、,，\-]+)$"
)

def is_noise_only(text: str) -> bool:
    """整块只有噪声/占位符/页码时返回 True。"""
    t = (text or "").strip()
    return (not t) or bool(_NOISE_ONLY_RE.match(t))
```

在 `chunker.py` 的 `chunk()` 里，按 section 分组组装后再做合并（**在同一节内合并，不跨节**，避免破坏面包屑语义）：

```python
def _merge_short_pieces(self, pieces: list[_Piece], min_chars: int) -> list[_Piece]:
    """把过短的块并入同节相邻块，而不是直接丢弃（避免丢内容）。"""
    kept: list[_Piece] = []
    for p in pieces:
        if is_noise_only(p.raw_text):
            continue                       # 纯噪声：丢弃
        if kept and len(p.raw_text.strip()) < min_chars:
            prev = kept[-1]
            merged_raw = f"{prev.raw_text}\n\n{p.raw_text}".strip()
            merged_embed = f"{prev.embed_text}\n\n{p.embed_text}".strip()
            kept[-1] = _Piece(merged_embed, merged_raw, prev.chunk_type, prev.page)
        else:
            kept.append(p)
    return kept
```

新增配置：

```yaml
chunking:
  min_chunk_chars: 30    # 小于该长度的块并入同节相邻块
```

> **说明**：治理 P0-1（页眉不再切断章节）后，大量碎片会**自然消失**——因为原本被页眉切碎的段落会重新合并为一个完整的节。因此这一步是**兜底**，不是主力。建议在 P0-1 之后再做，观察还剩多少短块。

#### ✔️ 验证

`docs/audit/dump_chunks.py` 的「正文 <40 字符的块」计数应从 **30 → 接近 0**。

#### 💡 学习要点

1. **"无信息"与"信息少"要区别对待**：前者丢弃，后者合并。一刀切地丢弃会丢内容。
2. **很多"输出质量问题"其实是上游问题的表征。** 先修根因，再看还剩多少——否则会在兜底逻辑上过度投入。
3. **合并要保持作用域。** 跨节合并会破坏面包屑语义（合并后的块属于哪个标题？），所以限制在**同节内**合并。

### P2-1 · `overlap_tokens` 是死配置

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（`grep` 全库引用 + 实测改值无效） |
| **代码引入** | 2026-10-10（配置自初始提交即存在，**从未被实现**） |
| **严重度** | 🔵 低（但涉及"虚假能力声明"） |
| **状态** | ✅ 已修复 |
| **所属环节** | 配置 |
| **代码位置** | `src/wealth_rag/config.py:59`、`config.yaml:48`、`tokenizer.py:55-63` |

#### 🔍 现象

`config.yaml` 里声明了块间重叠，README 也描述了该能力，但**实际完全不生效**。

#### 🧪 证据

- `config.py:59` 声明 `overlap_tokens: int = 0`；
- `config.yaml:48` 有 `overlap_tokens: 0  # 块间重叠 token 数（默认 0 对齐 naive；>0 时开启重叠）`；
- **`chunker.py` 全文没有任何地方引用 `overlap_tokens`**（`grep` 结果：仅 config 两处出现，chunker.py 只有 `breadcrumb` / `heading_max_level`）；
- `tokenizer.py:55-63` 的 `TokenCounter.tail()` 注释写着「块间重叠用」，但**无人调用**。

实测：把 `overlap_tokens` 设为 128 后重新切分，块边界完全不重叠（块 0 结尾「第 35 句」，块 1 开头「第 36 句」）。

#### 🎯 根因

**配置项是契约，声明而未实现比不声明更有害。**

配置文件和 README 共同构成了"系统能力清单"。一个声明了但未实现的配置，会让使用者（包括未来的自己）产生**错误的能力认知**——花时间去调一个根本没有接线的旋钮。

从工程习惯看，根因是**"先占位后实现"的开发顺序缺少闭环检查**：占位时写了配置和注释，实现时忘了，而没有任何机制（测试、lint、文档校验）能发现这个缺口。

#### ✅ 解决方案

**二选一，不要含糊。**

**方案 A：实现它。** 在 `_merge_segments` 开新组时，用上一组尾部做前缀：

```python
def _merge_segments(self, segments: list[str]) -> list[str]:
    max_tokens = self.cfg.max_tokens
    overlap = self.cfg.overlap_tokens
    pull_limit = int(max_tokens * 1.25)
    groups: list[str] = []
    cur, cur_tokens = "", 0
    for seg in segments:
        t = self.counter.count(seg)
        if cur and cur_tokens + t > max_tokens:
            if self._should_pull(cur, seg) and cur_tokens + t <= pull_limit:
                cur += seg
                cur_tokens += t
                continue
            groups.append(cur)
            tail = self.counter.tail(cur, overlap) if overlap > 0 else ""
            cur = tail + seg
            cur_tokens = self.counter.count(cur)
        else:
            cur += seg
            cur_tokens += t
    if cur.strip():
        groups.append(cur)
    return [g.strip() for g in groups if g.strip()]
```

> **需同步决定**：重叠部分是否也进 `raw_text`？进 → 内容一致但 LLM 上下文有重复；不进 → `text` 与 `raw_text` 结构不一致。建议**都进**，保持单一事实来源。

**方案 B：删掉它。** 从 `config.py`、`config.yaml`、`README.md` 中移除该配置，并注明「当前不使用块间重叠」。

> **参考数据**：Chroma 2024-07 的切分评测显示 `overlap` 会拉低 IoU（重复 token 被惩罚），但在**小嵌入模型**下 overlap 对 recall 更重要。本项目用 0.6B 模型属小模型，**值得实测而非默认关闭**。建议在评估集就绪后做 `{0, 64, 128}` 扫描。

#### ✔️ 验证

改值后重新切分，相邻块的边界文本应出现重叠；或写一个断言测试：`overlap_tokens > 0` 时，相邻块的 token 集合交集非空。

#### 💡 学习要点

1. **配置即契约。** 声明未实现的功能会造成虚假的能力认知，危害大于"没有这个功能"。
2. **"占位"必须有闭环检查**，否则遗忘是必然的。可以用一个测试断言"所有声明的配置项都被代码引用"来兜底。
3. **未使用的辅助函数是信号。** `TokenCounter.tail()` 存在但无人调用，这本身就是"某个功能没接完线"的线索。

### P2-2 · `parent_text` 冗余存储

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（代码审阅 + 统计 `parent_text` 携带率） |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🔵 低（存储与传输放大） |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 数据建模 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py:84-86`、`models.py:25` |

#### 🔍 现象

335 个块的 payload 里各自重复存了一份所属节的全文。若某节拆成 10 个子块，节全文就被存了 10 份。

#### 🧪 证据

`chunker.py:83-86`：

```python
parent_id = f"{doc_id}-s{si}" if len(pieces) > 1 else None
parent_text = (
    "\n\n".join(b.content for b in sec.blocks).strip() if parent_id else None
)
```

`parent_text` 随后被写入**每一个**子块的 payload（`models.py:25`、`to_payload()`）。

实测：722 个块中 **335 个**带 `parent_text`。

#### 🎯 根因

**父子块的关系被实现为「复制」而不是「引用」。**

`parent_id` 其实已经是一个引用（子块已能定位父块），但同时又把父块全文复制进了子块 payload。这是"读取方便"（避免二次查询）与"存储经济"（避免重复）之间的取舍——当前选择了前者，但没有评估放大的量级。

#### ✅ 解决方案

把父块**独立存储**，子块只保留引用：

**方案 A（推荐，改动小）**：父块作为独立 point 存入同一集合，但不参与向量检索。

```python
# 子块 payload：只存 parent_id
# 父块 payload：chunk_type="parent"，text=节全文（含面包屑），不写 dense/sparse 向量
```

检索命中子块后，按 `parent_id` 回查父块。Qdrant 本地模式回查成本极低。

**方案 B**：父块存独立集合（`chunks_parent`），与主集合解耦。

**顺带的好处**：父块独立后可以**单独建立粗粒度索引**，用于"整节级"召回兜底——当子块全部命中不佳时，父块级检索能提供更鲁棒的召回。

> **注意**：当前 `parent_id` 仅在 `len(pieces) > 1` 时生成——单块节没有父块。改造时需统一策略（例如单块节也建父块，或明确不建）。

#### ✔️ 验证

统计 payload 总字节数，改造后应显著下降（当前 PDF 那本书的 335 个块各自带着整节文本）。

#### 💡 学习要点

1. **关系型数据用"引用"而非"复制"。** 当已经有 `parent_id` 这样的引用字段时，再复制一份全文就要问"是否真的需要为了省一次查询而付出 N 倍存储"。
2. **冗余有时是合理取舍**，但应当**显式评估量级**后再决定，而不是顺手写进去。
3. **拆出父块会带来额外收益**：父块可以独立建索引，形成多粒度召回。

### P2-3 · `heading_max_level` 与 PyMuPDF 链路冲突

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15 |
| **发现方式** | 系统审查（真实解析复现，对比两个解析通道的标题层级） |
| **代码引入** | 2026-10-10（初始提交） |
| **严重度** | 🔵 低（但是"隐性故障"——静默劣化） |
| **状态** | ✅ 已修复 |
| **所属环节** | 配置 |
| **代码位置** | `config.yaml:47`、`chunker.py:166` |

#### 🔍 现象

`heading_max_level: 4` 意味着 H5/H6 标题**不被当作节边界，会被降级为正文**。

#### 🧪 证据

用 PyMuPDF 通道解析同一 PDF 的前 30 页，实测标题层级分布：

```
{1: 1, 2: 2, 3: 1, 4: 2, 5: 3, 6: 14}
```

**H5/H6 占多数（17/23）。** 也就是说：一旦 Docling 失败回退到 PyMuPDF（`pdf_engine: auto` 的既定行为），**绝大多数标题会被整层丢弃**，层级比 Docling 通道更糟。

#### 🎯 根因

**硬编码阈值绑定了实现细节（`#` 的数量），而不是语义概念（"这是几级标题"）。**

不同解析引擎对 `#` 数量的用法差异极大：

| 通道 | `#` 数量的含义 |
| :--- | :--- |
| Docling | 几乎不用层级区分（全给 H2） |
| PyMuPDF | 用 H5/H6 表达深层标题 |

用一个固定的数值阈值去卡两个语义完全不同的信号，必然有一边被误伤。

#### ✅ 解决方案

由 **P0-4 的「语义层级 + `not_title` 过滤」统一解决**：**不再用 Markdown 的 `#` 数量作为硬过滤条件**，改为：

```python
if m:
    title = m.group(2).strip()
    if is_running_header(...) or not_title(title):
        <降级为正文>
    else:
        <建节>   # 无论 # 有几个，一律视为候选标题
```

同时把 `heading_max_level` 的语义改为**「允许的最大语义层级」**（默认放宽到 7，覆盖到「第X条」），并在配置注释中说明它约束的是**语义层级**而非 `#` 数量。

#### ✔️ 验证

```powershell
python docs\audit\test_chunker_rules.py    # 测试 1：H5/H6 标题应被识别为独立节
```

#### 💡 学习要点

1. **阈值要绑定语义，不要绑定实现细节。** 卡 `#` 的数量是绑定实现；卡"标题层级"才是绑定语义。
2. **多路径实现（不同引擎/降级通道）的隐性故障最危险**——它只在特定条件下触发，且表现为"静默劣化"而非报错。设计降级路径时，必须验证降级后的行为是否可接受。
3. **同一个参数在不同通道下语义不同时，应当先归一化再判断**，而不是让参数去适配所有通道。

1. **文档描述"意图"而非"行为"是漂移的根源。** 写文档时应当核对代码，而不是回忆当初想怎么做。
2. **可验证的能力声明才有价值。** 一条无法用命令验证的能力描述，迟早会与实现脱节。
3. **文档与配置的失真会浪费排查时间。** 本次审查中，「512-token 上限精确」这条差点让人跳过 `pull_limit = 1.25` 这个真实放宽点。

### P0-8 · PDF 无书签，且章标题在文本层缺失

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15（第二批：实现第一批修复时，做更深的版面诊断发现） |
| **发现方式** | 系统审查（PyMuPDF 直读版面：字号分布 + 书签 + 逐页线条） |
| **严重度** | 🔴 高（P0-5「面包屑错误父级」的真正根因） |
| **状态** | ✅ 已修复（有实测证据） |
| **所属环节** | 解析 |
| **代码位置** | 新增 `src/wealth_rag/ingestion/outline.py`，接入 `parser.py:_rebuild_outline` |

#### 🔍 现象

P0-5 用「编号重启检测」把错误父级从 38.2% 压到 7.1%，但**没能根治**：正文里始终只有
「第一章 人民币」和「第六章 支付结算」两个章标题，第 2–5、7–12 章的层级无法建立。

#### 🧪 证据

三条独立证据指向同一结论——**章标题在 PDF 里根本没有可用文本**：

| 检查 | 结果 |
| :--- | :--- |
| `doc.get_toc()` 书签 | **0 条**（259 页的 PDF 完全没有书签） |
| 第 8 页（第一章开头） | 有文本：`24.0pt 第一章` + `21.0pt 人 民 币`（**被拆成两行**） |
| 第 31 页（第二章开头） | **完全空白**——`get_text` 无文本、`get_images` 0 张、`get_drawings` 0 条 |
| 第 32 页 | 直接从 `14.7pt 第一节 存款` 开始 |

也就是说：第 2–12 章的标题**只存在于目录页（第 5–7 页）**，任何解析器都不可能"识别"出来。

同时发现两条**可用的替代信号**：

```
目录页版式极规整（标题行 / 页码行 / 省略号行 各占一行）：
  10.3pt  第二章摇存贷款
  10.3pt  23
  10.3pt  …………………………………………………………………

页眉携带当前章号（整行只有章号、没有章名 —— 与真标题可区分）：
  8.7pt  第二章      ← 出现在 94 页上，前向填充可归属 250/259 页
```

字号层次本身也很干净：`24.0/21.0pt = 章`、`14.7pt = 节`、`11.8pt = 一、`、`10.3pt = 正文`、`8.7pt = 页眉`。

#### 🎯 根因

**依赖了 PDF 书签（outline），而该文档没有书签；同时章标题的文本层内容物理缺失。**

RAGFlow `TitleChunker` 的优先级是「PDF outline → 正则族命中计数 → layout 兜底」。
本项目只实现了"正则族"这一层，而章标题的**文本**压根不存在，正则无从下手。
这不是实现 bug，而是**对输入形态的假设不成立**。

#### ✅ 解决方案

新增 `src/wealth_rag/ingestion/outline.py`，把 RAGFlow 的三级优先级扩成：
**PDF outline → 目录 + 页眉重建 → （交给 `heading_rules`）语义层级**。

1. **`extract_bookmarks`**：有书签直接用（通用性，本项目走不到这条）；
2. **`extract_toc`**：解析目录页——「第X章 <章名>」且其后两行内出现纯数字即一条；
   **只接受条目数 ≥3 的页面**（目录每页十几条，正文页几乎不会有），且**不首页即停**（目录跨 3 页）；
3. **`extract_running_chapters`**：整行只有章号（`^第X章$`）即为页眉，前向填充得 (物理页 → 章)；
4. **`inject_chapter_headings`** 双路锚点把合成标题写回 Markdown：
   - **页码锚点**：章的首个物理页（依赖阅读顺序与页码一致）；
   - **内容锚点**：该章第一个「节」标题所在处。

> **内容锚点是必需的，不是锦上添花。** 实测仅用页码锚点时，第十二章的 5 个节
> （共 42 个块）恰好出现在页码锚点**之前**——Docling 的阅读顺序本就不总与页码一致，
> 导致这些块失去章级祖先。补上内容锚点后，第十二章从 **2 块 → 43 块**。

#### ✔️ 验证

```powershell
python docs\audit\test_outline.py     # 大纲重建回归（12 章断言）
python docs\audit\verify_fix.py       # 章级覆盖率
```

| 指标 | 仅页码锚点 | 页码 + 内容锚点 |
| :--- | :--- | :--- |
| 面包屑含「第X章」的块 | 457 / 669 = 68.3% | **575 / 664 = 86.6%** |
| 第十二章 金融体系 | 2 块 | **43 块** |
| 第十一章 普惠金融 | 30 块 | **82 块** |

#### 💡 学习要点

1. **"没有书签"和"识别不出标题"是两件事。** 前者是文档属性，后者是文本层事实。诊断时必须把
   「解析器能力不足」与「信息根本不存在」分开——否则会一直在错误的方向上加规则。
2. **一份 PDF 的标题可能被拆行**（`第一章` 24pt + `人民币` 21pt），任何按行判定的方案都会漏。
3. **目录页是最可靠的结构信息源**，版式通常比正文规整得多；页眉则可作为"当前章节"的免费标注。
4. **锚点要有多路冗余。** 依赖单一锚点（页码）会因上游阅读顺序不稳而失效；内容锚点不依赖顺序，
   两者互补。**加锚点时一定要实测覆盖率，而不是假设它会生效**——本例第一版内容锚点因键格式
   不一致而静默失效（目录侧用节名、查找侧用「第X节+节名」）。
5. **静默失效比报错更危险。** 键不匹配不会抛异常，只会让注入数量为 0。

### P1-5 · 噪声标题建节并成为后续块的错误父级

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15（第二批：实现 P0-1 后跑回归样例时发现） |
| **发现方式** | 系统审查（构造「伪标题与噪声」样例回归） |
| **严重度** | 🟠 中 |
| **状态** | ✅ 已修复 |
| **所属环节** | 切分 |
| **代码位置** | `src/wealth_rag/ingestion/chunker.py` 标题闸门 |

#### 🔍 现象

`## 续表` 这类纯噪声行会被建成一个「节」，并**成为后续块的错误父级**：

```
hp=测试文档 > 续表 > 二、另一个正常标题     ← 「续表」成了父级
```

#### 🧪 证据

`is_noise_only("续表")` 返回 `True`，因此该节**产出的块被丢弃**——但**节本身仍然存在**，
它的 `heading_path` 留在层级栈里，被下一个标题继承。

也就是说：**过滤了内容，却漏了它对路径的贡献**（与 P0-5「容器标题」同源的问题）。

#### 🎯 根因

P0-1 的标题闸门当时只拦了「页眉」，没有拦「纯噪声标题」。而 `min_chunk_chars` 的合并逻辑
工作在**块**层面，管不到**节**层面。

#### ✅ 解决方案

把 `is_noise_only` 并入标题闸门——噪声标题**整行丢弃**，既不建节、也不降级为正文：

```python
if cfg.title_rules and (
    is_noise_only(title)
    or is_running_header(title, self._doc_title, self._heading_freq, cfg.running_header_min_count)
):
    flush_para()
    i += 1
    continue
```

#### ✔️ 验证

构造样例：`## 一、正常标题` → `## 机制。` → `## 续表` → `## 二、另一个正常标题`。
修复后「二、另一个正常标题」应与「一、正常标题」**同级**，不再挂在「续表」下。

#### 💡 学习要点

1. **过滤内容 ≠ 消除影响。** 一个被判定为噪声的节点，若它参与路径构建，就必须在**建路径之前**拦掉。
2. **噪声治理要覆盖所有"会改变状态"的入口**：标题会改层级栈，表格会开新块，页眉会重置栈。

### P2-5 · `citation` 与面包屑重复文档标题

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-15（第二批：验收检索输出时发现） |
| **发现方式** | 系统审查（真实检索结果逐条检视） |
| **严重度** | 🔵 低（观感问题，非缺陷） |
| **状态** | ⚠️ 待定（属取舍，非缺陷） |
| **所属环节** | 数据建模 / 呈现 |
| **代码位置** | `config.yaml` → `chunking.include_doc_title` |

#### 🔍 现象

检索结果的引用看起来重复：

```
金融知识普及读本 | 第 19 页 | 金融知识普及读本 > 第一章 人民币 > 第二节 人民币防伪与反假
└── doc_title ──┘            └── heading_path 首层，又是文档标题
```

#### 🧪 证据

实测 **665 / 664** 个块的面包屑首层与 `doc_title` 相同（由 `include_doc_title: true` 造成）。

#### 🎯 根因

`include_doc_title` 把文档标题压入层级栈底，让每个块都带上文档上下文——**这对检索是好事**
（跨文档消歧、BM25 命中书名），但 `citation` 属性同时单独输出了 `doc_title`，于是呈现层重复。

#### ✅ 解决方案

**这是取舍，不是 bug**，两种做法各有代价：

| 选择 | 收益 | 代价 |
| :--- | :--- | :--- |
| `include_doc_title: true`（当前） | 面包屑自带文档上下文，跨文档消歧强 | `citation` 重复；给同文档所有块加同一常量前缀，轻度压缩稠密向量区分度 |
| `include_doc_title: false` | 引用干净；向量无常量成分 | 失去文档级上下文（多文档语料下影响更明显） |

若只想消除呈现重复，**不必关闭它**——改 `citation` 更精准：

```python
# models.py
path = " > ".join(p for p in self.heading_path if p != self.doc_title)
```

#### ✔️ 验证

改 `citation` 后，引用不再出现两次文档标题；检索指标不变。

#### 💡 学习要点

1. **呈现层的问题优先在呈现层解决**，不要为了"看起来不重复"去动检索用的数据。
2. **同一个字段服务两个目的时，要问"哪一层更该妥协"**——这里检索优先，呈现让路。
