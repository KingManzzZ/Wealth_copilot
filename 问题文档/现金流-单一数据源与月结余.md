### CASH-1 · 同一笔收支存两份

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-18 |
| **发现方式** | 用户反馈"我说了本月结余 2000，为什么月结余没刷新" → 查库 |
| **严重度** | 🔴 高（"Agent 没记住"的观感来源） |
| **状态** | ✅ 已修复 |

#### 🔍 现象

Agent 用 `record_expense` 记一笔支出后，仪表盘的月支出 / 月结余**完全不变**；
用户会认为 Agent 没记住。反过来，`set_monthly_cashflow` 改了汇总，交易流水抽屉也不变。

#### 🧪 证据

实测库（`backend/db/data.db`，修复前）：

```text
monthly_cashflow: 0 行
transactions:     1 行（看牙 2000，2026-10-18）
dashboard.kpis:   monthly_income=0, monthly_expense=0, monthly_surplus=0
```

即**流水里有账、KPI 里没有**。dashboard 的 KPI 只读 `monthly_cashflow`
（`api/routes/dashboard.py` 的 `_build_kpis(get_latest_month())`），
而记账只写 `transactions`（`core/services/transactions.py`），二者没有任何同步代码。

同一问题的另一侧：用户说「本月结余 2000 元」那一轮，模型调用了
`get_assets / get_debts / calculate_net_worth / calculate_emergency_fund /
update_goal / calculate_goal_contribution` —— **没有一个写现金流的工具**。
它把 2000 当成测算假设，还把目标截止日改了。

#### 🎯 根因

**同一事实被存了两份，且派生量被当成了可写字段。**

- `monthly_cashflow`（汇总）与 `transactions`（明细）都能表达"本月收支"，但没有任何
  一方的写入会触发另一方更新；
- 结余本质是 `income - expense` 的**派生值**，却有一个"手工 UPSERT 汇总"的入口，
  等于允许它与明细长期不一致；
- 该工具的描述还写着"**主要用于测试或数据补录**"——它本来就不该出现在业务能力清单里。

> 与审查报告 BK-27 / G-11 是同一个问题，只是这次从"用户感知"侧被触发。

#### ✅ 解决方案（决策 A：流水为唯一数据源）

| 改动 | 文件 |
| :--- | :--- |
| 现金流 service 改为**按月聚合流水**（`strftime('%Y-%m', occurred_at)`），`surplus` 查询时现算 | `core/services/cashflow.py` |
| 删除 `monthly_cashflow` 建表；启动时**空表自动清理**（非空则保留并告警，不静默丢数据） | `core/database/schema.py` |
| `GET /api/cashflow` 保留为只读；`POST /api/cashflow` 下线 | `api/routes/cashflow.py` |
| 下线 `set_monthly_cashflow` 工具（工具数 24 → 23） | `tools_hub/cashflow_tools.py`、`tools_schema.py` |
| 删除前端从未被调用的 `getCashflow` / `upsertCashflow` | `frontend/src/lib/api.ts` |

**为什么不是决策 B（汇总为权威）**：B 需要定义"记了流水之后要不要覆盖汇总"，
而那正是产生两份数据的原因；单用户账本里"逐笔流水"的信息量严格大于"月度汇总"，
没有理由再维护一个可能漂移的副本。

#### ✔️ 验证

一次性脚本（临时库，未写入真实账本）30 项断言通过，关键几条：

- 建表后**不存在** `monthly_cashflow`；
- 记 9 月 18000/9500 → 结余 8500；记 10 月 8000/6000 → 最近月切到 10 月、结余 **2000**；
- `dashboard()` 直接调用：`monthly_surplus=2000`、`saving_rate=0.25`、图表按月份升序且不零填充；
- 走 `tools_route.route("record_income", …)`（模型真实调用路径）→ KPI 立即变化；
- 旧库迁移：空表被删、非空表保留并告警。

#### 💡 学习要点

1. **派生量不要有存储位。** 一旦能写，就必须回答"另一处什么时候同步"，而这个答案往往是"忘了"。
2. **"两份数据"的 bug 往往表现为"界面不刷新"**，根因却在数据模型层。
3. 迁移时**空表删、非空留并告警**：自动化只处理"确定无信息"的情况。

#### ⚠️ 遗留

现金流目前**没有固化测试**（验证用的是一次性脚本）。建议按
`backend/tests/cancel/` 的结构补一套 `tests/cashflow/`：聚合、负数、月份边界、迁移四类断言。

### CASH-2 · 「本月结余 2000 元」无法落库

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-18 |
| **严重度** | 🟠 中（用户说了、系统没记住） |
| **状态** | ✅ 已修复 |

#### 🔍 现象

用户说「本月结余 2000 元」，Agent 回了一段分析、改了目标，但**月度现金流仍然是空的**。
用户的原话是："为什么没有刷新月结余的状态"。

#### 🎯 根因（两层）

1. **语义层**：结余是方程 `income - expense = 2000` 的结果，只给右边**无解**——
   必须知道收入或支出中的至少一个，才能反推另一个。
2. **提示词层**：`prompt.py` 有 40 行讲 RAG 检索、有"缺参数先问用户"，但**没有一句**
   说"用户陈述财务状况时要落库"。审查报告 #15 也记着：13 个写工具在 prompt 中零提及。

于是模型合理地把它当成"对话里的一条信息"，而不是"一次数据录入"。

#### ✅ 解决方案

| 改动 | 内容 |
| :--- | :--- |
| prompt 新增「关于财务数据写入」 | 陈述即录入意图；**结余是派生值、没有"存一个结余"的工具**；只给结余时必须先追问收入或支出；**绝不编造金额把账做平**；落库后回显可核对口径 |
| 注入当前日期 | `agent.py` 在 system 消息末尾加「当前日期：…」。否则「本月」落到哪个月只能靠模型猜，`occurred_at` 可能记错月份 |
| 下线 `set_monthly_cashflow` | 它是"存一个汇总"的入口，与"结余不可写"直接冲突（见 CASH-1） |

#### ✔️ 验证

- 提示词规则已生效于 `SYSTEM_PROMPT`；工具清单从 24 降到 23，schema 与注册表一致（契约测试守住）。
- 端到端行为需要真实模型验证（`tests/rag/test_real_agent.py` 是同类入口），
  本次未跑——**这是待办，不是已证明**。

#### 💡 学习要点

**"模型能理解"和"系统会落库"是两件事。** 工具契约只规定"调用长什么样"，
不规定"什么时候必须调用"；后者只能靠提示词规则，并且要用真实模型回归。

### CASH-3 · 负结余的展示与语义

| 元信息 | 内容 |
| :--- | :--- |
| **发现时间** | 2026-10-18 |
| **严重度** | 🟡 低（后端语义正确，展示误导） |
| **状态** | ⚠️ 部分修复（后端已正确，前端待改） |

#### 🔍 结论先说

**月结余可以为负，而且不应该夹取。** 支出大于收入就是赤字，这是真实语义；
代码里没有任何 `max(0, …)`。实测：

```text
2026-09  收入 5000 / 支出 7000 → surplus = -2000，saving_rate = -0.4
2026-10  收入 0    / 支出 3000 → surplus = -3000，saving_rate = 0
```

金额本身永远为正（`transactions.amount` 有 `CHECK (amount > 0)`），
负结余完全来自"按类型求和"，不存在"负支出"这种输入。

#### 🔍 三个展示层粗糙点（待改）

| # | 现象 | 位置 |
| :--- | :--- | :--- |
| 1 | 月结余卡片**永远绿色 + 上升箭头**，-3000 也显得"向好" | `frontend/src/components/dashboard/kpi-overview.tsx` |
| 2 | 负数格式化成 `¥-2,000`（标准写法 `-¥2,000`） | `frontend/src/lib/utils.ts` 的 `formatCurrency` |
| 3 | 收入为 0 但有支出时，储蓄率被强制成 **0%**，于是"支出 3000 / 结余 -3000 / 储蓄率 0.0%"自相矛盾 | `backend/api/routes/dashboard.py`、`cashflow_tools.py` |

#### ✅ 建议方案（未实施）

1. KPI 卡按符号分色/换箭头（负结余用 `chart-3` + `ArrowDownRight`）；
2. `saving_rate` 在 `income == 0` 时返回 `None`，前端显示 `—`，而不是 0%；
3. `formatCurrency` 处理符号位置；
4. prompt 补一句：`surplus` 为负说明当月入不敷出（动用储蓄/借款），回答要明确指出，
   不要说成"平衡"——尤其当同时看到 `saving_rate: 0` 时，第 3 点会主动误导模型。

#### 💡 学习要点

**"能不能为负"是数据语义问题；"看起来像不像负"是展示问题。**
后端不该为了好看夹取数据；前端不该让颜色与箭头撒谎。
