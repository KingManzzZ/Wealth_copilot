# 02 · 前沿策略调研

> 目标：搞清"agent 执行到一半被叫停/失败时，已经生效的副作用怎么办"这件事，
> 工业界与学术界各自站在哪个位置、各自承诺什么、代价是什么。
>
> 结论先行：**回滚的关键不是"写一个 undo 函数"，而是"先有提交边界"**。下面四类方案，
> 区别就在于边界画在哪里、以及边界内允许什么发生。

## 2.1 补偿事务（Saga）：最成熟、最贴合本项目

### 原始形态

Saga 由 Garcia-Molina & Salem（1987）提出：把长事务拆成一串**本地事务**，每个本地事务
配一个**补偿事务**；任何一步失败，就按**逆序**执行已完成步骤的补偿。它牺牲隔离性
（中间状态对他人可见），换取不需要分布式锁与 2PC。

### 工业实现：Temporal

[Temporal 的 Saga Pattern](https://docs.temporal.io/design-patterns/saga-pattern) 把上面的模式
落成了 SDK 级惯例，几条工程细节值得直接抄：

1. **补偿在正向动作执行前注册**（推荐默认）。理由很硬：一张信用卡可能"扣款成功但
   Activity 返回失败"，此时只有预先注册的补偿才能覆盖它。代价是补偿必须能处理
   "正向根本没发生"的情况（空操作）。
2. **补偿必须幂等**，因为它可能被重试、也可能在正向未发生时执行。
3. **逆序执行**（LIFO）：后做的先撤，保证依赖顺序。
4. **补偿失败不能吞**：记录日志并继续执行剩余补偿，持久失败要报警转人工。
5. **正向动作带幂等键**，避免重试产生第二笔。

Temporal 官方给的对比表也很直白：

| 方案 | 一致性 | 回滚机制 | 耦合 | 可扩展性 |
|---|---|---|---|---|
| Saga（编排式） | 最终一致 | 补偿事务 | 松 | 高 |
| 两阶段提交 | 强一致 | 分布式锁/回滚 | 紧 | 低 |
| Saga（协同式） | 最终一致 | 事件驱动补偿 | 很松 | 高 |
| 本地事务 | 强一致 | 数据库回滚 | 无 | 单服务 |

**什么时候不该用 Saga**（同一页文档）：需要强 ACID、单服务内可用本地事务、**定义不出补偿**、
或者必须对外表现为原子——这四条任一条成立，就别硬套。

### Agent 专属形态：Restate

[Restate 的 Rollback on Failures](https://docs.restate.dev/ai/patterns/rollback) 直接把它做到了
**工具层**：每个工具执行完把 undo 动作压进列表，agent 遇到终态错误时逆序回滚。

```python
@durable_function_tool
async def book_hotel(wrapper, booking):
    ctx = restate_context()
    # 先注册补偿，再执行正向动作
    booking_ctx.on_rollback.append(
        lambda: ctx.run_typed("Cancel hotel", cancel_hotel, id=booking_id)
    )
    return await ctx.run_typed("Book hotel", reserve_hotel, id=booking_id, booking=booking)

try:
    result = await DurableRunner.run(agent, req.message, context=booking_ctx)
except restate.TerminalError:
    for compensation in reversed(booking_ctx.on_rollback):
        await compensation()
    raise
```

要点：**compensation 与 forward 都是 durable step**，所以即使进程在回滚途中重启，
补偿也会继续跑完，不会"回滚到一半"。这正好补上本项目最担心的 M5（崩溃）。

### 对本项目的适配

- 每个写工具天然有逆操作：`record_*` → 按返回的 id 删除；`update_*`/`upsert_*` → 恢复 before 快照；
  `delete_transaction_tool` → 把删掉的行重新 insert。
- 需要补的是：**谁记录、记在哪、什么时候执行**（见 03）。
- 不需要补的：分布式协调、跨服务补偿——我们只有一个 SQLite。

## 2.2 语义事务与影子状态：学术界的最新答案

**Cordon: Semantic Transactions for Tool-Using LLM Agents**（EuroSys 2027，[arXiv:2606.17573](https://arxiv.org/abs/2606.17573)，
2026-06）指出现有 agent runtime 的根本问题：工具被暴露成**孤立 RPC**，每次调用单独审批/执行，
于是"跨步骤才暴露的风险"（读取的密钥 → 摘要 → 发给外部；多文件编辑的语义冲突）在结构上
无法被拦住。它的主张是：

> 需要的不是"再加一个 per-call guardrail"，而是一个**任务级的运行时边界**。

### 抽象：语义事务

Cordon 把一次任务建模成

```
T = ⟨scope, intents, R, W, D, E, O, G, A, status⟩
```

| 字段 | 含义 |
|---|---|
| `scope` / `intents` | 任务边界与其中的工具意图 |
| `R` | 读到的锚点（证据） |
| `O` / `G` | 工具返回/派生的语义对象，以及它们之间的依赖（lineage） |
| `W` / `D` | 可逆的本地写与删（**影子状态**） |
| `E` | 外部副作用（**暂存在 outbox**，不立即释放） |
| `A` | 委托的权限与审批义务 |
| `status` | active / validating / committed / aborted / compensated |

协议三段：**Prepare**（本地写进 shadow、外部效果进 outbox）→ **Validate**（把 lineage、权限、
暂存效果、策略作为一个整体校验）→ **Commit / Abort**（通过则原子提升 shadow + 释放效果；
否则丢弃 shadow、封存审计记录）。

### 工程实现

- **tool-dispatch interposition**：在工具分发处拦截，而不是改每个工具；
- **shadow-state engine**：可逆变更先写在影子状态；
- **effect outbox**：对外动作先不下发；
- **recovery log**：记录跨边界状态，供崩溃后恢复与补偿。

### 实验数据（论文自述）

- 45 个风险工作流：**裸执行 45/45 全部提交了违规效果**；基于现有防御边界的适配方案只拦住 14/45；
  Cordon **45/45 在提交前拦截**；
- 回滚延迟中位数 **4.17ms**，15/15 恢复检查通过；
- 排除审批等待后，任务平均耗时反而降低 **24.6%–27.9%**，token 用量降低 **23.6%–28.4%**
  （论文解释：早失败省掉了后续无用步骤）。

### 对本项目的意义与代价

- **方向正确**：把"写"和"提交"拆开，是唯一能让"取消即不生效"成立的结构；补偿只是退而求其次。
- **代价很大**：要改造工具分发、引入影子表、把外部效果排队；本项目只有 SQLite 且无外部副作用，
  影子状态能带来的额外收益主要是"一轮内多写的原子性"。
- **可借用的小设计**：`lineage`（哪个结果被哪个后续动作使用）与 `audit metadata`。
  我们至少该记录"哪个 turn 写了哪一行、由哪个工具调用产生"。

## 2.3 持久化执行与检查点：解决"恢复"，不解决"撤销"

### DBOS

[DBOS](https://docs.dbos.dev/python/programming-guide) 的模型是 **workflow = 若干个 step**，
状态**checkpoint 到系统数据库**（默认 SQLite，生产建议 Postgres）。进程崩溃/被中断后，
从**最后一个完成的 step** 继续，已完成的 step 不重跑。它保证的是"执行到底"，不是"撤销"。

### Temporal

Temporal 的 durable execution 在这里的价值是：**补偿动作本身也是 durable 的**——
Worker 挂了，补偿照样会被重试到成功（这正是 Saga 文档里强调的"补偿必须能重试"）。

### LangGraph

[LangGraph 的 time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel) 基于
checkpointer：可以 replay（从旧 checkpoint 重跑）与 fork（改状态后分叉）。
文档里两条警告非常关键：

> Replay **re-executes nodes** — LLM calls, API requests, and interrupts fire again and may
> return different results.
>
> `update_state` **does not roll back a thread**. It creates a new checkpoint that branches
> from the specified point.

也就是说：**时间旅行不是回滚**。它让"对话状态"回到过去，但已经发生的外部副作用不会消失，
重放还会**再发生一次**。把它当回滚用，是 agent 工程里最常见的一类误解（见 2.7）。

## 2.4 快照与回溯：只适合"可整体替换的状态"

### Claude Code checkpoints

[Claude Code 的 checkpointing](https://code.claude.com/docs/en/checkpointing) 在**每个开启一轮的
prompt 前**给文件拍快照，`/rewind` 可以"恢复代码+对话 / 只恢复对话 / 只恢复代码"，
每个会话保留最近 100 个 checkpoint。文档把边界写得很清楚：

| 不覆盖 | 说明 |
|---|---|
| Bash 命令改的文件 | `rm` / `mv` / `cp` 造成的改动**无法**通过 rewind 撤销 |
| 子代理的编辑 | 只有前台 fork 的 skill 能被恢复 |
| 会话外/并发会话的改动 | 默认不捕获 |
| 符号链接/硬链接 | 恢复时跳过并给警告 |
| 版本历史 | 明确"不是 VCS 的替代品" |

这条产品级限制很有说服力：**只要副作用发生在"你的工具"之外，快照就兜不住**。

### Arrakis

[Arrakis](https://github.com/abshkbh/arrakis) 把 agent 的代码执行放进 MicroVM，
提供 **backtracking**（回退到之前的状态）、REST API/Python SDK、端口转发。
适用于"整个环境可以快照/克隆"的场景（代码执行、computer use）。

### 对本项目的意义

SQLite 只有 184KB，做**整库快照**技术上很便宜（`VACUUM INTO` 或文件复制），但：

- 另一个会话这期间写的账会被一起抹掉（并发污染）；
- 快照之后用户的**手工修改**也会丢；
- 丢失"哪条写被撤销"的审计线索。

所以整库快照只适合当"最后的逃生舱"，不适合当常规回滚手段。

## 2.5 预防：审批与幂等（成本最低的一层）

### 人在环审批：Restate HITL

[Approvals with Pause & Resume](https://docs.restate.dev/ai/patterns/human-in-the-loop)：
用 durable promise（awakeable）把审批做成一等公民——

1. agent 创建 promise，拿到回调 id；
2. 通知审批人（Slack/邮件/控制台）；
3. agent **挂起**（不占算力，serverless 不计费）；
4. 审批人 resolve promise；
5. agent 从**挂起点**继续，进程重启也不影响；
6. 可加超时（示例是 3 小时），超时走降级分支。

参照实现还有 LangGraph 的 `interrupt()`：在节点中间暂停、恢复时重新执行该节点（所以审批
逻辑必须幂等）。

### 幂等键：Stripe 的做法

[Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests)：客户端生成
`Idempotency-Key`（建议 V4 UUID），服务端保存**第一次执行的状态码与响应体**，同 key 重试
直接返回保存的响应；v1 保留 24 小时，且会**比对参数**，参数不同则报错。

对 agent 的直接启示：**"取消后用户又说一遍"应当是可识别的重复请求**，而不是产生第二笔账。

## 2.6 横向对比

| 方案 | 能阻止写入 | 能撤销已提交 | 一轮内原子性 | 崩溃恢复 | 实现成本 | 本项目适配 |
|---|---|---|---|---|---|---|
| 补偿事务（Saga / Restate） | ❌（已发生才补偿） | ✅ 语义撤销 | ❌（逐条） | ✅ 需日志 | 低-中 | ⭐⭐⭐ 首选 |
| 语义事务（Cordon） | ✅（shadow 未提交） | ✅ 丢弃 shadow | ✅ | ✅ 有 recovery log | 高 | ⭐⭐ 未来方向 |
| turn 级 DB 事务 | ✅（未提交） | ✅ 回滚事务 | ✅ | ✅（DB 自动回滚） | 中 | ⭐⭐ 原子性升级项 |
| 整库/文件快照 | ❌ | ✅ 整体还原 | ✅ | ⚠️ 需快照留存 | 低 | ⭐ 逃生舱 |
| 人在环审批 | ✅（等待批准） | — | — | ✅（durable promise） | 中 | ⭐⭐⭐ 高风险写 |
| 幂等键 | — | — | — | ✅ | 低 | ⭐⭐⭐ 必做 |
| 时间旅行（LangGraph） | ❌ | ❌（重放会再执行） | — | — | — | ❌ 不适用 |

## 2.7 三个反模式

1. **把 replay 当 rollback。** LangGraph 的 replay 会重新执行节点与副作用；用它"撤销"，
   等于把写再做一遍。
2. **把快照当回滚。** 文件/整库快照只覆盖"快照得到的状态"；Bash、外部 API、并发会话都不在里面
   （Claude Code 文档专门列了这张限制表）。
3. **补偿没有日志、也不幂等。** 补偿跑到一半崩了，既没撤销、也没记录，还可能在重启后重复补偿
   （比如把已经删掉的行再删一次——删除本身幂等，但"恢复旧值"的补偿不幂等就会覆盖新值）。

## 2.8 落到本项目的三条结论

1. **先记录写集。** 没有 `turn_writes`，补偿与审计都无从谈起；这也顺手解决 M2 的可见性问题。
2. **补偿落库 + 幂等 + 冲突检测。** 学 Temporal 的"执行前注册、逆序执行、幂等、失败继续"；
   冲突检测是我们的额外要求（M4），因为用户可以随时手工改数据。
3. **原子性用 turn 级事务或影子状态，不要用整库快照。** 前者是数据库能力，后者会误伤并发写。
