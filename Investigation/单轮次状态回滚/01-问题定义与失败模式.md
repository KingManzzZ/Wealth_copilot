# 01 · 问题定义与失败模式

> 目标：把"单轮次状态回滚"说清楚到可以写测试的程度——**回滚什么、不回滚什么、怎样算成功**。

## 1. 术语

| 术语 | 本项目里的含义 |
|---|---|
| **一轮（turn）** | 一次 `POST /api/chat` 的生命周期：从用户消息落库，到 `done` / `cancelled` |
| **状态回滚** | 使这一轮产生的**持久化状态变化**不再生效，且用户看到的世界与数据一致 |
| **补偿（compensation）** | 用一个相反的写操作抵消已生效的写（删掉刚插入的行 / 恢复旧值），**不是**数据库的物理回滚 |
| **撤销日志（undo log）** | 记录"哪个工具、对哪张表、哪一行、改成了什么"，用于事后补偿与崩溃恢复 |
| **提交边界（commit boundary）** | 一个批次内的写要么全部生效、要么全部不生效的那个分界点 |
| **影子状态（shadow state）** | 写先落在暂存区，校验通过后才落到真实位置（Cordon 的核心） |
| **幂等（idempotent）** | 同一补偿执行一次与执行多次，结果相同 |

## 2. 本项目一轮里有哪些"状态"

| 状态 | 存储 | 本轮可写 | 能否回滚 | 备注 |
|---|---|---|---|---|
| 用户消息 | `messages` | ✅ 请求开始即写 | ⚠️ 可删，但**不建议**删（用户说的话是事实） | 回滚不应吞掉用户输入 |
| 助手消息 | `messages` | ✅ 结束时写 | ✅ 可删/改标记 | 已用 `interrupted` 标记 |
| 会话标题/更新时间 | `conversations` | ✅ | ⚠️ 可忽略 | 回滚标题意义不大 |
| 交易流水 | `transactions` | ✅ `record_income/expense`、`update/delete_transaction_tool` | ✅ 插入可删、更新可还原 | **回滚主战场** |
| 资产 | `assets` | ✅ `record_asset/update_asset` | ✅ UPSERT 前值可还原 | 新增行与改值两种 |
| 负债 | `debts` | ✅ `record_debt/update_debt` | ✅ | 同上 |
| 目标 | `goals` | ✅ `create_goal/update_goal/complete_goal_tool` | ✅ | 含状态字段 |
| 基本信息 | `basic_info` | ✅ `update_basic_info` | ✅ | 单行，快照小 |
| 月度现金流 / KPI | 无存储（派生） | — | ✅ 自动 | 由流水聚合，流水回滚即回滚 |
| RAG 索引 | Qdrant | ❌ 只读 | — | — |
| LLM token / 日志 | 外部 | — | ❌ **不可回滚** | 成本已发生 |

> 结论：**回滚面 99% 是"数据库行"**。这比通用 agent 简单——没有支付、没有发邮件、
> 没有外部 API 副作用，所以"补偿"可以做到接近物理还原。

## 3. 六类失败模式

### M1 · 单条写已提交后取消（最常见）

```
用户：记一笔午餐 35
[thinking] → tool_call record_expense → INSERT + COMMIT（35 元已进库）
用户点停止 → 检查点抛 TurnCancelled → 落库 interrupted 轮次
```

现状：**这笔 35 永远在库里**。用户以为"我停了，应该没记上"，但仪表盘支出已经变了。
这是本次调研要解决的核心场景。

### M2 · 一轮里多次写，只有部分完成

模型并行/连续调用两个写工具（`record_expense` + `update_goal`），第二个执行前被取消。
现状：第一个已提交、第二个没执行 → **半完成状态**，而消息里也看不出"哪些生效了"。

### M3 · 写成功但回答被中止 → 双方都不知道写过

策略 B 把被中止的轮次排除出模型上下文（见 S1-3）。后果：
- 用户看不到回答，只看到"已停止"；
- 模型下一轮也不记得自己写过；
- 用户再说"记一笔" → **重复记账**。

### M4 · 回滚撞上后续修改

取消发生在 `t1`，补偿在 `t2` 执行；期间用户（或另一个会话）改过同一行。
若无冲突检测，补偿会**删掉/覆盖用户的后续修改**——这比不回滚更糟。

### M5 · 进程崩溃 / 断连

worker 线程在"写完、还没补偿"之间崩溃。若补偿信息只在内存里，重启后**无从恢复**；
本轮会永远停在"已写入、未回滚、无记录"的状态。

### M6 · 外部副作用（本项目当前没有，但要预留）

接支付、发邮件、调用第三方 API 之后，补偿只能是"语义撤销"（退款、发更正邮件），
不可能物理回滚。届时必须区分"可补偿"与"不可补偿"的写，并在执行前就决定策略。

## 4. 现有实现的边界

```text
POST /api/chat
   │
   ├─ 用户消息落库（请求开始）
   ├─ worker: chat_stream
   │     ├─ 每轮开头 check(cancel)
   │     ├─ 每个 chunk check(cancel)
   │     ├─ 每个工具前 check(cancel)     ← 唯一能"阻止写入"的门
   │     ├─ tool_call → route() → INSERT + COMMIT   ← 一旦开跑必写完
   │     └─ tool_result（客户端可能收不到）
   └─ finally: 落库 assistant（interrupted=1）+ 解锁 + mark_done
```

已具备：

- ✅ **取消检查点**：工具执行**前**可以拦下；
- ✅ **工具结果落库**：即使被中止，已执行工具的 `result` 也在 `messages.tool_calls` 里；
- ✅ **上下文隔离**：`interrupted` 轮次不进模型上下文。

缺口：

- ❌ 没有"这一轮写了哪几行"的记录；
- ❌ 没有逆操作；
- ❌ 没有"回滚"这个状态（只有 `interrupted`）；
- ❌ 崩溃后无恢复依据。

## 5. 怎样算回滚成功（验收标准）

| # | 标准 | 说明 |
|---|---|---|
| A1 | **该轮写入不再可见** | 事务流水/资产/负债/目标/基本信息回到本轮开始时的值 |
| A2 | **派生数据自动正确** | 月度现金流与 KPI 由流水派生，无需单独回滚 |
| A3 | **幂等** | 同一轮回滚执行两次，结果与执行一次相同 |
| A4 | **冲突安全** | 若该行在本轮之后被改过 → **不覆盖**，标记 `conflict` 并告知用户 |
| A5 | **可审计** | `turn_writes` 里能查到每条写的 before/after 与补偿状态 |
| A6 | **崩溃可恢复** | 重启后能继续未完成的补偿，或至少把状态标成 `rollback_failed` |
| A7 | **用户可见** | 前端明确显示"已撤销 N 项"或"有 1 项无法撤销（原因）" |
| A8 | **不吞用户输入** | 用户消息保留；只回滚工具产生的副作用 |

## 6. 明确不做的

| 不做什么 | 原因 |
|---|---|
| 回滚已消耗的 LLM token | 不可逆，只能靠"停止得早"省钱 |
| 回滚历史轮次 | 超出"单轮次"范围；跨轮撤销需要版本链 |
| 回滚用户的手工修改 | 只认**本轮工具**产生的写 |
| 整库快照恢复 | 会误伤并发会话的写，且丢审计 |
| 物理级 WAL 回滚 | 需要 turn 级事务（P2 才做），且只解决原子性不解决已提交 |
