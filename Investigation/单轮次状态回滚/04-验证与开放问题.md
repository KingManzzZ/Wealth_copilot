| # | 用例 | 覆盖 |
|---|---|---|
| T1 | `insert_is_reverted_and_messages_disappear` | 记一笔 → 撤回 → 行删除、消息不可见、返回用户原话 |
| T2 | `no_writes_turn_can_be_withdrawn` | 只查不写的轮次也能撤回对话 |

| T5 | `conflict_aborts_whole_withdraw` | 数据之后被改过 → 整轮放弃、不覆盖、消息不撤 |
| T6 | `withdraw_any_turn_truncates_later` | 撤中间一轮：这轮及之后消失、更早保留、写集逆序撤 |
| T7 | `withdraw_middle_keeps_earlier` | 撤中间一轮时更早的轮次不受影响 |
| T8 | `single_turn_withdraw_keeps_later` | `truncate=false`：只撤目标轮，后面的对话与数据保留 |
| T9 | `proposal_targets_previous_turn…` | 提案默认指向上一轮、只读（前后计数不变） |
| T10 | `explicit_turn_id_is_honored` / `first_turn_has_no_previous` / `unknown_turn` / `no_context` | 提案的目标解析与错误分支 |
| T11 | `repeat_withdraw_is_not_found` | 重复撤回 → 404 |
| T12 | `withdrawn_messages_not_replayed` | 撤回的轮次不进模型上下文 |
| T13 | `withdraw_endpoint_roundtrip` | 路由：200/404、返回体、消息列表为空 |
| T14 | `withdraw_unknown_conversation_is_404` | 会话不存在 → 404 |

**每个用例一个一次性数据库**（`_support.temp_database()`），绝不写 `backend/db/data.db`。

> 这条规则是用一次真实事故换来的：路由测试最初漏了临时库，往真实账本写了一条
> 测试流水和一个会话；虽然撤回把流水删掉了，但会话/审计行需要手工清理。
> 现在所有测试都强制走临时库。

## 4.3 指标（实现已满足的部分）

| 指标 | 现状 |
|---|---|
| 写集覆盖率 | 由快照差异保证，**结构上不会漏**（5 张业务表全覆盖） |
| 撤回冲突 | 整轮放弃，**不覆盖用户修改**（T5） |
| 撤回延迟 | 一轮 1~3 条写，同步完成（毫秒级） |
| 误删 | 只删"本轮插入且未被修改"的行；改过的一律不动 |
| 消息隔离 | 唯一过滤点在 `get_conversation_messages`（T8） |

## 4.5 仍然开放的问题

1. **"点撤回"要不要提示确认？**
   现在用原生 `confirm`。若觉得打扰，可以改成"撤回后 5 秒内可撤销"，把确认换成可逆。

2. **撤回后模型该不该知道？**
   现在撤回的轮次完全消失（不进上下文）。若用户紧接着说"刚才那个不对"，模型不知道
   "刚才"指什么。可以注入一句极简事实（待办里列了）。

3. **截断语义是否符合预期？**
   撤回中间一轮会连同它之后的对话一起撤（否则上下文矛盾）。若用户只想"删掉某条消息但保留后面"，
   需要另一套消息级删除 + 上下文修复策略，不属于本轮范围。

4. **冲突时是否给"仍然恢复"？**
   现在整轮放弃（安全优先）。若真实使用中冲突频繁，再考虑让用户显式确认后强制恢复。
