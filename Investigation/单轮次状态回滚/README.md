# 单轮次状态回滚 · 调研与实现

> **起因**：用户点"撤回"时，要把**一轮对话**恢复到"没发送过"的状态。
> 它有两层，缺一不可：
> 1. **对话层**：这条用户消息 + 助手回答从会话里消失（模型下次也看不到）；
> 2. **数据层**：这一轮写进账本的流水/资产/负债/目标/基本信息要还原。
>
> 只做第一层会出现"对话没了、账上多一笔"；只做第二层会出现"账对了、对话还留着"。
>
> **状态**：P0 已实现（快照差异 + 撤回接口 + 前端按钮 + 10 个测试）。
> **调研时间**：2026-10-18。
> **范围**：`backend/api/routes/{chat,conversations}.py`、`backend/core/services/`、
> `backend/core/database/schema.py`、前端消息态。
>
> 相关：[`../../问题文档/Agent-生成中止与取消.md`](../../问题文档/Agent-生成中止与取消.md)（取消只停生成，不回滚写入）。

## 一页结论

**回滚不是"撤销一个请求"，而是给一轮执行建立"提交边界"。** 没有边界，就只能逐条补偿，
而逐条补偿永远存在"补偿到一半"的中间态。

前沿可以归成四类，覆盖不同层次的失败：

```
预防（别发生） → 暂存/提交边界（还没生效） → 补偿/快照（已生效，撤销） → 审计与恢复（崩了也能收尾）
```

| 类别 | 代表 | 解决什么 | 对本项目的可借用度 |
|---|---|---|---|
| 补偿事务（Saga） | [Temporal Saga](https://docs.temporal.io/design-patterns/saga-pattern)、[Restate Rollback](https://docs.restate.dev/ai/patterns/rollback) | 已提交的步骤，逆序 undo | ⭐⭐⭐ 最贴合：写工具都能定义逆操作 |
| 语义事务 / 影子状态 | [Cordon（EuroSys'27）](https://arxiv.org/abs/2606.17573) | 任务级提交边界：本地改写入 shadow、外部副作用进 outbox、validate 后统一 commit | ⭐⭐ 方向正确，工程量大 |
| 持久化执行 / 检查点 | [DBOS](https://docs.dbos.dev/python/programming-guide)、Temporal | 进程崩溃后从"最后一个完成的 step"恢复 | ⭐⭐⭐ 用于"补偿日志不丢" |
| 快照与回溯 | [Claude Code checkpoints](https://code.claude.com/docs/en/checkpointing)、[LangGraph time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)、[Arrakis](https://github.com/abshkbh/arrakis) | 把状态整体退回到某个点 | ⭐ 单文件 SQLite 可做，但会误伤并发写 |
| 审批与幂等 | [Restate HITL](https://docs.restate.dev/ai/patterns/human-in-the-loop)、[Stripe idempotency](https://docs.stripe.com/api/idempotent_requests) | 写之前先确认；重试不产生第二笔 | ⭐⭐⭐ 成本最低，先做 |

三条最值得记住的判断：

1. **先有边界，才有回滚。** 补偿是"事后擦屁股"，影子状态是"根本不擦"——后者更彻底，
   但要求工具层把"写"和"提交"拆开（Cordon 的做法）。本项目当前每个工具自己开连接、
   自己 commit，连"这一轮写了什么"都没有记录，所以第一步只能是**记录写集**。
2. **补偿必须幂等，且补偿日志必须落库。** Temporal 的实践是"**在执行前**注册补偿"，
   这样即使正向动作失败在中途也能被覆盖；Restate 的 agent 示例则维护一个 undo list、
   在终态错误时逆序执行。共同点：补偿可能被重试多次，必须能安全重放。
3. **replay ≠ rollback。** LangGraph 的时间旅行会**重新执行**节点（包括 LLM 调用与副作用），
   它给的是"分叉"而不是"撤销"；Claude Code 的 checkpoint 也只覆盖**自己的文件编辑工具**，
   不覆盖 Bash 命令造成的改动。判断一个方案是不是回滚，看它是否承诺"副作用不重复发生"。

## 本项目现状速览（P0 已实现）

| 能力 | 现状 |
|---|---|
| 停止生成 | ✅ `turn_id` + 取消接口 + 检查点 |
| 撤回一轮（对话） | ✅ 消息软删（`withdrawn=1`），不进上下文、不出现在列表 |
| 撤回一轮（数据） | ✅ 轮前/轮后快照差异 → `turn_writes` → 逆序还原 |
| 撤回任意一轮 | ✅ 从该轮起截断（后面的对话一并撤回，保证上下文不矛盾） |
| 冲突安全 | ✅ 数据在本轮之后被改过 → 整轮放弃，不覆盖 |
| 前端 | ✅ 每条用户消息一个「↩」图标 + 二次确认（不可恢复）+ 输入框回填 + 失败提示 |
| 测试 | ✅ `backend/tests/rollback/` 11 个用例（含截断与路由） |
| 崩溃恢复 | ❌ 未做：进程崩在轮次中途，`turns.status` 会停在 `running` |
| 写前确认 / 幂等 | ❌ 未做（删除/修改类仍无二次确认） |

## 实现路线（已落地的是 P0）

| 阶段 | 内容 | 状态 |
|---|---|---|
| **P0** | 快照差异 + `turn_writes` + 撤回接口 + 前端按钮 | ✅ 已实现 |
| **P1** | 撤回任意一条（截断到该轮之前）、30 秒内"恢复"、撤回后给模型一句提示 | 待做 |
| **P1** | 崩溃恢复：启动扫描 `turns.status='running'` 的遗留轮次 | 待做 |
| **P2** | turn 级事务（`BEGIN IMMEDIATE` … `COMMIT/ROLLBACK`） | 仅在需要更强原子性时考虑 |
| **P2** | 写前确认（删除/更新类）+ 幂等键 | 预防层 |

> 实现选的是**快照差异**，不是最初设想的"在每个工具里埋点"：
> 5 张业务表总量很小（184KB 库），每轮扫两遍的成本可以忽略，
> 换来的是"不改任何工具、不会漏记"。

**不推荐**整库快照回滚：会抹掉另一个会话这期间写的账，且丢审计。
