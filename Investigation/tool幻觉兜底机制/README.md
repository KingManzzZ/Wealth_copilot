## 一页结论

**前沿的共识不是"提高一次命中的准确率"，而是把工具名当作不可信输入**，用四道防线把不确定性关进笼子，并且**允许模型弃权**。

```
预防（不发生） → 拦截（不执行错的） → 修复（能自愈） → 收敛（不失控）
```

三条最有价值的判断：

1. **兜底的上限由解码层决定。** 能控制推理栈时，用语法约束把工具名变成枚举选择，名字幻觉在物理上不可能发生（TensorRT-LLM Guided Decoding 的 structural tag 就是这么做的）。本项目走第三方 OpenAI 兼容 API，拿不到这一层，只能靠服务端校验补齐——这是**约束条件，不是选择**。

2. **修复的关键不是模糊匹配，是错误信息的信息量。** 工业实现的经验很一致：把「可用工具清单」回灌给模型，远比盲重试有效。hermes-agent 甚至把一个"盲重试 3 次"的旧实现直接**改成**"喂错误信息让模型自己改"。

3. **"调了不存在的工具名"只是四类工具幻觉里的一类。** 只兜这一类会漏掉时机幻觉（重复调用）和内容幻觉（参数编造）——而这两类在本项目里目前完全没有兜底。

## 现有实现覆盖情况速览

| 幻觉形态 | 现状 | 判定 |
|---|---|---|
| 完全编造工具名 | `route()` 返回 `{"error": "未知工具: x"}` | ✅ 已兜，但**信息量为零** |
| 名字近失（`Search_Knowledge` / `get-assets`） | 精确匹配失败，误判为不存在 | ❌ **本不该失败** |
| 缺必填参数 | Python `TypeError` 原文回灌 | ⚠️ 已兜，但泄露实现细节 |
| 参数非合法 JSON | 降级 `{}` + route 报 json 错 | ✅ 已兜 |
| 参数是合法 JSON 但非对象 | `**kwargs` 抛怪错 | ⚠️ 已兜，错误信息不可读 |
| 重复调用同一工具 | 没有任何检测 | ❌ **完全没兜** |
| 参数值编造 | 无业务校验 | ❌ 属业务层，需另行设计 |

## 一句话回顾本项目相对同行的位置

`tools_route.py` 里"注册表由 schema 驱动、不随文件里的函数数量漂移"和"`_belongs_to_hub` 只认工具层内部函数"这两个设计，**已经构成了一道同行经常缺失的白名单防线**——后者还顺带保证了模型幻觉出的名字即使撞上某个辅助函数（`_render_payload` 之类）也进不了注册表。这部分是资产，后续改动不要把它的边界放宽。

短板集中在**修复的信息量**和**收敛的归因**上，也正是 Phase 0–2 要补的部分。
