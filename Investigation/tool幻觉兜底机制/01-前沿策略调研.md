# 工具调用幻觉兜底机制：前沿策略调研

> 调研对象：LLM Agent 调用外部工具时，模型输出**不存在或错误工具名**（以及更广义的工具幻觉）的检测、修复与降级策略。
> 落地对象：本仓库 `backend/core`（`tools_route.py` / `agent.py`，24 个工具，deepseek-flash 走 OpenAI 兼容 API）。

---

## 0. 摘要

这个问题的前沿做法可以用一句话概括：**不要把工具名当成模型"算出来的答案"，而要当成"用户输入"来校验。**

由此派生出一条完整的防线链，四层各自解决不同的问题，**互不可替代**：

| 防线 | 作用位置 | 目标 | 典型手段 |
|---|---|---|---|
| 预防 | schema / prompt / 解码 / 候选集 | 让幻觉不发生 | 名字设计、显式清单、弃权许可、**约束解码**、Tool RAG |
| 拦截 | 调用前 | 不执行错的东西 | 白名单、名称归一化、模糊匹配、参数 schema 校验 |
| 修复 | 错误回灌 | 一次不中能自愈 | **带信息量的错误载荷**、错误分级、重试预算 |
| 收敛 | 失败后 | 不失控、不误导 | 熔断、重复检测、**弃权动作**、归因文案 |

三条最值得记住的结论：

1. **兜底的上限由解码层决定，下限由错误信息质量决定。** 约束解码能从根上消灭名字幻觉，但它需要控制推理栈；拿不到那层时，服务端校验 + 高质量错误回灌是唯一可行的组合。
2. **"模糊匹配"不是重点，"错误信息里有没有可用工具清单"才是。** 两个独立工业实现的演进方向完全一致：从"盲重试"改成"把错误和清单喂回模型"。
3. **"调不存在的工具名"只占工具幻觉的一小部分。** 学术界的分类里它只是四类之一；只兜这一类会系统性漏掉重复调用（时机幻觉）和参数编造（内容幻觉）。

## 1. 问题界定：先把"幻觉"拆开

### 1.1 学术界分类（Relign / RelyToolBench）

目前最清晰的分类来自上海交大 X-LANCE 的 **Relign** 工作（[arXiv 2412.04141](https://ar5iv.labs.arxiv.org/html/2412.04141)，ICML 2025）。它把工具幻觉分成两大类、四小类：

| 大类 | 子类 | 定义 | 典型例子 |
|---|---|---|---|
| **工具选择幻觉**<br>（选错了） | **类型幻觉** | 调用了任务无关的工具，或**编造了工具集中不存在的工具** | 用户问负债，模型调 `get_assets`；或直接编一个 `query_debt_summary` |
| | **时机幻觉** | 调用时序错误，典型是**用相同输入重复调用同一工具** | 同一轮里把 `search_knowledge` 用同样的 query 调两次 |
| **工具使用幻觉**<br>（用错了） | **格式幻觉** | JSON 非法、参数名错、缺必填、类型错 | 把 `query` 写成 `q`；漏掉 `required` 字段 |
| | **内容幻觉** | 参数值是从模型脑子里编的，不是从用户输入推出来的 | 用户没说城市，模型自己填了"北京" |

**关键坐标**：本仓库 `tools_route.py` 现在兜住的是「类型幻觉 + 部分格式幻觉」；「时机幻觉」和「内容幻觉」完全没有兜。

论文还给了两个指标，后面第 7 节会用到：

- **RePR（Reliable Pass Rate）= Pass Rate − Task Hallucination Rate**：把"因为幻觉而侥幸通过"的任务扣掉。论文实测各模型的 RePR 明显低于原始通过率，说明**幻觉会污染成功率统计**——只看"任务成没成"会高估系统可靠性。
- **Utility = R_task − P_tool − P_hallucination**：成功 +20，多调的工具按次扣（上限 10），幻觉 −10。这个公式的价值在于**把"多试几次总能成"变成有代价的行为**。

### 1.2 映射到本项目的具体形态

| 形态 | 触发点（现有代码） | 现状 |
|---|---|---|
| 完全编造工具名 | `route()` 精确查表失败 @ `tools_route.py:181` | 返回 `{"error": "未知工具: x"}`，回灌给模型 |
| **名字近失**（`Search_Knowledge`、`get-assets`、`functions.get_assets`） | 同上 | **被当成"不存在"，本不该失败** |
| 缺必填参数 | `func(**kwargs)` 抛 `TypeError` @ `tools_route.py:187` | `str(e)` 原样回灌，暴露 Python 内部措辞 |
| 参数非合法 JSON | `json.loads` 抛错 | `agent.py:106` 先降级为 `{}`，`route` 再报 json 错 |
| 参数是合法 JSON 但非对象（`[1,2]`/`null`） | `func(**kwargs)` 抛 `TypeError: argument of type ... is not a mapping` | 兜住了但错误信息不可读；且 `tool_call` 事件已把 list 推给前端 |
| **重复调用同一工具** | 无任何检测 | **完全没兜** |
| **参数值编造** | 无业务校验 | 属业务层（如"用户没提供金额却记录了金额"），需另行设计 |

## 2. 总览：四道防线的作用与成本

```
                  ┌─────────────────────────────────────────────┐
   模型输出工具名  │  预防：schema / prompt / 解码 / 候选集裁剪    │  降低 P(幻觉)
        │         └─────────────────────────────────────────────┘
        ▼
   ┌──────────┐   ┌─────────────────────────────────────────────┐
   │ 归一化   │──▶│  拦截：白名单 · 归一化 · 模糊匹配 · 参数校验  │  拦住剩余大部分
   └──────────┘   └─────────────────────────────────────────────┘
        │ 命中                      │ 未命中
        ▼                           ▼
   ┌──────────┐   ┌─────────────────────────────────────────────┐
   │ 执行工具 │   │  修复：带信息量的错误载荷 · 错误分级 · 预算   │  把"失败"变"多一轮"
   └──────────┘   └─────────────────────────────────────────────┘
        │                           │ 修不好
        ▼                           ▼
                  ┌─────────────────────────────────────────────┐
                  │  收敛：熔断 · 重复检测 · 弃权 · 归因文案      │  不失控不误导
                  └─────────────────────────────────────────────┘
```

各防线的投入产出，按本项目的实际情况排序：

| 防线 | 实现成本 | 收益 | 本项目优先级 |
|---|---|---|---|
| 修复（错误载荷增强） | 极低（改一个 dict） | 高 | **P0** |
| 拦截（归一化 + 参数校验） | 低 | 高 | **P0** |
| 收敛（熔断 + 去重） | 低 | 中高 | **P1** |
| 预防（prompt 侧） | 极低 | 中 | **P1** |
| 预防（约束解码） | 高，且依赖部署栈 | 极高 | 暂不可用 |
| 预防（Tool RAG） | 中 | 工具数 > 50 才有意义 | 暂不需要 |

## 3. 防线一：预防

### 3.1 Schema 层：名字本身就是防线

几个被反复验证的经验：

- **名字要自解释且互不相似。** `get_assets` 与 `get_financial_profile` 语义邻近，是这个项目里最容易混的一对。名字越相似，类型幻觉越容易退化成"看起来很合理的错"，而这类错**最难被错误信息纠正**。
- **参数名用全称。** `query` 而不是 `q`，`start_date` 而不是 `sd`。模型有强烈的"缩写"倾向，全称能减少格式幻觉。
- **`description` 不能为空。** 这一点本仓库已有契约测试守住（`test_tool_contract.py` 里检查所有工具 description 非空），是对的。
- **工具数量存在舒适区。** BFCL / Gorilla 系列工作反复显示候选工具数上升时选择准确率下降；Tool RAG 类工作（见 3.4）专门为"上百上千个工具"设计。**经验阈值在 20–30 之间**，本项目 24 个还在"全量枚举"的舒适区，但已经接近边界。

### 3.2 Prompt 层：显式清单 + 弃权许可

这是成本最低的一层，但经常被忽略。BFCL 给非 function-calling 模型的 system prompt 是这么写的（见 [BFCL 官方 blog](https://gorilla.cs.berkeley.edu/blogs/8_berkeley_function_calling_leaderboard.html)）：

> "You are given a question and a set of possible functions... **If none of the function can be used, point it out.** If the given question lacks the parameters required by the function, also point it out. You should only return the function call in tools call sections."

那句 "point it out" 不是客套话，是**低成本的幻觉抑制剂**——模型的默认倾向是"必须调点什么"，明确给它一个"什么都不调、直接说明"的出口，能显著降低硬着头皮瞎调的概率。

对应到本项目 `prompt.py`，现在只提了 `search_knowledge` 和 `calculate_*` 两个工具族，没有"禁止臆造工具名"的约束。补一小节即可：

```text
## 关于工具名

* 只能使用系统提供的工具，工具名必须与清单完全一致，不要臆造、缩写或翻译工具名。
* 如果现有工具都不足以完成任务，直接用文字向用户说明，并指出缺什么信息，
  不要为了"显得在工作"而调用不相关的工具。
```

### 3.3 解码层：约束解码（最强，但本项目拿不到）

这是唯一能从物理上消灭"名字幻觉"的手段。

**原理**：在解码时用语法（JSON Schema / 正则 / EBNF）限制每一步的 token 候选集。工具名一旦被写成枚举，模型就**不可能**输出枚举外的名字。

**代表性实现**：

- **TensorRT-LLM Guided Decoding**（[官方文档](https://nvidia.github.io/TensorRT-LLM/features/guided-decoding.html)）支持 XGrammar / LLGuidance 两种后端，提供 JSON Schema、正则、EBNF、**structural tag** 四级约束。它的 function calling 示例直接把工具名做成语法分支：

  ```
  <function=get_current_weather>{"city": ..., "unit": ...}</function>
  <function=get_current_date>{"timezone": ...}</function>
  ```

  配置之后，模型输出第三个名字在语法层面就是不可能的。

- **OpenAI strict mode / structured outputs** 是同一思路的托管版本，把 schema 约束下沉到服务端解码。
- 开源的 XGrammar、Outlines、llguidance 也是同一族。

**本项目的现实约束**：deepseek-flash 走的是 OpenAI 兼容的 `client.chat.completions.create`，`base_url` 由环境变量 `LLM_URL` 指定，`extra_body` 只能塞厂商自定义字段——**拿不到 grammar 级约束**。所以这条路在当前架构下不可用，应记为"若将来自建推理（vLLM / TensorRT-LLM / SGLang）则优先启用"。

**重要认知**：这不是"我们选了另一条路"，而是**被架构决定只能走服务端校验**。所以第 4、5 节的工作不是锦上添花，是当前架构下的必要补偿。

### 3.4 候选集裁剪：Tool RAG

当工具规模上百，把全部工具塞进 context 会同时降低选择准确率、抬高成本。做法是把工具描述向量化，按用户 query 检索 Top-K 再注入。

**前沿进展**：PwC 的 **Graph RAG-Tool Fusion**（[arXiv 2502.07223](https://ar5iv.labs.arxiv.org/html/2502.07223)）指出现有 Tool RAG 只做语义相似度、**忽略了工具之间的依赖结构**（"查股价"依赖"查股票代码"，两者又都依赖系统级工具）。它把工具建成知识图（节点=工具，边=工具依赖/参数依赖），检索时先向量召回 top-k，再沿依赖边 DFS 扩展。

在它构造的 **ToolLinkOS**（573 个工具、平均每工具 6.3 个依赖）上，mAP@10：

| 方法 | mAP@10 |
|---|---|
| 词法检索（BM25） | 0.185 |
| 朴素向量 RAG | 0.210 |
| 混合 RAG | 0.202 |
| Graph RAG-Tool Fusion | 0.856 |
| **Graph RAG-Tool Fusion + 重排** | **0.927** |

绝对提升 71.7 个百分点。这个数字的意义不是"要用它"，而是**说明工具规模上去之后，检索层的质量差异是数量级的**。

**对本项目的判断**：24 个工具不需要 Tool RAG，全量枚举反而更稳（检索会引入召回失败这一新的错误源）。这是一个**规模触发的设计**，触发阈值建议定在工具数 > 50。

### 3.5 训练层：数据合成与偏好对齐

这两条对本项目不直接可用（用第三方模型），但结论可以借用。

**ToolACE**（[arXiv 2409.00920](https://arxiv.org/abs/2409.00920)，ICLR 2025）解决的是"真实工具调用数据稀缺"：用自演化的方式合成 API，再用**双层验证**（规则 + 模型）保证合成数据正确，并按难度分级采样。

**Relign** 的做法更贴近本题：它观察到工具幻觉的根因是**模型没有正确建模"何时该做决策"**——当"参数不全""工具不匹配"这类前提不满足时，从"决定性动作空间"（全都是"调工具"）里选任何动作都必然错。

于是它**扩展了动作空间**，加入两个弃权动作：

- `ChangeTools`：换一个工具
- `TalkToUser`：问用户 / 说明情况

然后用 SFT 教会模型使用弃权动作，再用 DPO 按 `正确动作 > 弃权动作 > 幻觉动作` 的偏好层级优化。

**效果**（RelyToolBench，Overall 列）：ToolLLaMA-7B 的工具幻觉率从 **56.5% 降到 18.3%**；对照的 GPT-4o 是 8.3%，GPT-4o-mini 17.9%。

**可借用的核心洞见**：模型"弃权"应该比"编造"更被鼓励。这条不需要训练就能落地——直接翻译成 prompt 许可（3.2）+ 熔断策略（第 6 节）。

## 4. 防线二：拦截

### 4.1 白名单：本项目已有，且比看上去更值钱

`tools_route.py` 顶部注释记录了从"扫描文件注册所有函数"到"以 schema 为准"的演进。这个改动顺带带来了两个安全属性，值得明确写下来，避免后来者为了方便把它放宽：

1. **注册表恒等于 schema**——模型面对的候选集和实际能执行的集合不会漂移。
2. **`_belongs_to_hub` 只认工具层内部的函数**——模型幻觉出的名字即使**恰好撞上某个辅助函数**（`_render_payload`、`build_evidence_payload`、`prewarm`…），也进不了注册表，照样是"未知工具"。

第 2 点是**意外但对的安全属性**。如果未来有人为了"少写一个 schema 项"而放宽它，就等于把一堆非工具函数暴露成了可调用入口。

### 4.2 名称归一化：被低估的一层

模型输出的名字经常不是"编造"，而是**同一个名字的不同写法**。这类"近失"（near-miss）在所有幻觉里占比很高，而且**最不该失败**——它完全可以通过归一化救回来。

BFCL 的评测代码里就有一层同类处理：函数名里可能含 `.`，而 OpenAI 系列不接受点号，所以推理和评测时都把 `.` 替换成 `_`。这说明"名字的书写形式"在工程上本来就需要归一化。

**工业实现的归一化阶梯**（来自 NousResearch/hermes-agent 的 [PR #701](https://github.com/NousResearch/hermes-agent/pull/701)）：

```python
def _repair_tool_call(self, tool_name: str) -> str | None:
    """1. Try lowercase  2. Try normalized (lowercase + hyphens/spaces -> underscores)
       3. Try fuzzy match (difflib, cutoff=0.7)"""
    from difflib import get_close_matches

    lowered = tool_name.lower()
    if lowered in self.valid_tool_names:
        return lowered

    normalized = lowered.replace("-", "_").replace(" ", "_")
    if normalized in self.valid_tool_names:
        return normalized

    matches = get_close_matches(lowered, self.valid_tool_names, n=1, cutoff=0.7)
    return matches[0] if matches else None
```

对 Python 侧的 agent，我建议再加两条这类实现容易漏掉的：

4. **驼峰转下划线**：`getAssets` → `get_assets`（Python 名字是 snake_case，模型从其他生态迁移过来时会用驼峰）
5. **剥掉命名空间前缀**：`functions.get_assets` / `tools.get_assets` → `get_assets`

### 4.3 模糊匹配的阈值必须分两档 ⚠️

这是整个方案里**最容易踩坑的一处**。

模糊匹配有两个完全不同的用途，阈值和适用范围都不一样：

| 用途 | 行为 | 阈值 | 适用范围 |
|---|---|---|---|
| **自动修复** | 直接把名字改掉然后执行 | 高（≥0.85） | **只对只读工具开放** |
| **候选建议** | 回灌 `did_you_mean`，让模型自己选 | 低（~0.5） | 全部工具 |

**为什么写工具不能自动修复**：把 A 猜成 B 会**静默执行错误的工具**。

- `get_asset` → `get_assets`：无害，反正只读。
- `update_asset` → `update_debt`：这是事故。用户想改资产，系统改了负债，而且**调用成功、没有报错**。

按本项目的命名规范，只读/写入可以靠前缀区分，很干净：

```python
_READ_ONLY_PREFIXES = ("get_", "calculate_", "search_", "list_")
```

相应地，`record_` / `update_` / `delete_` / `create_` / `set_` / `complete_` 开头的 12 个工具应排除在自动修复之外，只给建议。

这个设计的取舍要说清楚：**这不是保守，是承认"错误执行"的代价高于"多问一轮"**。Relign 的 Utility 公式（第 7 节）也是这个思路——幻觉有独立负分，不能靠"多试几次"摊掉。

### 4.4 别名表：确定性的补充

模糊匹配是启发式，别名表是确定性的：`search_policy` → `search_knowledge`、`query_assets` → `get_assets`。把线上真实出现过的错名沉淀成显式映射，比模糊匹配准确得多，而且**可审计**。

代价是需要维护。所以别名表必须配 7.3 的埋点：只有先知道线上到底出现了哪些错名，别名表才不会变成拍脑袋的产物。

### 4.5 参数校验：不要用 Python 的报错当错误信息

现在缺必填参数时，模型收到的是 `get_assets() missing 1 required positional argument: 'x'`。有三个问题：

1. **泄露实现细节**（Python 措辞、内部函数签名）；
2. **不含"该怎么改"**——没说可用参数有哪些；
3. **模型可能照抄**这个措辞去回复用户。

而 schema 里现成就有 `required` 和 `properties`，直接校验即可：

```python
{"error": "缺少必填参数: query",
 "missing_arguments": ["query"],
 "required_arguments": ["query"],
 "retryable": true}
```

对**幻觉参数**（不在 `properties` 里的键）建议也拦下来。理由：BFCL 的评测逻辑里，"只允许使用函数文档中声明的参数"是判定幻觉的硬性依据（[BFCL blog](https://gorilla.cs.berkeley.edu/blogs/8_berkeley_function_calling_leaderboard.html) 的 "Required Parameters Matching" 一节明确写了 "ensures that only parameters exist in the function doc are used, **flagging the model hallucination outputs**"）。在评测层算幻觉的东西，在运行时也不该放过。

不过这条有个取舍：拦下来会多花一轮，放过去（把多余参数丢掉）能省一轮。建议**拦下来但只在 `additionalProperties` 未显式允许时**，并且错误信息里列出可用参数——因为"模型编了个参数名"通常意味着它对工具的理解有偏差，早点纠正比让它带着错误理解继续往下走好。

## 5. 防线三：修复

### 5.1 错误载荷的三要素

一个"未知工具"错误值多少钱，取决于它包含几个要素：

| 要素 | 作用 | 缺了会怎样 |
|---|---|---|
| **错的是什么** | 模型确认自己写了什么 | — |
| **有哪些能用** | 把候选集重新呈现在模型眼前 | 模型只能凭上下文猜，命中率取决于随机性 |
| **怎么改** | `did_you_mean` + 明确指令 | 模型可能换个同样错的名字再试 |

BFCL 的 "relevance detection" 分类就是这个逻辑的反面验证：它在 240 个用例里**不提供任何相关工具**，期望模型输出"不调用函数"。这类用例存在的意义正是测量"模型在没有可用工具时会不会硬编一个"。

### 5.2 两个工业实现，同一方向

**① OpenAI Agents SDK**（[PR #3402](https://github.com/openai/openai-agents-python/pull/3402)）

新增了一个 agent 级配置：

```python
unknown_tool_behavior: Literal["raise", "respond"] = "raise"
```

- 默认 `"raise"`：抛 `ModelBehaviorError`。文档写明了理由——**开发期崩得早最安全**。
- 设为 `"respond"`：追加一条合成的 tool output，内容是

  ```
  Tool 'does_not_exist' is not available on agent 'test'. Available tools: known.
  ```

  然后继续跑，让模型下一轮自己恢复。

它的实现细节值得注意：即使工具名无效，也仍然**先记录 `ToolCallItem` 再追加 `ToolCallOutput`**，保证对话历史的结构完整——否则下一轮请求会因为"tool_calls 里的 id 没有对应的 tool 消息"而被 API 拒绝。

**② hermes-agent**（[PR #701](https://github.com/NousResearch/hermes-agent/pull/701)）

这个 PR 更有意思，因为它**推翻了一个旧实现**。改动前：

```python
if invalid_tool_calls:
    self._invalid_tool_retries += 1
    if self._invalid_tool_retries < 3:
        # Don't add anything to messages, just retry the API call
        continue
```

改动后：

```python
# Return helpful error to model — model can self-correct next turn
available = ", ".join(sorted(self.valid_tool_names))
messages.append({
    "role": "tool",
    "tool_call_id": tc.id,
    "content": f"Tool '{tc.function.name}' does not exist. Available tools: {available}"
})
```

**这是"重试"与"修复"的分界线**：盲重试等于让模型在没有新信息的情况下重新采样，能不能中取决于随机性；把错误和可用清单喂回去，模型是在有信息的情况下重新决策。这个教训比任何模糊匹配算法都重要。

### 5.3 错误分级：本项目缺的一层

现在所有失败都汇成同一个 `{"error": str(e)}`。模型拿到它无法区分两类完全不同的情况：

| 类型 | 例子 | 正确反应 |
|---|---|---|
| **可重试**（retryable） | 参数名写错、名字近失、缺必填 | 改一下立刻重试 |
| **不可重试**（fatal） | RAG 依赖缺失、数据库不可用、工具内部 bug | 重试无用，应当**改口**告诉用户 |

不分级的后果很具体：模型对确定性故障反复重试，直到烧光 `MAX_ROUNDS`，最后报一句"达到最大循环次数"——**用户和日志都看不出真实原因**。

建议在错误载荷里加 `"retryable": true/false`，并在 `retryable: false` 时附一句提示：

```json
{"error": "RAG 引擎不可用", "error_kind": "tool_exception",
 "retryable": false,
 "hint": "该错误大概率不可通过重试解决，请改用其他方式回答或告知用户。"}
```

> 已知局限：`route()` 里的裸 `except Exception` 无法真正区分"工具 bug"和"临时故障"。要做到准确分级，需要工具侧抛出专门的异常类型（如 `RetryableToolError` / `FatalToolError`），`route()` 据此分类。这是 Phase 2 之后可以继续深入的方向。

### 5.4 重试预算与去重

三层预算，成本递增：

1. **全局轮次上限**（本项目 `MAX_ROUNDS = 5`）——兜底，但粒度太粗。
2. **同名工具连续失败计数**——建议 2 次即收。同一个名字错两次，说明模型没理解错误信息，再试大概率还是错。
3. **同参调用去重**——完全相同的 `(name, arguments)` 第二次出现，直接判定为**时机幻觉**，不再执行。

第 3 条顺带补上了 1.1 表里"完全没兜"的那一类。Relign 对时机幻觉的定义就是"用相同输入重复调用同一工具"，所以这个检测器同时也是一段轻量的幻觉监控。

去重时要注意：**仍然要回填 `role: "tool"` 消息**，否则 `tool_calls` 和 `tool` 消息数量对不上，下一轮请求会被 API 拒绝（同 5.2 里 OpenAI SDK 的处理）。

## 6. 防线四：收敛

### 6.1 熔断必须归因

熔断本身简单，难的是**熔断后说什么**。

现在本项目跑满轮次时报 `达到最大循环次数（5），已中止`。这句话对用户没有意义，对排查也没有意义——真正的原因可能是"工具名一直无效"、"参数一直错"、"模型在打转"。

改进方向：**记录最后一次失败的 `error_kind`，熔断时把它带出来**。例如"连续 2 次调用了不存在的工具，已停止"。

### 6.2 弃权动作：Relign 的核心洞见

第 3.5 节提过，Relign 的出发点是"当决策前提不满足时，决定性动作空间里全是错答案"。它给的两个弃权动作翻译到运行时就是：

| 弃权动作 | 运行时含义 | 本项目对应 |
|---|---|---|
| `ChangeTools` | 换个工具；如果一个都不合适，说明情况 | 错误载荷里的 `available_tools` + `did_you_mean` |
| `TalkToUser` | 问用户要缺失的信息 | 熔断时的降级文案 + prompt 里的弃权许可 |

**最重要的落地结论**：熔断之后应该**给用户一句人话**，而不是只丢一个 `error` 事件。用户需要知道"哪一步出了问题""接下来能做什么"。

### 6.3 写操作的额外风险

读工具错一次只浪费一轮；**写工具错一次已经落库**。所以：

- 写工具默认**关闭自动修复**（见 4.3）
- 写工具的参数校验更严（尤其 `required`）
- 写工具失败后**不要自动换一个写工具重试**——"记资产失败所以记成负债"这种连锁错误比单纯失败糟糕得多

## 7. 度量：怎么证明兜底真的有效

### 7.1 基础指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 未知工具率 | 未知工具调用数 / 总工具调用数 | 幻觉基线 |
| **自愈率** | 首次失败后下一轮成功 / 首次失败次数 | **兜底是否真的有用** |
| 平均轮次 | 完成任务的平均轮数 | 兜底的成本 |
| 用户可见错误率 | 最终以 error 收尾的会话占比 | 兜底的上限 |

其中最该盯的是**自愈率**——它直接衡量"错误回灌"这条路径的转化效果。如果自愈率很低，说明错误信息的信息量不够（回到 5.1）。

### 7.2 复合指标（借用 Relign）

- `RePR = Pass Rate − Task Hallucination Rate`：扣掉"靠幻觉侥幸成功"的任务。它揭示的问题很尖锐：**只看成功率会系统性高估系统可靠性**。
- `Utility = R_task − P_tool − P_hallucination`：成功 +20，多余的调用按次扣分（上限 10），幻觉 −10。

`Utility` 的构造思路值得直接借鉴到内部评测：它把"多试几次总能成"变成有代价的行为，正好对应第 5.4 节的重试预算。

### 7.3 埋点方案

在 `route()` 里打一条结构化日志即可，字段建议：

```text
[tools_route] tool=<原始名> resolved=<真名> how=<exact|normalized|fuzzy|none>
              status=<success|error> error_kind=<unknown_tool|bad_json|missing_arg|
              unknown_arg|tool_exception> round=<轮次>
```

有了它，三个问题都能回答：哪些错名最高频（→ 回填别名表）、自愈率多少（→ 判断错误信息够不够）、有多少是确定性失败被重试（→ 发现工具 bug）。

### 7.4 离线回归集

固定一组"必然幻觉"的用例进 CI，覆盖：

- 完全编造的名字
- 四种近失写法（大小写、驼峰、连字符、命名空间前缀）
- 缺必填参数
- 幻觉参数
- 非对象 JSON（`[1,2]`、`null`、`"str"`）
- 同名同参重复调用
- 写工具的近失名（验证**不会**被自动修复）

最后一条是**反向测试**，比正向测试更重要——它守住的是"不要把 `update_asset` 修成 `update_debt`"这条底线。

## 9. 反模式与风险

按危害排序：

1. **⚠️ 模糊匹配不看工具类型就自动执行** —— 最危险的一条。静默执行错误的写操作，比报错糟糕一个数量级。必读 4.3。
2. **盲重试**（不喂错误信息直接重发请求）—— 浪费成本且命中率取决于随机性。hermes-agent 的 PR 就是为了改掉它。
3. **无上限重试** —— 单轮成本 × 轮次，且会掩盖"这条路根本走不通"。
4. **错误信息暴露 Python 内部细节** —— `missing 1 required positional argument` 既泄露实现，模型还可能照抄给用户。
5. **把确定性 bug 当模型问题重试** —— `route()` 的裸 `except Exception` 有这个副作用：真正的代码缺陷会被包装成"工具出错"，然后被重试掩盖。建议加 `error_kind` 分类并监控分布。
6. **别名表只加不删** —— 工具改名后旧别名会变成"静默调用已废弃工具"的入口。别名表要有清理机制。
7. **只兜"名字不存在"** —— 漏掉时机幻觉（重复调用）和内容幻觉（参数编造）。这是本项目当前的实际状态。
8. **开发期就开 `respond`** —— 会掩盖 schema 与实现的错配。OpenAI SDK 默认 `raise` 是有道理的：**开发期崩得早，生产期才能稳**。
