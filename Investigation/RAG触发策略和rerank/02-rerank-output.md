# 02 · Rerank 输出策略：排序、截断与证据组织

> 对应问题：**rerank 出来的结果怎么定序、怎么截断、怎么组装成给 LLM 的证据块？**

现有在线链路（`backend/RAG_/src/wealth_rag/retrieval/hybrid.py`）最后四步是：

```
rerank 打分 → _fuse 融合排序 → _dedupe_by_parent 去重 → [:final_k] 截断 → _fill_parent_text 回查父块
```

这四步里有 **1 个排序语义问题、1 个截断顺序 bug、1 个输出格式缺口**。逐个说。

---

## 1. 最终排序应该以 rerank 分为准（不是加权混合）

### 1.1 现状

`_fuse()` 在「重排可信」这一档做的是：

```python
max_rrf = max(x.score for x in results)          # RRF 分的最大值（也就是第 1 名的 RRF 分）
max_rerank = max(x.rerank_score ...)
if max_rerank >= r.rerank_floor:                 # 0.25
    w = r.rerank_weight                          # 0.6
    for x in results:
        x.score = (1 - w) * (x.score / max_rrf) + w * (x.rerank_score or 0.0)
```

即：**RRF 分按自身最大值归一化到 [0,1]，然后与 rerank 分（本身就是 0~1 概率）按 0.4 : 0.6 加权求和**，写回 `x.score`，再按它排序。

### 1.2 问题

| 问题 | 说明 |
| --- | --- |
| **量纲差异被掩盖，但没有被消除** | RRF 分是 `1/(k+rank)` 型倒数排名分，其**分布形状与 rerank 概率完全不同**。按最大值归一化只对齐了上界，中段分布依然畸变。 |
| **归一化基准不稳定** | `max_rrf` 取的是本次结果集里的最大值。不同的查询、不同的候选集 → 同一份文档的 `score/max_rrf` 会变。这意味着**同一个 (query, doc) 对在两次调用里可能得到不同的最终分**，无法跨轮比较，也无法设一个稳定的「够不够好」阈值。 |
| **权重 0.6 没有依据** | 这个权重是拍出来的，且没有评估集验证。 |
| **覆盖了原始 RRF 分** | `x.score` 被就地改写，**原始 RRF 分丢失**，事后无法复盘「这一条是靠关键词命中进来的还是靠语义进来的」。 |

### 1.3 候选方案对比

| 方案 | 做法 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **A · 纯 rerank 定序** | 最终排序 = `rerank_score` 降序；`score` 保留为 RRF 原始分，另存 | 语义清晰（排序只由最可信的信号决定）；跨查询可比；无需调参 | 完全丢弃召回阶段的多样性信号 | ✅ **首版推荐** |
| **B · 加权融合（现状改进版）** | 保留加权，但两路都做 min-max 或 rank-based 归一化，权重写进配置 | 保留两路信息 | 仍需调参；归一化基准问题依旧（除非用固定基准或 rank 归一） | ⚠️ 仅在有评估集证明增益时启用 |
| **C · RRF 到 rerank 的级联** | 用 RRF 只做「选谁进 rerank」（现状的 `fused_top=20`），rerank 只做「怎么排序」 | 职责彻底分离；每个阶段只做自己擅长的事；**这正是典型 two-stage retrieval 的标准形态** | — | ✅ **首版推荐（与 A 等价）** |
| **D · 分数校准后融合** | 用历史数据拟合 rerank 分 → 相关性概率的映射，再融合 | 理论上最优 | 需要标注数据 + 持续维护 | ❌ 本阶段不做 |

**推荐 A/C**。理由：**RRF 的职责是「召回并粗排」，rerank 的职责是「精排」——两级排序的分工本来就不该通过加权求和混在一起**。加权融合的动机是「怕 rerank 不稳」，但这个需求已经由 `rerank_floor` 三档判定覆盖了（rerank 不可信时整档退回 RRF）。两套机制做同一件事，只会互相干扰。

**保留 `rerank_weight` 配置项但默认改为 1.0**（等价于纯 rerank），这样想回退成融合只需改配置，不用改代码。

### 1.4 建议的数据结构改动

```python
@dataclass
class SearchResult:
    score: float              # 保留：召回阶段原始分（RRF）
    rerank_score: float | None
    final_score: float | None  # 新增：最终排序分（= rerank_score，或 rerank 不可信时 = score）
    evidence_quality: str     # 新增：'high' | 'medium' | 'low'（见第 5 节）
```

> 现状 `score` 承担了两个语义（「召回分」和「最终分」），是排序语义混乱的根源。拆开之后，`score` 归召回、`final_score` 归排序，`low_confidence` 可以退化成 `evidence_quality == 'low'` 的兼容别名。

## 2. 去重必须先于截断（现有代码顺序反了）

### 2.1 现状

```python
if r.dedupe_by_parent:
    results = self._dedupe_by_parent(results, final_k)   # 内部：命中即 break，最多 final_k 条
else:
    results = results[:final_k]
```

`_dedupe_by_parent(results, final_k)` 的实现是「遍历 → 去重 → 收集到 `final_k` 条就停」。

由于 `results` 进来时已经是按分数降序的**完整 `fused_top` 候选池（默认 20 条）**，这个顺序实际上是对的：它在整个池子里去重并收集到 8 条为止。**所以严格来说这里不是 bug —— 但它的行为容易被误读，而且存在一个真实的边界损失**：

> 如果前 8 个候选全部来自同一节（同一个 `parent_id`），去重后只剩 1 条，而循环会在「收集满 8 条」时提前退出——此时它已经遍历完了整个 20 条池子吗？不是：它只在 `len(out) >= final_k` 时才 break，所以**它会继续遍历整个池子直到收满**。这条逻辑是**正确**的。

**澄清结论：去重逻辑本身没有 bug。** 但有两个真实问题：

| 真实问题 | 说明 | 建议 |
| --- | --- | --- |
| **去重可能填不满 `final_k`** | 如果候选池里就只有 3 个不同的节，最终只返回 3 条，且**上层无法区分「只有 3 条相关」和「本来能返回 8 条但被去重砍掉了」** | 返回值里带上 `candidates_considered` / `dedup_dropped` 两个计数，供上层和评估使用 |
| **去重键的语义不一致** | `key = res.parent_id or " > ".join(res.heading_path) or res.chunk_id` —— 前两者是**节级**，第三个是**块级**。当父块缺失时，去重粒度悄悄从「节」变成「块」，同一节的两个子块都会被保留 | 统一为「节」级：无 `parent_id` 时用 `heading_path`；再没有就用 `doc_id + page`，而不是 `chunk_id` |

### 2.2 截断的推荐顺序

```
1. 按 final_score 降序（= rerank 分）
2. 按「节」去重（保证证据覆盖面）
3. 应用上下文预算（token 上限，见第 4 节）—— 超预算时从尾部丢弃，并**只丢整节**
4. 截断到 final_k
```

**「只丢整节」这个约束很重要**：如果预算只够放进某一节的 2 个子块中的 1 个，那这一节的上下文是残缺的，反而更容易让模型误读。要么整节进，要么整节不进。

## 3. 排序里的「位置偏置」问题（Lost in the Middle）

这是**本项目当前完全没处理**的一个已知失效模式。

[Liu et al., 2023（Lost in the Middle）](https://arxiv.org/abs/2307.03172) 的结论：把关键信息放在长上下文的**中间**位置时，模型准确率显著低于放在开头或结尾——形成一个 U 形曲线（开头 ~85%、中间 ~52%、结尾 ~82%）。而且**上下文越长、文档越多，问题越严重**；更长的上下文窗口并不能消除它。

对本项目的直接含义：

| 场景 | 后果 |
| --- | --- |
| `final_top=8`，每条证据 200~500 token | 上下文 1.6K~4K token 起（还没算 `parent_text`），中间 3~5 条证据处于注意力低谷 |
| 最相关的那条被排在第 1 位 | ✅ 没事 |
| 第 2、3 条也相关，但被夹在中间 | ⚠️ 可能被忽略，模型只用第 1 条作答 |
| 命中的子块 + 展开的父块全文 | 父块动辄上千 token，**极易把真正相关的子块挤到中间** |

### 3.1 缓解手段（按投入产出比排序）

| 手段 | 做法 | 评价 |
| --- | --- | --- |
| **① 减少条数** | `final_top` 从 8 降到 **3~5** | 最有效、最简单。调研材料的明确建议是「用 3-5 条高度相关的，而不是 20 条杂的」 |
| **② 明文标注重要性** | 每条证据前加 `【证据 1 · 相关度最高】` / `【证据 2】`…，用编号 + 标签显式提示 | 低成本、与「结构化上下文带标签」的建议一致 |
| **③ 首尾放置** | 把最相关的放第 1 位，次相关的放**最后**一位 | 简单；但会破坏「按相关度单调排列」的可读性 |
| **④ 上下文预算硬上限** | 给证据上下文设 token 上限（如 2000），超了从尾部丢 | 直接抑制「上下文越长越糟」 |
| **⑤ Map-Reduce** | 每条证据单独问一次模型再汇总 | ❌ 成本 N 倍，本项目不划算 |

**推荐组合：① + ② + ④，暂不做 ③。**
理由：③（首尾放置）在 `final_top` 已经降到 3~5 之后收益很小，却让证据编号与相关度顺序不一致，反而给模型和调试都添乱。**先靠「少而精」压住总量，是性价比最高的做法。**

## 4. 上下文预算：`parent_text` 是最大的体积风险

### 4.1 现状

`_fill_parent_text()` 在最终截断**之后**回查父块全文，挂到 `res.parent_text`。这部分体积**完全不受 `final_top` 控制**：

- 子块上限是 512 token（`chunking.max_tokens`）；
- 父块是**整节全文**，理论上没有上限 —— 一个长节可能几千 token；
- 8 条证据 × （子块 512 + 父块 3000）≈ **28K token**，一次工具调用就能把上下文打爆。

### 4.2 建议

| 建议 | 说明 |
| --- | --- |
| **给工具加 `context_budget_tokens`（默认 2000）** | 预算内优先放子块 `raw_text`；剩余预算才用于父块扩展 |
| **父块按需给，不默认全给** | 工具加 `include_parent` 布尔参数（默认 `false`）。模型需要更大上下文时会自己再要一次——这比默默塞 28K token 好 |
| **父块扩展按预算截断** | 若给父块，也只给「子块所在位置附近的前后 N 个字符」，而不是整节。**但要注意：截断父块需要知道子块在父块里的偏移**——当前 payload 里没有这个信息，需要摄入侧补 `parent_offset` 字段（或退化为「父块前 1500 字符」这种粗糙做法） |
| **子块 `raw_text` 已含前置叶子标题** | 不需要再拼一遍 `heading_path`，否则标题重复两遍浪费 token |

> ⚠️ **不要直接把 `Retriever.search()` 的返回值 `json.dumps` 丢给 LLM。** 那个 `SearchResult` 里有 `text`（含面包屑前缀，与 `raw_text` 内容重叠）、`raw_text`、`parent_text`、`heading_path`、`source_path`（本地绝对路径，对用户无意义且可能泄露目录结构）、`parent_id`、`chunk_id`（UUID，对 LLM 无信息量）。**必须经过一层瘦身适配。**

## 5. 证据质量信号怎么传给上层

现有唯一的信号是 `low_confidence: bool`，由「最高重排分 < 0.05」触发。问题：

1. **它是个绝对值阈值，未校准** —— 0.05 这个值在不同语料/模型上含义不同，很可能把「泛查询下重排普遍给低分」误判成「库里没证据」（代码注释自己也承认这档存在）；
2. **它是有损的二值化** —— 丢掉了「重排器不确定但也不否定」（0.05 ≤ max < 0.25 那一档）的信息；
3. **它没有规定上层动作** —— 标记了但不知道该干什么。

### 5.1 建议改为三值 `evidence_quality`

| 取值 | 触发条件 | 语义 | 上层动作 |
| --- | --- | --- | --- |
| `high` | `max_rerank >= rerank_floor`(0.25) | 重排器确认有高度相关证据 | 正常作答，**必须带引用** |
| `medium` | `no_answer_threshold`(0.05) ≤ `max_rerank` < `rerank_floor` | 重排器不确定；排序已退回关键词路 | 可以作答，但**必须声明证据强度有限**；建议提示用户补充信息 |
| `low` | `max_rerank < no_answer_threshold`(0.05) | 重排器判定全都不相关 | **拒答**：明确说知识库中没有找到依据，并建议求助渠道；**禁止凭记忆编造** |

配套：把 `max_rerank`（最高重排分）**原样透出**给上层（字段名如 `top_rerank_score`）。有了原始分数，上层可以自己定策略，而不必被写死的布尔值绑住。

> 调研依据：CRAG 的消融实验证明「中档软策略」不能删（[CRAG §4.3 与 Table 2](https://ar5iv.labs.arxiv.org/html/2401.15884)）；同时 CRAG 的实测表明**轻量专用评估器（T5 84.3%）远优于大模型零样本判断（ChatGPT 58.0%）**，所以这里应该信任 rerank 分数，而不是让主 LLM 自己判断「检索结果靠不靠谱」。

## 6. 给 LLM 的证据块格式（推荐）

### 6.1 工具返回的 JSON 结构

```json
{
  "evidence_quality": "high",
  "top_rerank_score": 0.8921,
  "query_used": "个人养老金 缴费上限",
  "result_count": 3,
  "results": [
    {
      "index": 1,
      "citation": "金融知识普及读本（第二版） | 第 42 页 | 第三章 养老金融 > 个人养老金制度",
      "text": "个人养老金实行个人账户制，参加人每年缴纳个人养老金的上限为 12000 元……",
      "chunk_type": "text",
      "parent_text": null
    },
    {
      "index": 2,
      "citation": "个人养老金实施办法 | 第 3 页 | 第二章 参加范围",
      "text": "……",
      "chunk_type": "text",
      "parent_text": null
    }
  ],
  "notice": null
}
```

拒答时：

```json
{
  "evidence_quality": "low",
  "top_rerank_score": 0.008,
  "result_count": 0,
  "results": [],
  "notice": "知识库中未检索到与该问题相关的可靠证据。请勿凭记忆作答；应告知用户未找到依据，并建议其咨询专业机构或提供更多信息以便重新检索。"
}
```

### 6.2 字段设计要点

| 字段 | 为什么这样设计 |
| --- | --- |
| `index` | **编号是引用机制的锚点**。SYSTEM_PROMPT 里规定「用 `[1]` `[2]` 标注每句结论的来源」，编号必须由后端给，不能让模型自己数 |
| `citation` | 直接用现有 `SearchResult.citation` 属性（`文档 | 页码 | 标题路径`），已经是可读格式 |
| **不含** `score` / `rerank_score` | **不要把内部分数暴露给 LLM**：模型会拿分数当「可信度」在正文里复述（「该证据相关度 0.89」），对用户毫无意义，还会污染输出风格。分数只给前端/日志 |
| **不含** `source_path` | 本地绝对路径（如 `E:\...\data\19-080249-金融知识普及读本.pdf`）对用户无意义，且泄露目录结构 |
| **不含** `chunk_id` / `parent_id` | UUID 对 LLM 零信息量，纯浪费 token |
| **不含** `text`（含面包屑的嵌入文本） | `raw_text` 已经前置了叶子标题，`text` 的面包屑前缀（`文档标题 > 章 > 节`）与 `citation` 重复 |
| `notice` | 把「该不该拒答」的指令**放在数据里**，比放在 SYSTEM_PROMPT 里更贴近使用点，模型遵循度更高 |
| `query_used` | 回显实际检索用的查询串。**这对调试追问改写极其重要**——能一眼看出模型有没有正确补全指代 |

### 6.3 SYSTEM_PROMPT 需要补的规则

```
关于知识库证据：
* 当你调用了 search_knowledge，回答必须基于返回的证据，不得凭记忆补充证据中没有的
  政策数额、法规条款或产品信息。
* 每一处来自证据的结论都要标注来源编号，如「根据 [1]」。
* 若 evidence_quality 为 "low" 或 results 为空，必须如实告知用户「知识库中未找到
  相关依据」，并建议其咨询专业机构或补充信息；禁止编造。
* 若 evidence_quality 为 "medium"，可以作答，但要说明「以下是基于有限资料的说明」。
* 不要把证据的编号、相关度分数或内部字段当作内容复述给用户。
```

### 6.4 证据在消息里的放置位置

工具消息（`role: "tool"`）→ 放在 `messages` 里由 Agent 循环自动回填（现有 `agent.py:117-121` 已经这么做）。

**不需要**把证据再复制进 system prompt 或拼进 user message —— 那会造成同一份证据出现两次，既浪费 token 又可能让模型混淆「哪些是用户说的、哪些是资料说的」。

## 7. 小结

| 环节 | 现状 | 建议 |
| --- | --- | --- |
| **最终排序** | RRF 归一化分与 rerank 分加权（w=0.6） | **改为纯 rerank 定序**；RRF 分保留为召回元数据；`rerank_weight` 默认 1.0 |
| **去重** | 按 parent/heading 去重，逻辑正确但去重键粒度不一致 | 去重键统一到「节」级；返回 `candidates_considered` / `dedup_dropped` 计数 |
| **截断** | 截断到 `final_top`(8) | 降到 **3~5**；按「整节」粒度丢弃，不切碎 |
| **位置偏置** | 未处理 | 靠「少而精」+ 明文编号标签 + 上下文预算上限压制；暂不做首尾重排 |
| **上下文预算** | 无上限，`parent_text` 可无界膨胀 | 加 `context_budget_tokens`(默认 2000) + `include_parent`(默认 false) |
| **质量信号** | 二值 `low_confidence` | 三值 `evidence_quality`(high/medium/low) + 透出 `top_rerank_score` |
| **给 LLM 的格式** | `SearchResult` 直接序列化（含 UUID/绝对路径/重复文本/内部分数） | 瘦身适配层：编号 + citation + 正文 + notice，去掉内部字段 |
| **拒答** | 只有标记，无动作定义 | `low` → 强制拒答话术；`medium` → 降级声明；`high` → 必须引用 |
