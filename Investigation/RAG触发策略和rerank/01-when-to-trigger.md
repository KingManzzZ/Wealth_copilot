# 01 · 触发策略：什么时候该去查知识库

> 对应问题：**RAG 什么时候触发？谁来决定？决策错了怎么办？**

---

## 1. 问题定义

「触发」包含三层，必须分开讨论，否则很容易把它们混成一个「要不要 RAG」的粗粒度开关：

| 层次 | 决策内容 | 时机 |
| --- | --- | --- |
| **L1 · 是否检索** | 这一轮回答需不需要外部知识？纯寒暄、纯算术、纯用户数据查询就不需要 | 生成答案之前 |
| **L2 · 检索什么** | 查询串怎么写？（多轮追问要补全指代；宽泛问题要拆解或抽象） | 检索之前 |
| **L3 · 检索够不够** | 拿到的证据能不能支撑回答？不足以支撑时是**重试**、**换查询**、还是**拒答**？ | 检索之后、生成之前 |

现有 RAG 模块只实现了 L2 的一个最简版本（原样把 query 送进去），完全没有 L1 和 L3 —— L1 是本次融合要新增的能力，L3 目前只有 `low_confidence` 这一个弱信号。

---

## 2. 学术界的四条主流路线

### 2.1 Self-RAG —— 让模型自己生成「要不要检索」的反思标记

[Self-RAG](https://arxiv.org/abs/2310.11511)（Asai et al., 2023）的核心论点是：**「不管需不需要都固定检索固定条数」会损害模型的多功能性**。做法是训练 LM 生成一组 *reflection token*，其中 `[Retrieve]` 决定是否触发检索，`[IsRel]` / `[IsSup]` / `[IsUse]` 分别评判「检索到的段落相关吗 / 回答有依据吗 / 回答有用吗」。

- **对本项目的意义**：它把「是否检索」建模成模型输出的一部分，而不是外挂一个分类器。**这与当前 ReAct 架构（模型通过 function calling 决定调哪个工具）在形态上是同构的** —— 区别只在于它是训练出来的专用 token，我们是通用模型 + 工具描述引导。
- **不可直接照搬的原因**：需要微调（论文用 LLaMA2-7B/13B 在 GPT-4 标注数据上训练），本项目走 API 大模型，没有微调路径。

### 2.2 Adaptive-RAG —— 用查询复杂度分类器在「不检索 / 单步检索 / 迭代检索」之间选

[Adaptive-RAG](https://aclanthology.org/2024.naacl-long.389/)（Jeong et al., NAACL 2024）观察到：*并非所有用户请求都落在「简单」或「复杂」两端*。它训练一个**小 LM 分类器**预测查询复杂度，据此选最简策略：

```
简单查询  → 不检索，直接答（省掉无谓开销）
中等查询  → 单步检索
复杂查询  → 迭代/多跳检索
```

- **关键设计**：分类器的标签不是人工标的，而是**从「各策略实际预测结果」里自动收集**出来的（哪个策略答对了，就用哪个策略当标签）。这个思路很实用 —— 本项目后续若要加分类器，训练数据可以从「Agent 日志里模型自己选了什么工具、结果好不好」自动回收。
- **对本项目的意义**：给出了「三档路由」而非二值开关的范式，与本项目的三档需求（不检索 / 单次检索 / 多轮检索）吻合。

### 2.3 CRAG —— 检索**之后**才决策，用置信度触发三种纠错动作

[Corrective RAG](https://ar5iv.labs.arxiv.org/html/2401.15884)（Yan et al., 2024）不决定「要不要检索」，而是决定「检索完发现是垃圾怎么办」。它用一个轻量检索评估器（T5-large，0.77B）给每个 (query, doc) 对打相关性分，然后三档触发：

| 置信度 | 触发动作 | 做法 |
| --- | --- | --- |
| `CORRECT` | **至少一个**文档分 > 上阈值 | 保留，并做 decompose-then-recompose 知识精炼（拆成句子级 strip，过滤掉无关 strip，再按序重组） |
| `INCORRECT` | **全部**文档分 < 下阈值 | 丢弃全部，改写查询走外部检索（web search） |
| `AMBIGUOUS` | 其余 | 两者都做：内部知识精炼 + 外部检索，合并 |

论文的三个可迁移结论：

1. **三档优于二档**：消融实验显示，去掉 `Ambiguous` 这一档（把中间地带强行判成 Correct/Incorrect）会掉点。作者原话是——只有当**置信度不确定时采取软策略**，才能缓解「评估器本身不准」带来的伤害。本项目的 `rerank_floor`(0.25) / `no_answer_threshold`(0.05) 双阈值设计**在思想上与 CRAG 一致**，值得保留并补齐中间档的行为定义。
2. **知识精炼（refine）贡献最大**：消融显示去掉 refinement 掉点最多（PopQA 上 54.9 → 49.8）。对应本项目就是「不要把整块原文直接塞进上下文」，而要做片段级筛选。
3. **检索评估器不必是大模型**：论文实测 T5-based evaluator（84.3% 准确率）**显著优于 ChatGPT 直接判断（58.0%）**。说明「用大模型零样本判断检索质量」是很差的做法，**用本项目的 Qwen3-Reranker 打分反而更有依据** —— 这正是本项目已有的能力。

### 2.4 Agentic RAG / 工具化检索 —— 把检索当成一个工具

[Agentic RAG 综述性材料](https://github.com/ombharatiya/ai-system-design-guide/blob/ddf21ffb87e6c28a1765ba41a6136564895296d5/06-retrieval-systems/08-agentic-rag.md) 把这一路线概括为：检索不再是固定前置步骤，而是 Agent 可自主调用的工具，并且可以**多轮调用、改写查询、后续再检索**。

- **优点**：决策与生成在同一个模型里完成，不需要额外分类器；能处理「先查法规、再查产品、再对比」这类多步检索。
- **已知代价**：延迟不可预测（模型可能连续调用 3 次）、模型可能**该查而不查**（幻觉 = 零成本，检索 = 有成本，模型有偷懒倾向）、也可能**无意义地反复查**。

## 3. 本项目应该怎么选

### 3.1 结论：首版用「LLM 工具调用」做 L1，但必须补两个硬缺口

**推荐方案：模型自主决定（ReAct 工具调用）+ 规则兜底 + 追问改写。**

理由（结合本项目实际）：

| 论据 | 说明 |
| --- | --- |
| **架构已经就位** | `tools_route.py` 自动发现机制意味着新增 RAG 工具的成本 ≈ 0；Agent 循环已经在处理「模型决定调工具 → 后端执行 → 结果回填 messages」的完整链路。加一个分类器反而要在 `agent.py` 里插一段前置逻辑，破坏现有结构。 |
| **职责边界干净** | RAG 模块自己声明「只负责检索，不含答案编排」（见其 README）。让 RAG 模块内部再判断「要不要检索」，等于把编排职责漏进检索模块。 |
| **领域差异太大，规则写不全** | 财富规划场景里，「我需要查知识库吗」的答案高度依赖语义：`「我这个月能存多少」`= 纯用户数据；`「个人养老金缴费上限是多少」`= 纯外部法规；`「按我这个收入该怎么配养老金」`= 两者都要。规则引擎写不全这类组合。 |
| **可观测性** | 工具调用会在 SSE 里产生显式 `tool_call` 事件，前端能看到「正在查知识库」，调试时能直接看出「模型这轮到底查没查」。分类器是隐式的，出问题更难定位。 |

**但必须补的两个缺口：**

#### 缺口 A：多轮追问的指代消解（L2，最容易翻车）

现状代码把 `history` 交给 LLM，但**检索模块只收到当前这一句**。真实对话里极其常见：

```
用户：个人养老金的缴费上限是多少？
助手：（答）每年 12000 元。
用户：那它和税优健康险能叠加吗？        ← 「它」指什么？检索模块不知道
```

对 `「那它和税优健康险能叠加吗」` 直接做向量检索，召回的几乎必然是垃圾 —— 因为查询本身缺少实体锚点。

**处理方式（两条路，建议都做）：**

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A1 · 由 Agent 自己改写**（推荐首版） | 工具 schema 里把 `query` 描述成「**可独立检索的完整查询**，追问时必须补全指代（如把『它』替换成具体政策名称）」，并在 SYSTEM_PROMPT 里明确要求 | 零额外调用、零额外延迟；依赖模型遵循指令。DeepSeek 这类模型对这类指令遵循度通常够用 |
| **A2 · 检索侧自动改写** | 在 RAG 适配层加一个「若 query 长度 < 阈值 或 含指代词（它/这个/那/上面说的），则用 history 让 LLM 改写一次再检索」 | 多一次 LLM 调用（+200~800ms）；但可靠。可作为 A1 失效时的兜底 |

> 调研依据：多轮 RAG 的查询改写是 [query rewriting 模式](https://raw.githubusercontent.com/ai-engineering-curriculum/rag-engineer-learning/refs/heads/main/lessons/mod-106-hybrid-retrieval-fusion-query-rewriting/04-query-rewriting-patterns.md) 中明确点名的失效模式修复手段；同一材料也提醒**改写会在不合适的查询上反而降低召回**，所以 A2 应该带条件触发，而不是无脑每次都改。

#### 缺口 B：确定性兜底触发（幻觉成本不对称）

「模型该查而不查」是工具化检索路线的固有风险。在**财富规划**这个领域，这个风险的代价是不对称的：
编造一条不存在的监管规定（如错误的缴费上限、错误的税率、错误的产品条款）→ 用户可能据此做真实的资金决策。

**建议的兜底触发器（确定性、与模型并行，不阻塞）：**

```
规则 R1（合规/法规类）：query 命中「政策|法规|规定|条例|办法|税|税率|上限|额度|合规|监管|银保监|证监会」等词
   → 强制检索（即使模型这轮没调工具）

规则 R2（引用诉求）：query 含「依据|出处|来源|哪一条|原文|文件」
   → 强制检索，且输出必须带 citation

规则 R3（首轮无工具调用 + 命中 R1/R2 词表）
   → 在 yield done 之前，对 messages 追加一条 system 提示：「本轮问题涉及监管/政策事实，
     请先调用 search_knowledge 查证后再回答」，然后继续循环（消耗一轮 round 预算）
```

> ⚠️ 规则引擎只能兜底「明显该查」的情况，不要试图用它覆盖全部判断。R3 是**软兜底**（提示模型再想一次），不是硬注入 —— 硬注入会破坏 Agent 的自主性，也会让「用户只想聊两句」的场景变得很烦。

### 3.2 三档路由的落地映射（Adaptive-RAG 的三档 → 本项目）

| 复杂度档 | 本项目对应场景 | 触发策略 |
| --- | --- | --- |
| **不检索** | 寒暄；纯用户数据查询（`get_assets` / `calculate_net_worth`）；纯算术 | 模型不调 RAG 工具 |
| **单步检索** | 「缴费上限是多少」「什么是再平衡」这类事实型单跳问题 | 模型调用 1 次 `search_knowledge` |
| **多步检索** | 「我这个资产结构适合什么养老金策略」= 先查自己的资产（已有工具）→ 再查政策 → 综合 | 模型在同一轮或跨轮多次调用，RAG 工具需支持 `doc_type` 过滤以缩小范围 |

### 3.3 工具的输入契约（首版建议）

```python
{
  "type": "function",
  "function": {
    "name": "search_knowledge",
    "description": (
      "检索金融知识库（政策法规、财富规划教材、产品对比资料），返回带来源引用的证据片段。"
      "适用于：政策/法规/规定的具体条款与数额、金融产品条款、专业概念与方法的权威解释。"
      "不适用于：用户自己的资产/负债/流水/目标（用对应的数据工具）、纯数学计算（用计算工具）。"
      "若问题是对上一轮的追问，必须先把指代补全成可独立检索的完整查询。"
    ),
    "parameters": {
      "type": "object",
      "properties": {
        "query": {
          "type": "string",
          "description": (
            "可独立检索的完整查询（不是对话原句）。追问时必须补全指代，"
            "例如把『它和税优健康险能叠加吗』写成『个人养老金与税优健康险能否叠加抵扣』。"
          ),
        },
        "top_k": {"type": "number", "description": "返回证据条数，默认 5，最多 8"},
        "doc_type": {
          "type": "string",
          "enum": ["policy", "textbook", "product", "all"],
          "description": "限定检索范围；不确定时用 all（默认）",
        },
      },
      "required": ["query"],
    },
  },
}
```

> **注意**：`doc_type` 需要 RAG 侧支持按文档类型过滤。当前 `QdrantStore._filter` 只支持 `doc_id` 单字段过滤（见 `store/qdrant_store.py:148-154`），**要么扩展成 `doc_type` payload 字段 + filter，要么首版先砍掉这个参数**。建议首版砍掉——`doc_id` 过滤在 24 篇文档规模下几乎没有实用价值，而 `doc_type` 需要重新摄入打标。

### 3.4 L3（检索后质量判定）的现状与缺口

现有代码（`retrieval/hybrid.py::_fuse`）已经是一个三档判定：

```python
if max_rerank < r.no_answer_threshold:        # 0.05
    → 全部标记 low_confidence                # 「库中可能没有相关证据」
elif max_rerank >= r.rerank_floor:            # 0.25
    → RRF 归一化分与 rerank 分加权融合，重排主导
else:
    → 保留 RRF 排序（泛查询保底）
```

这个设计与 CRAG 的三档思想一致，**方向是对的**。缺口在：

1. **阈值未经校准**（0.05 / 0.25 是拍出来的经验值），必须用本项目语料实测分数分布后重新定（见 [04](../04-open-questions-and-eval.md)）；
2. **`low_confidence` 之后没有动作定义**：现在只是打个标记，上层拿到之后该做什么没有规定。CRAG 的答案是「触发纠错动作」，本项目首版最合理的动作是**拒答 + 明确告知用户**（而不是硬答），因为财富规划领域编造法规的代价太高；
3. **中间档（0.05 ≤ max < 0.25）当前是「静默退回 RRF」** —— 代码注释里叫「泛查询保底」。这档的语义是「重排器不确定」，但返回给上层的 `low_confidence=False`，**上层无法区分「重排确认很相关」和「重排不确定、退回关键词排序」**。建议补一个显式的 `evidence_quality` 三值字段（详见 [02](02-rerank-output.md#5-证据质量信号怎么传给上层)）。

## 4. 不建议的做法

| 做法 | 为什么不做 |
| --- | --- |
| **每轮都无条件检索** | ① 纯财务数据查询（「我这个月花了多少」）不需要知识库，白白增加 1~3s 延迟；② 会往上下文里塞不相关内容，稀释真正有用的证据（CRAG 论文的核心论点就是低质检索结果会**主动误导**生成） |
| **外挂一个「是否需要 RAG」的小分类器** | ① 本项目没有标注数据来训它；② Adaptive-RAG 的分类器是训练出来的，零样本用小模型判复杂度实测并不稳；③ 多一跳延迟；④ 与现有 ReAct 结构重复 |
| **用大模型零样本判断检索结果好不好** | CRAG 论文实测：ChatGPT 判检索相关性 58.0%，专用轻量评估器 84.3%。**本项目已有 Qwen3-Reranker，直接用它的分数更有依据** |
| **把 `rerank_floor` 当拒答阈值** | 语义混淆。`rerank_floor` 判的是「重排器可不可信」，`no_answer_threshold` 判的是「库里有没有东西」。把前者当拒答条件会在泛查询上大面积误拒 |

## 5. 小结

| 问题 | 结论 |
| --- | --- |
| **谁来决策？** | 首版：LLM 通过 function calling 自主决策（与现有 ReAct 架构一致，零结构改动） |
| **决策粒度？** | 三档：不检索 / 单次检索 / 多轮检索；靠工具描述 + SYSTEM_PROMPT 引导，不靠分类器 |
| **最大的两个缺口？** | ① 追问指代未消解 → 检索质量断崖；② 模型该查不查 → 领域代价不对称（会编法规） |
| **怎么补？** | ① 工具 schema 强制要求「可独立检索的完整查询」+ 可选自动改写兜底；② 关键词规则 + 软兜底再提示 |
| **检索完不够怎么办？** | 沿用现有三档判定，但阈值必须实测校准；`low_confidence` 的动作定义为「拒答并说明」，不是「硬答」 |
