# 两个前置件详解

> 本文把 [05-落地方案](05-落地方案-WealthPilot.md) 里 P0 与 P2 两件事拆开讲透：
>
> 1. **历史回放展开器** —— 把 UI 形态的历史变成 OpenAI 协议形态
> 2. **`/api/chat` 接入 `conversation_id`** —— 让后端成为历史的权威源
>
> 这两件本身**不是**上下文管理，但 L2 的所有策略（掩码、窗口、摘要）都建立在它们之上。
> 它们的共同特点是：**看起来只是"加个函数/加个字段"，实际上每个都有必须先想清楚的边界情况。**

---

## 0. 先修正一个说法

在之前的对话里我说过：

> “messages 表存的是 UI 形态（工具结果内嵌在 `assistant.tool_calls`），
> 直接回放会缺 `role="tool"` 消息 → API 400。”

**核对代码后，这个说法需要修正。**

- **作为对存储数据的判断，它是成立的**：DB 里确实只有 `user` / `assistant` 两种角色，
  工具结果内嵌在 `tool_calls` 的 JSON 里，直接映射会缺 `tool` 消息。
- **但当前线上不会因此 400**：因为**前端在发送前做了转换**
  （[`useChat.ts:30-71`](../../frontend/src/hooks/useChat.ts#L30-L71) 的 `buildHistory`），
  它会补出 `role="tool"` 消息。类型定义里甚至把这条协议约束写成了注释
  （[`types/index.ts:28-42`](../../frontend/src/types/index.ts#L28-L42)）：

  > ```
  > - assistant 带 tool_calls 时，其后必须紧跟对应数量的 tool 消息
  > - tool_calls[].function.arguments 是 JSON 字符串
  > ```

所以准确的表述是：

> **这层转换已经存在，但它在错误的层（客户端），而且它自己有两个真实的协议漏洞。**

结论不变——这件事仍然必须做，只是理由变了：不是“修一个必然会炸的 bug”，
而是“**把关键协议逻辑从客户端搬到服务端，并修掉它在客户端时留下的两个洞**”。

# 第一部分 · 历史回放展开器

## 1.1 必须分清三种“消息形态”

同一个工具调用，在系统里有三种完全不同的形状。混用任何两个都会出问题。

### 形态 A · UI 形态（前端 `ChatMessage.toolCalls`）

```ts
interface ToolCall {
  id: string
  name: string
  arguments: Record<string, unknown>   // ← 对象
  result?: unknown                     // ← 结果内嵌在这里
  status: "running" | "success" | "error"
  startedAt: number
  endedAt?: number
}
```

**特征**：为展示服务。`result` 与 `status` 内嵌，只为了画“工具卡片”和打勾/标红。
`startedAt/endedAt` 是纯 UI 数据（算耗时）。

### 形态 B · OpenAI 协议形态

```jsonc
// 1 条 assistant，携带 tool_calls
{"role": "assistant", "content": "我查一下",
 "tool_calls": [{"id": "call_1", "type": "function",
                 "function": {"name": "get_assets", "arguments": "{}"}}]}

// N 条 tool，每个 call 一条，必须紧跟其后
{"role": "tool", "tool_call_id": "call_1", "content": "{\"data\": ...}"}
```

**特征**：`arguments` 是**字符串**（不是对象）；结果在**独立的 `role="tool"` 消息**里；
`tool_calls` 元素必须包一层 `type` + `function`。

### 形态 C · DB 存储形态（`messages` 表）

```
role       = "assistant"
content    = "我查一下"
tool_calls = JSON 数组，元素是 **形态 A**（含 result/status/startedAt）
```

**特征**：本质是“把形态 A 整体序列化后存进一个 TEXT 列”。
[`conversations.py:114-116`](../../backend/core/services/conversations.py#L114-L116) 就是这么写的
（`json.dumps(entry["tool_calls"])`）。

### 三处差异一览

| 差异 | 形态 A（UI） | 形态 B（协议） | 展开时要做什么 |
| :--- | :--- | :--- | :--- |
| `arguments` 类型 | 对象 | **字符串** | `json.dumps` |
| 结果位置 | 内嵌 `result` | **独立 tool 消息** | 拆出 N 条 |
| 调用结构 | 扁平 `{id,name,...}` | `{id,type,function:{name,arguments}}` | 包一层 |

**任何一处没转，都会踩坑**：`arguments` 传对象 → SDK 序列化异常或模型读到畸形容器；
结果不拆 → 缺 tool 消息 → 400；结构不包 → 协议不认。

## 1.2 当前是谁在做这层转换

[`frontend/src/hooks/useChat.ts:30-71`](../../frontend/src/hooks/useChat.ts#L30-L71) 的 `buildHistory`。
它做对了三件事：

```ts
const calls = m.toolCalls ?? []
const tool_calls = calls
  .filter((tc) => tc.name)                                  // ① 过滤无名调用
  .map((tc) => ({
    id: tc.id,
    type: "function" as const,                              // ② 包 type
    function: {
      name: tc.name,
      arguments: JSON.stringify(tc.arguments ?? {}),        // ③ 对象 → 字符串
    },
  }))
history.push({ role: "assistant", content: m.content, tool_calls })

for (const tc of calls) {
  if (tc.result !== undefined) {                            // ④ 补 tool 消息
    history.push({ role: "tool", content: ..., tool_call_id: tc.id })
  }
}
```

所以**正常的会话续聊是能跑通的**。但这层实现有四个问题。

## 1.3 为什么仍然必须搬到服务端

### 原因 1 · 两份实现必然漂移

[05-落地方案](05-落地方案-WealthPilot.md) 的 P2 要让后端接管历史。一旦后端从 DB 回放，
就**必须重新实现一遍**同样的转换。于是系统里出现两份：

- 前端 `buildHistory`（服务端组装前的兼容路径还在用）
- 后端 expander（服务端组装用）

两份做同一件事，**改一处忘一处只是时间问题**。而这类不一致的症状是“某种历史组合下才 400”，
极难复现。

### 原因 2 · 客户端可被绕过

[`chat.py:11-13`](../../backend/api/routes/chat.py#L11-L13)：

```python
class ChatRequest(BaseModel):
    message: str
    history: list          # ← 类型只是 list，没有任何结构校验
```

`history: list` 意味着**任何 JSON 都能进来**。后端的正确性完全依赖前端“守规矩”。
这既是健壮性问题，也是安全问题（详见 §2.2-C3）。

### 原因 3 · 转换时机与落库时机不一致

- 转换发生在**发送时**（`buildHistory(messagesRef.current)`，`useChat.ts:198`）
- 落库发生在**整轮结束时**（`finally` 块，`useChat.ts:246-251`）

两者看到的 `toolCall` 状态**可能不同**。这正是下面的漏洞 A 的成因。

### 原因 4 · 服务端回放根本拿不到这份转换

这是最根本的一条：**P2/P3 的所有 L2 策略都要求“服务端拿到历史并组装 messages”**。
只要转换只在客户端，服务端就永远无法独立完成组装。

## 1.4 两个真实漏洞（有代码证据）

### 漏洞 A · `result === undefined` 时缺 tool 消息 → 会话永久损坏

**触发链**（每一环都有代码位置）：

1. `tool_call` 事件到达 → 前端建一个 `status: "running"`、**没有 `result`** 的 tc
   （[`useChat.ts:275-283`](../../frontend/src/hooks/useChat.ts#L275-L283)）；
2. 只有 `tool_result` 事件到达时，才会写入 `result`（[`useChat.ts:285-298`](../../frontend/src/hooks/useChat.ts#L285-L298)）；
3. 如果流在**这两个事件之间**中断，`result` **永远是 `undefined`**。

   中断的常见原因：用户关页面 / 点停止、网络断开、后端异常（`chat.py` 的 `except` 产出 error 事件）、
   进程被重启。

4. `buildHistory` 只对 `result !== undefined` 的调用补 `tool` 消息
   （[`useChat.ts:57`](../../frontend/src/hooks/useChat.ts#L57)）→
   **assistant 的 `tool_calls` 里有一个 id，但后面没有对应的 `tool` 消息**；
5. **更糟的是它被持久化了**：`finally` 块把这条 assistant（连同 `status: "running"` 的 tc）
   写进 DB（[`useChat.ts:246-251`](../../frontend/src/hooks/useChat.ts#L246-L251)）。

**后果**：这个会话**再也无法继续**。下次打开它、发任何消息，`buildHistory` 都会产出
“有 `tool_calls` 无 `tool` 应答”的历史 → 请求 400。

而且**错误提示与真实原因无关**——用户看到的是“请求失败”，而非“上次的工具调用没完成”。

补一刀：`applyEvent` 的 `error` 分支**不改消息结构**
（[`useChat.ts:299-301`](../../frontend/src/hooks/useChat.ts#L299-L301)：
*“thinking / round / done / error 不改消息结构”*）。
所以后端发一个 `error` 事件**不会**把在跑的 tc 标成失败，它仍然是 `running`、仍然没有 `result`。

### 漏洞 B · `name` 过滤不对称 → 孤儿 tool 消息

看这两行的**不对称**：

```ts
const tool_calls = calls.filter((tc) => tc.name).map(...)   // 第 38 行：过滤了 name
...
for (const tc of calls) {                                   // 第 56 行：遍历未过滤的 calls
  if (tc.result !== undefined) { push tool 消息 }
}
```

如果某个 tc 的 `name` 为空（或缺失）但 `result` 存在：

- `assistant.tool_calls` 里**没有**它（被 filter 掉了）；
- 但 `tool` 消息**有**它（循环用的是未过滤的 `calls`）。

→ 产生一条 **`tool` 消息，其 `tool_call_id` 不在前一条 assistant 的 `tool_calls` 里**。
这是另一种协议违规：孤儿 tool 消息。

> **两处必须用同一个列表。** 这个 bug 的教训不是“记得过滤”，而是
> **配对关系必须由构造保证（单一数据源），不能靠两侧各自过滤**。

## 1.5 正确设计：一个纯函数 + 五条不变量

### 五条不变量（invariants）

| # | 不变量 | 违反后果 |
| :-- | :--- | :--- |
| **I1** | 每个 `tool_calls[i].id` **恰好**对应一条 `tool` 消息 | 400（缺应答） |
| **I2** | 每条 `tool` 消息的 `tool_call_id` 必须能在**紧邻的前一条** assistant 的 `tool_calls` 里找到 | 400（孤儿应答） |
| **I3** | `arguments` 必须是**字符串** | 序列化异常 / 模型读错 |
| **I4** | 缺 `result` 时**必须合成**一条 tool 消息，不能省略 | 400（缺应答） |
| **I5** | 不改变消息相对顺序，不重排 | 上下文语义错乱 |

**I1 与 I2 必须同时成立**，且必须由**同一个过滤后的列表**同时驱动
（这是修漏洞 B 的关键）。**I4 是修漏洞 A 的关键**——见下。

### 为什么 I4 要“合成”而不是“省略”

省略 → 缺应答 → 400，会话死掉。
合成 → 模型看到“这个调用没拿到结果，可以重试” → 会话活着，且模型知道自己该重试。

也就是说，**I4 把一个致命的协议错误降级成了一个可恢复的语义提示**。

### 代码骨架

```python
# backend/core/services/replay.py（新增）

import json


#: 给"没有结果"的工具调用合成的提示。刻意复用 route() 的错误契约（error_kind/retryable），
#: 让模型用同一套理解去处理——它已经学会"retryable=true 就重试"。
_INTERRUPTED = json.dumps({
    "error": "该工具调用未返回结果（可能被中断）",
    "error_kind": "interrupted",
    "retryable": True,
    "hint": "如需该数据，请重新调用此工具。",
}, ensure_ascii=False)


def _as_arguments_string(value) -> str:
    """I3：协议要求 arguments 是 JSON 字符串；DB 里可能存的是对象。"""
    if isinstance(value, str):
        return value
    return json.dumps(value if value is not None else {}, ensure_ascii=False)


def expand_to_model_messages(rows) -> list:
    """把 DB 的 UI 形态消息行展开成 OpenAI 协议形态的 messages。

    **只做形态转换，不做裁剪。** 裁剪（掩码/窗口/摘要）是它下游的独立步骤，
    两者分开才能各自测试、各自回滚。

    rows 元素：{"role": "user"|"assistant", "content": str, "tool_calls": [...]?}
    返回：可直接喂给 chat.completions.create 的 messages（不含 system）。
    """
    out = []

    for row in rows:
        role = row["role"]

        if role != "assistant":
            out.append({"role": role, "content": row.get("content") or ""})
            continue

        calls = row.get("tool_calls") or []

        # I1/I2 的实现关键：**只在**这里过滤一次，两侧共用 usable。
        # 绝不能让 tool_calls 与 tool 消息各自过滤——那正是漏洞 B 的成因。
        usable = [c for c in calls if c.get("name")]
        if len(usable) != len(calls):
            print(
                f"[replay] ⚠️ 丢弃 {len(calls) - len(usable)} 条无 name 的 tool_call"
                f"（无法构造合法协议，成对丢弃）"
            )

        if not usable:
            out.append({"role": "assistant", "content": row.get("content") or ""})
            continue

        out.append({
            "role": "assistant",
            "content": row.get("content") or "",
            "tool_calls": [
                {
                    "id": c["id"],
                    "type": "function",
                    "function": {
                        "name": c["name"],
                        "arguments": _as_arguments_string(c.get("arguments")),
                    },
                }
                for c in usable
            ],
        })

        # I4：**无条件**为每个 usable 调用补一条 tool 消息；缺 result 时用合成内容。
        for c in usable:
            result = c.get("result")
            if result is None:
                content = _INTERRUPTED
            elif isinstance(result, str):
                content = result
            else:
                content = json.dumps(result, ensure_ascii=False)
            out.append({"role": "tool", "tool_call_id": c["id"], "content": content})

    return out
```

### 三个设计取舍，说明为什么这么写

**① 输入是“存储形态行”，不是“前端传来的 history”。**
这样即使 P2 还没做，也能先用 DB 数据测试；等 P2 上线时无需改函数。
如果按“前端 history”设计，P2 时必重写。

**② 成对丢弃，绝不成对拆开。**
无 `name` 的调用无法构造合法 `tool_calls` 元素，所以**连它的 tool 消息一起丢**。
宁可少一条历史，也不能破坏 I1/I2。

**③ 不在这里做截断。**
`result` 可能是 15k 字符的检索原文——这属于 L1 的裁剪职责
（见 [01-L1 §4](01-L1-单次调用上下文.md)），不在这里做，否则两个职责耦合。

## 1.6 测试计划

### 正向用例

| 用例 | 断言 |
| :--- | :--- |
| 单个 tool_call + 有 result | 输出 = assistant(1 个 call) + tool(1 条)，id 配对 |
| 并行 3 个 tool_call | 输出 = assistant(3) + tool(3)，顺序与 calls 一致 |
| `arguments` 是对象 | 输出里是**字符串**且能 `json.loads` |
| 无 tool_calls 的 assistant | 输出是纯 assistant，不额外补 tool |

### 反向用例（更重要）

| 用例 | 断言 | 守的不变量 |
| :--- | :--- | :--- |
| **某调用缺 `result`** | 仍输出**等量** tool 消息，内容含 `interrupted` | **I4** |
| **某调用 `name` 为空但有 result** | 该调用与它的 tool 消息**一起消失**，不产生孤儿 | **I1/I2** |
| `tool_calls` 为空数组 | 不输出 tool 消息 | I1 |
| `result` 是字符串 / 是对象 | 都能正确进 `content` | I4 |

### 一条结构性断言（建议加）

```python
def assert_pairing(messages):
    """不变量自检：任何 assistant.tool_calls 的 id 集合，必须与紧随其后的 tool 消息集合完全相等。"""
    pending = None
    for m in messages:
        if m["role"] == "assistant" and m.get("tool_calls"):
            assert pending is None, "上一条 assistant 的 tool_calls 还没被应答"
            pending = {c["id"] for c in m["tool_calls"]}
        elif m["role"] == "tool":
            assert pending is not None, "孤儿 tool 消息"
            assert m["tool_call_id"] in pending, f"{m['tool_call_id']} 不在待应答集合"
            pending.discard(m["tool_call_id"])
        else:
            assert pending is None, "tool_calls 未应答就出现新消息"
    assert pending is None or pending == set()
```

把它用在**每条**用例的末尾，比逐个字段断言更可靠。

拿一个含工具调用的真实会话（从 `messages` 表读），经 `expand_to_model_messages` 后直接：

## 1.7 迁移路径

| 步 | 动作 | 风险 |
| :-- | :--- | :--- |
| 1 | 后端加 `replay.py` + 单测，**不接线** | 零 |
| 2 | `/api/chat` 对传入 `history` 做**归一化**：已是协议形态 → 透传；是 UI 形态 → 转换 | 低（需幂等，见下） |
| 3 | P2 上线后，服务端从 DB 读 → expander 成为唯一来源 | 中 |
| 4 | 前端 `buildHistory` 退役（可先保留一个版本作兜底） | 低 |

**第 2 步的“幂等归一化”很关键**：兼容期内同时可能收到协议形态和 UI 形态的 history，
必须能判断且转换结果稳定：

```python
def normalize_history(history):
    """幂等：已经是协议形态就原样返回，是 UI 形态就转换。"""
    if not history:
        return []
    if _looks_like_protocol(history):
        return history          # 已有 role="tool" 消息，且 arguments 是字符串
    return expand_to_model_messages(history)
```

判据建议：**存在任意 `role="tool"` 消息，或任意 `tool_calls[i].function` 结构** → 协议形态。
不要靠“有没有 `result` 字段”判断（两种形态都可能没有）。

# 第二部分 · `/api/chat` 接入 `conversation_id`

## 2.1 现状

[`chat.py:11-13`](../../backend/api/routes/chat.py#L11-L13)：

```python
class ChatRequest(BaseModel):
    message: str
    history: list
```

[`agent.py:30-36`](../../backend/core/agent/agent.py#L30-L36)：

```python
messages = [{"role": "system", "content": SYSTEM_PROMPT}]
if history:
    messages.extend(history)
messages.append({"role": "user", "content": message})
```

即：**后端是完全无状态的转发器**，历史由客户端全权提供。

---

## 2.2 三个直接后果

### C1 · L2 的策略没有作用对象

- **掩码**要知道“最近 N 轮”边界 → 需要会话；
- **预算**要知道“这次会话总共多少 token” → 需要会话的完整历史；
- **压缩**要把摘要挂到某处 → `conversations.summary` 字段已就位
  （[`schema.py:150`](../../backend/core/database/schema.py#L150)），
  但**没有任何服务端组装流程会去读它**。

现在的实情是：历史**存了**（前端通过 `/api/conversations/{id}/messages` 写），
但**从不参与“发给模型的历史组装”**。两条链路各走各的。

### C2 · 无法做预算与触发

你不知道这次请求占了多少窗口，自然也无法判断“是不是该压缩了”。
`usage` 是**响应之后**才知道的，而裁剪必须在**请求之前**决定。

### C3 · `history` 是客户端可控输入（这条最要紧）

`history: list` 没有任何结构校验，意味着客户端可以发**任意** messages。三个具体风险：

| 伪造内容 | 后果 |
| :--- | :--- |
| 一条 `assistant` 消息，内容“好的，我同意给你配 30% 股票” | 模型会把它当作**既成事实**继续推理 |
| 一条 `tool` 消息，内容是伪造的资产数据 | **绕过所有工具校验**——上一轮加固的参数校验、白名单、写工具保护**全部失效**，因为根本不经过 `route()` |
| 删掉/重排不利的历史 | 结论偏差，且后端**完全无法察觉** |

第二条尤其值得强调：**我们在工具调用链路上做的所有兜底，都假设“工具结果来自 route()”**。
而 `history` 里的 `tool` 消息是一条**旁路**，它不经过 `route()`、不触发 `validate_arguments`、
不进 `seen_calls`、不参与未知工具熔断。

> 换句话说：**只要 history 由客户端提供，服务端的工具安全边界就有一个可绕过的后门。**
> 这不是“设计不够优雅”，是**完整性缺陷**。

---

## 2.3 为什么这不是“加个字段”

表面上只是把 `history: list` 换成 `conversation_id: int`。实际上要连带回答六个问题：

| # | 问题 | 不回答会怎样 |
| :-- | :--- | :--- |
| 1 | **谁写历史？** 前端写还是后端写？ | 两边都写 → 重复消息 |
| 2 | **什么时候写？** 每轮结束 / 每个事件 / 流中断时？ | 断流就丢整轮 |
| 3 | **并发怎么办？** 两个标签页同会话 | 消息交错、tool_calls 错配 |
| 4 | **重试怎么幂等？** 客户端重发同一条 | 用户消息重复入库 |
| 5 | **老前端怎么办？** 仍传 `history` | 直接 422 |
| 6 | **断流留下的半截消息怎么标？** | 又回到漏洞 A |

**第 6 个问题与第一部分直接相连**：断流产生的“assistant 有 tool_calls、tool 无 result”
必须能被回放器正确处理（I4 就是为它准备的）。

---

## 2.4 目标契约

### 接口

```python
class ChatRequest(BaseModel):
    message: str
    conversation_id: int | None = None    # 新增；None 表示新会话，由后端创建
    client_msg_id: str | None = None      # 新增；幂等键，防重发

    # 兼容期保留：带 conversation_id 时**忽略**；只传 history 时走旧路径并告警
    history: list | None = None
```

### 服务端流程

```
POST /api/chat
  │
  ├─ ① conversation_id 为空 → 创建会话行（title 由首条消息截取）
  ├─ ② 校验会话存在（不存在 → 404，而不是静默新建）
  ├─ ③ 幂等检查：client_msg_id 已在 messages 里 → 直接返回错误或复用
  ├─ ④ 先把 user 消息落库            ← 关键：防断流丢用户输入
  ├─ ⑤ 读 messages → expand_to_model_messages()
  ├─ ⑥ 裁剪（P1 掩码 / 锚点）→ 预算检查 → 必要时压缩（P3）
  ├─ ⑦ 流式生成；**每轮结束追加** assistant（含 tool_calls）
  └─ ⑧ 流异常/断开 → 把已产出部分追加为 interrupted 的 assistant
```

### 两个关键改动（与现状相反）

**改动 1：user 消息在请求开始就落库，而不是整轮结束。**

现状是前端在 `finally` 里一次性写 user + assistant（[`useChat.ts:246-251`](../../frontend/src/hooks/useChat.ts#L246-L251)）。
中途断流 → **用户的输入也丢了**。后端接管后，先落 user 是更安全的选择。

**改动 2：assistant 每轮追加，而不是整轮结束才写。**

一次对话可能有 5 轮工具循环。若只在结束时写，前 4 轮的中间产物全丢；
断流时更是什么都没有。按轮追加，断流也能留下“做到哪一步”。

### 状态机

```
conversation:
   (无) ──首条消息──> active ──删除──> (删除, messages 级联)
                        │
                        └── messages 追加（整轮多次）

message.status（建议新增列）:
   pending（user 已入、assistant 未出）
   completed
   interrupted（流中断，assistant 半截）
```

> `status` 也可以不加列：**用 `tool_calls` 里那个缺 `result` 的调用本身表达“未完成”**
> 是最轻的做法（无需迁移），代价是查询时不便统计。我倾向先不加列，靠 §1.5 的 I4 兜住。

---

## 2.5 四个必须先想清楚的边界

### B1 · 断流

有三种处理，必须选一个：

| 方案 | 行为 | 评价 |
| :--- | :--- | :--- |
| 丢弃半截 assistant | 历史干净 | **用户输入白丢、模型不知道发生过**，下次会重复劳动 |
| 原样保存 | 保留痕迹 | 会触发漏洞 A（缺 tool 应答）→ **400** |
| **保存 + 靠 I4 合成** | 保留痕迹且协议合法 | ✅ **推荐** |

选第三种：不新增字段、不回滚逻辑，只要回放器按 I4 无条件补 tool 消息即可。

### B2 · 并发（两个标签页同会话）

症状：两个流同时往一个 `conversation_id` 追加 → 消息交错，
`assistant(tool_calls)` 与 `tool` 消息错配 → 回放时 I1/I2 校验失败。

两种解法：

| 解法 | 说明 | 代价 |
| :--- | :--- | :--- |
| **会话级互斥** | 同一会话同时只允许一个流（内存锁 / DB 标记） | 简单，但多进程要共享锁 |
| **乐观锁** | `conversations` 加 `version`，追加时校验；冲突则 409 | 需要前端处理冲突 |

**建议先做会话级互斥**（单用户场景下足够），并在 UI 上禁用“同会话并行发送”。

### B3 · 重试幂等

客户端网络抖动重发同一条消息 → 用户消息重复入库。

解法：`client_msg_id` + `messages` 表加唯一索引（或查重后跳过）。
**不要用 `message` 文本判重**——用户合法地连发两句一样的话是正常的。

### B4 · 老前端兼容

必须有兼容期，否则一次部署就断掉所有在线用户：

```
有 conversation_id  → 新路径：服务端读库 + 组装
只有 history        → 旧路径：normalize_history(history) 后使用，并打 warn 日志
两者都有            → 以 conversation_id 为准，忽略 history（并 warn）
两者都无            → 纯单轮对话（合法）
```

**兼容期一定要有明确的退出条件**（比如“上传率 < 1% 后移除”），否则兼容代码会永久留存。
这与本项目此前记录的经验一致：**权宜之计要有退役动作**。

## 2.6 迁移路径（4 步，每步可独立上线）

| 步 | 动作 | 可回滚？ | 验收 |
| :-- | :--- | :--- | :--- |
| 1 | 后端加 `conversation_id`（可选）+ 服务端组装；`history` 仍生效 | ✅（字段不传即旧行为） | 新旧路径都能跑通同一会话 |
| 2 | 前端改为传 `conversation_id`，**保留** `buildHistory` 作兜底 | ✅（开关切回） | 同一会话续聊、含工具调用不报错 |
| 3 | 后端开始**写**历史（前端停止写） | ⚠️ 需避免双写期 | 消息不重复、轮次顺序正确 |
| 4 | 移除 `history` 参数与前端 `buildHistory` | ❌ | 旧客户端返回 422（或保留 1 个版本的兼容） |

**第 3 步是风险点**：写权转移期间如果两边都在写，会重复。
建议用一个 feature flag 明确“当前谁是写方”，**不要靠两边各自判断**。

---

## 2.7 验收

| 检查项 | 方法 | 期望 |
| :--- | :--- | :--- |
| 续聊含工具调用不报 400 | 真实会话跑通 | ✅ |
| 断流后仍能续聊 | 手工 kill 流（中途关闭连接），再发消息 | 不 400，且模型知道工具未完成 |
| 并发保护 | 同会话两个请求同时发 | 一个 409 / 一个被拒 |
| 幂等 | 同一 `client_msg_id` 重发两次 | 库里只有一条 |
| 预算可控 | 打印每轮 `input tokens` | 趋稳，不单调上升 |
| 后门关闭 | 构造带伪造 `tool` 消息的 `history` | 新路径下被忽略（不再影响模型） |

倒数第二、三项是新路径真正的价值——**它们在前端主导的架构下根本无法实现**。

# 第三部分 · 两者的顺序与依赖

## 3.1 为什么 expander 先做

| 理由 | 说明 |
| :--- | :--- |
| **纯函数** | 输入 list、输出 list，无 IO、无状态、无 DB → 测试成本极低 |
| **可独立验收** | 单测 + 一次真实 API 调用即可证明配对正确 |
| **零行为变更** | 不接线时对线上无影响 |
| **是 P2 的前置** | 服务端组装必须调用它，否则组装出来的 messages 不合法 |

## 3.2 但 expander 必须**按“从 DB 回放”来设计**

即使当下最先处理的输入是“前端传来的 history”，expander 的输入契约也应当定义成
**存储形态行**（`{role, content, tool_calls}`）而不是前端的 `HistoryMessage`。

理由：前端的 `HistoryMessage` 已经是协议形态（`function.arguments` 是字符串、
有独立 `tool` 消息），拿它做输入等于**让函数依赖一个即将退役的形态**。

用存储形态做输入的好处：

- 现在就能用 DB 里的真实数据测试；
- P2 上线时**不用改函数**；
- 兼容期的“归一化”只是它的一个薄包装。

## 3.3 顺序图

```
             ┌─────────────────────────────┐
现在 ──────> │ 前端 buildHistory（客户端） │ ──> /api/chat ──> agent
             └─────────────────────────────┘
                     ↑ 两个漏洞，且不可信

             ┌─────────────────────┐
第 1 步后 ──> │ normalize_history() │ ──> /api/chat ──> agent
             └─────────────────────┘
                     ↑ 幂等：协议形态透传，UI 形态走 expander

             ┌──────────────┐   ┌──────────┐
第 3 步后 ──> │ messages 表  │──>│ expander │ ──> 裁剪 ──> agent
             └──────────────┘   └──────────┘
                     ↑ 服务端权威，客户端 history 被忽略
```

## 附 · 一句话

> **expander 解决“历史能不能正确喂给模型”，`conversation_id` 解决“历史归谁管”。**
> 前者是正确性问题（会 400），后者是控制权与完整性问题（会被绕过）。
>
> 两个都做完，L2 才真正有地基可以动工。
