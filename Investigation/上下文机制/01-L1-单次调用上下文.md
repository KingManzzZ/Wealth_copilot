# L1 · 单次调用上下文

> **作用域**：一次 `chat.completions.create` 请求。边界是「这一次 HTTP 调用」。
> **核心问题**：这一次的 `messages` 里放什么、按什么顺序放、放多少。
> **产出指标**：每轮 input tokens、缓存命中率、答案质量。

---

## 1. L1 的边界与解剖

`messages` 的实际结构（本项目 [`agent.py:30-36`](../../backend/core/agent/agent.py#L30-L36) 就是这个形状）：

```
┌─ system      指令（角色、规则、工具使用规范）          稳定，几乎不变
├─ tools       工具 schema（24 个，每轮都传）            稳定，随代码变
├─ history     L2 决定的「历史切片」                     每次都在变
├─ user        本次用户输入                             必然变
└─ tool 往返   assistant(tool_calls) + tool(result) × N  轮内变
```

L1 要优化的就是这张表里**前两段的复用**和**最后两段的体积**。

一个容易被忽略的事实：**L1 是唯一真正“花 token”的地方**。L2 的裁剪、L3 的检索，
最终都要落到“这一次请求的 messages 长什么样”。所以 L2/L3 全是 L1 的上游供给方。

---

## 2. 策略一：顺序即成本（提示词缓存）

这是 L1 里**性价比最高、也最容易做错**的一条。

### 2.1 原理

提示词缓存（prompt caching）按**前缀**命中：缓存键是「这个块的内容 + 它之前的所有内容」。
所以**越稳定的东西越要放前面**，任何一处变动都会让后面全部失效。

**稳定度阶梯**（从最稳定到最易变）：

```
1. system prompt        很少变
2. tools 定义           随代码发布变
3. 长静态上下文（文档/示例）  一个会话内不变
4. 上一轮 assistant 回复   该轮结束后就固定
5. 当前轮输入            每轮必变
```

### 2.2 各家的机制差异（直接影响能不能用）

| 提供商 | 机制 | 关键约束 |
| :--- | :--- | :--- |
| **Anthropic** | 显式 `cache_control` 断点 | **每请求最多 4 个断点**；默认 TTL 5 分钟，1h TTL 需 beta header；写 1.25×、读 0.1× |
| **OpenAI** | 自动前缀缓存 | 前缀需 **≥1024 tokens** 且**字节级一致**；无写溢价、也无 TTL 控制 |
| **Gemini** | 隐式 / 显式两套 | 显式 `cachedContents.create()` 有**最小尺寸悬崖**（2.5 Pro 约 32k、2.5 Flash 约 4096） |

### 2.3 五个真实陷阱

来源：[prompt-cache gotchas](https://github.com/OnlyTerp/prompt-cache-skills/blob/main/docs/gotchas.md)（工程踩坑汇总）

| # | 陷阱 | 症状 |
| :--- | :--- | :--- |
| 1 | **把断点打在“当前的 user 消息”上** | 每轮都在付 1.25× 写入、读命中为 0，**比不缓存更贵** |
| 2 | **工具定义序列化不一致** | dict 迭代顺序 / 空白 / JSON Schema 重排 → 工具缓存**每轮都 miss**，且不报错 |
| 3 | **system prompt 里注入时间戳** | “今天是 2026-10-16” → 缓存**每天失效一次** |
| 4 | **`prompt_cache_key` 用随机 UUID** | OpenAI 拿它当 pod 路由提示，随机 key = 随机路由 = **冷缓存**。应改用「system + tools 的 hash」 |
| 5 | **中转层 200 接受但静默丢弃缓存字段** | 网关/relay 接受 `cache_control` / `prompt_cache_key` 却不实现，**永不命中且无任何报错** |

> **⚠️ 第 5 条对本项目直接相关**
>
> 本项目的 `client = OpenAI(base_url=os.getenv("LLM_URL"))` 走的就是一个 **OpenAI 兼容中转**。
> 这意味着：即使你按 Anthropic/OpenAI 的文档配了缓存字段，**这个中转很可能根本不转发**。
>
> **验证方法**（不要相信文档，要测实际链路）：发两次相同前缀的请求，检查返回的 `usage`：
>
> - OpenAI 系：`usage.prompt_tokens_details.cached_tokens > 0`
> - Anthropic 系：`usage.cache_read_input_tokens > 0`
>
> **命中率 = `cache_read / (cache_read + cache_creation + input_tokens)`**，
> 稳态 agent 循环应 **> 0.8**。如果长期为 0 且无报错，就是被中转吞了。

### 2.4 本项目可立即做的最小改动

当前 `SYSTEM_PROMPT` 是模块级常量（[`prompt.py`](../../backend/core/agent/prompt.py)），
`TOOLS_SCHEMA` 是模块级常量——**顺序天然已经是对的**（system 在前、tools 紧随）。

所以 L1 缓存的成本几乎为零，只需要确认两件事：

1. **不要**往 system prompt 里动态插时间/用户名（目前没有，保持）；
2. 确认 `LLM_URL` 那个中转是否真的透传缓存字段（做一次上面的验证）。

## 3. 策略二：工具定义本身就是上下文

24 个工具的 schema 每轮都要传，它占的 token 是**固定成本 × 轮次**。

Anthropic 在 [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 里把这一条点得很明确：

> “One of the most common failure modes we see is **bloated tool sets** that cover too much
> functionality or lead to ambiguous decision points about which tool to use.
> If a human engineer can't definitively say which tool should be used in a given situation,
> an AI agent can't be expected to do better.”

这与我此前在工具幻觉调研里的结论是同一条：**工具数超过 ~20–30 后，选择准确率开始下降，需要引入检索**。
而这里补上另一半代价：**工具 schema 的 token 成本是每轮重复支付的**。

### 取舍

| 做法 | 收益 | 代价 |
| :--- | :--- | :--- |
| 全量传 24 个 | 简单、选择空间完整 | 每轮固定 token；选择准确率下降 |
| 按需检索工具（tool RAG） | token 省、准确率高 | 引入“召回失败”这一新错误源 |
| 削减工具（合并/裁剪 description） | 直接省 | 能力变弱 |

**本项目的判断**：24 个仍在舒适区，暂时不要引入工具检索；但**description 可以压缩**——
`search_knowledge` 的 description 已经很长（[`tools_schema.py:418-429`](../../backend/core/tools/tools_schema.py#L418-L429)），
它每轮都在付费。这类“给模型看的说明”值得做一次 token 审计。

## 4. 策略三：工具结果截断（L1 内最大的 token 黑洞）

JetBrains 的实测数据（[The Complexity Trap](https://ar5iv.labs.arxiv.org/html/2508.21433)）：
**工具输出约占一个典型 turn 的 84%**。在你们的场景里同样成立——`search_knowledge`
一次返回 3~5 条证据 + 可能附加 parent 全文，很容易上千 token。

### 与 L2 的观察掩码的区别

| | 作用时机 | 目的 |
| :--- | :--- | :--- |
| **L1 截断** | 本次请求**刚拿到结果时** | 别让这一条就把窗口撑爆 |
| **L2 掩码** | 结果**变成历史之后** | 别让旧结果一直占着窗口 |

两者是互补的，**都要做，但顺序上先做 L1 截断**——因为 L1 不需要任何跨轮状态。

### 截断的几种做法

| 做法 | 说明 | 适用 |
| :--- | :--- | :--- |
| **头尾保留**（head/tail） | 留前 N 行 + 后 M 行，中间省略 | 日志、长列表 |
| **字段裁剪** | 只保留模型要用的字段，丢掉元数据/内部 ID | 结构化返回（**本项目主要适用**） |
| **结构化摘要** | 只回“共 N 条，前 3 条是…” | 检索结果 |
| **外置 + 引用** | 结果存文件/DB，只在上下文里放引用（path/id） | just-in-time 模式 |

`just-in-time` 是 Anthropic 明确推荐的路子：

> “agents built with the ‘just in time’ approach maintain **lightweight identifiers**
> (file paths, stored queries, web links) and use these references to dynamically load
> data into context at runtime using tools.”

**对本项目的映射**：`search_knowledge` 返回的证据片段其实已经做过裁剪（只回片段不回全文），
这一点做对了。但 `include_parent=True` 时会附上整节全文——这是**唯一可能爆量的口子**，
建议加一个硬上限（当前 schema 描述里写了“体积较大”，但没写成代码约束）。

## 5. 策略四：`tool_calls` 与 `tool` 消息必须配对

这是**协议级硬约束**，不满足直接 400：

- `assistant` 消息里的每个 `tool_calls[i].id`，**必须**有一条对应的 `role="tool"`、
  `tool_call_id` 相同的消息；
- 数量对不上、id 对不上，请求直接被拒。

这条在工具幻觉加固里已经踩过一次（[`agent.py:120-129`](../../backend/core/agent/agent.py#L120-L129)
的“重复调用跳过时仍要回填 tool 消息”就是为它）。**但它在 L2 会成为主要矛盾**：
你们的 `messages` 表为了 UI 折叠，把工具结果内嵌在 `assistant.tool_calls` 里，
回放时必须展开。详见 [02-L2](02-L2-单会话上下文.md) 第 8 节。

## 6. 策略五：思考内容（`reasoning_content`）要不要回传

本项目的请求带了：

```python
reasoning_effort="high",
extra_body={"thinking": {"type": "enabled"}}
```

流式响应里的 `delta.reasoning_content` 当前被**转发给前端但不进 `messages`**
（[`agent.py:70-72`](../../backend/core/agent/agent.py#L70-L72)）。

**这是合理的默认**，理由：

- 思考内容通常不参与后续轮次的推理（多数厂商不建议回传，回传还会占 token）；
- 但**在某些多步工具场景下**，模型需要知道“上一轮我为什么选了这个工具”，
  这时丢失思考链会导致重复探索。

| 策略 | token 成本 | 连续性 |
| :--- | :--- | :--- |
| 不回传（当前） | 最省 | 工具多步时可能重复探索 |
| 回传完整 | 最贵，且模型可能“复读”思考 | 最好 |
| **回传摘要**（“上轮打算 X，因为 Y”） | 折中 | 较好 |

建议：**先保持不回传**，等 L2 的掩码/摘要机制建好后，在需要时用“一句式计划摘要”补偿。

## 7. 策略六：预算分配

把窗口当固定预算来分配，而不是“能塞就塞”。一个可用的起点：

| 段 | 预算占比 | 说明 |
| :--- | :--- | :--- |
| system + tools | 固定 | 实际测量后写死，不参与动态分配 |
| 历史（L2 供给） | ≤ 40% | 超出就触发 L2 的裁剪 |
| 本轮工具往返 | ≤ 30% | 超出就在 L1 截断 |
| 预留输出 | ≥ 15% | **必须留**，否则模型无法作答 |
| 安全余量 | ~10% | 应对估算误差 |

**关键洞察**：**compaction 本身也要花 token**（要调一次摘要模型），所以不能等“满了才压缩”——
必须留出压缩所需的余量。这是很多实现翻车的地方（详见 L2 §6）。

## 8. 度量

| 指标 | 算法 | 健康区间 |
| :--- | :--- | :--- |
| 缓存命中率 | `cache_read / (cache_read + cache_creation + input)` | **> 0.8**（稳态） |
| 每轮 input tokens | 直接读 `usage` | 与话题长度相关，应**趋于平稳**而非单调上升 |
| 工具输出占比 | 工具消息 token / 总 input token | 参考值 ~84%（JetBrains），低于它说明截断有效 |
| 截断触发率 | 触发截断的调用 / 总工具调用 | 过高说明工具返回本身就太胖 |

## 9. 反模式

| 反模式 | 后果 |
| :--- | :--- |
| 在 system prompt 里插时间戳/用户名 | 缓存天天空转，还查不出原因 |
| 缓存断点打在最后一条 user 消息 | 每轮付写溢价、读取为 0，比不缓存更贵 |
| 工具 schema 序列化不稳定（dict 顺序） | 每轮 miss，静默 |
| 假设“中转会透传缓存字段” | 配了等于没配，且没有报错 |
| 不预留输出 token | 模型答到一半被截断 |
| 工具结果不截断就塞进 messages | 一次大返回就把窗口吃掉，后续全在挤 |
