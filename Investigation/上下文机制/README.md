# 上下文管理机制 · 调研

> **调研对象**：LLM Agent 的上下文（context）如何被组织、裁剪、压缩与跨会话复用。
> **分层依据**：按**作用域**分三层（L1 单次调用 / L2 单会话 / L3 跨会话）。
> 每层的核心问题、失效模式、实现位置都不同，不能用同一套机制硬套。
> **调研时间**：2026-10-16
> **落地对象**：本仓库 `backend/core`（`agent.py` 的工具循环、`services/conversations.py` 的历史存储）
>
> **范围说明**：本项目当前**只针对单用户**，因此不涉及多租户隔离这一层
> （原 L4 调研已移除，见文末说明）。

## 为什么按作用域分层

“上下文管理”这个词被用得很泛，但不同人指的是完全不同的东西：

- 有人指 **“这次请求塞什么进 messages”**（L1）；
- 有人指 **“聊了 50 轮怎么还记得开头”**（L2）；
- 有人指 **“换个会话还认识我”**（L3）。

这三层的**触发条件、失效模式、度量指标、实现位置**全都不同。混着谈就会得出
“用摘要解决一切”这类错误结论。

## 三层总览

| 层 | 作用域 | 核心问题 | 主导策略 | 本项目现状 |
| :--- | :--- | :--- | :--- | :--- |
| **L1** | 单次模型调用 | 这一次的 `messages` 怎么排、塞多少 | 稳定前缀（缓存友好）、工具结果截断、预算分配 | ⚠️ 有基本组装，**无预算、无截断、无缓存意识** |
| **L2** | 单会话（多轮） | 历史变长后怎么不失忆、不退化 | 观察掩码 → 滑动窗口 → compaction/摘要 | ✅ **已实现**：掩码 + 窗口 + 压缩（`agent/context.py` / `agent/compaction.py`） |
| **L3** | 跨会话（用户级） | 换个会话还认不认得这个人 | 结构化事实 / 记忆抽取+检索 / 时序知识图 | ⚠️ **半个**（`get_financial_profile` 工具，非上下文机制） |

## 四条关键结论

### 1. “上下文越长越好”是错的，这有系统实证

Chroma 的 **Context Rot** 报告测了 18 个模型（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3），
在**刻意保持任务难度不变、只拉长输入**的条件下，性能依然**非均匀退化**。三个具体发现：

- **信噪比越低退化越快**：needle-question 语义相似度低的样本，随长度增长退化更明显；
- **单个干扰项就掉分**，4 个更糟，且不同干扰项影响不等；
- **反直觉**：语料**结构连贯**时模型表现比**打乱顺序**更差。

最狠的一组对比来自 LongMemEval：**只给相关片段（约 300 tokens）显著优于给全量 113k tokens**。

> 结论不是“窗口不够大”，而是：**“取相关”远优于“全塞”**。这直接支持 L2 的检索式/压缩式路线，
> 而不是“等大窗口就行”。

### 2. 在工具型 Agent 里，上下文的主要体积不是对话，是工具输出

JetBrains 的 **The Complexity Trap**（SWE-bench Verified，5 种模型配置）测出一个关键比例：
**环境观察（工具输出）约占一个典型 turn 的 84%**。

这解释了为什么“观察掩码”（把旧工具输出替换成占位符）这么有效：

| 策略 | 成本 | solve rate |
| :--- | :--- | :--- |
| 无管理（raw） | 基准 | 基准 |
| **观察掩码** | **−50% ~ −57%** | 持平或**略升** |
| LLM 摘要 | −41% ~ −55% | 持平或**下降** |

Qwen3-Coder 480B 上：掩码把 solve rate 从 53.4% 提到 **54.8%（+2.6%）**，同时成本 **−52.7%**。
而在 Gemini 2.5 Flash（thinking）上，**LLM 摘要反而把 solve rate 从 40.4% 打到 31.4%（−22.3%）**。

> 结论：**先做最轻的掩码，不要一上来就上 LLM 摘要。** 摘要会引入延迟、成本、以及“摘要失真”
> 这一新故障源，而收益未必为正。

### 3. 摘要的关键不是“压多少”，是“留什么”，而且必须先保 recall

Anthropic 的实践建议很具体：

- 摘要**先最大化 recall**（把该留的都留住），再迭代提 precision（删冗余）；
- 必须保留：**目标与约束、已确认事实、决策与理由、未解决的问题**；
- 优先丢弃：**冗余的工具输出与重复探索**；
- Claude Code 的做法：压缩后**额外保留最近访问的 5 个文件**；
- **工具结果清理（tool result clearing）是最安全、最轻触的 compaction 形式**。

还有一个容易被忽略的点：**原始用户目标不应该进入摘要**——它应该被**锚定**在摘要之外，
否则多层摘要后目标会漂移，这是“聊着聊着忘了最初要干嘛”的技术根因。

### 4. L3 不是 L2 的延伸，是另一套机制（而且通常是结构化的）

三个代表性系统的定位完全不同：

| 系统 | 形态 | 关键设计 | 实证 |
| :--- | :--- | :--- | :--- |
| **MemGPT / Letta** | OS 式分层记忆 | core / archival / recall 三层；模型**自己编辑记忆**；interrupts 控制流 | 长文档分析 + 多会话聊天 |
| **Mem0** | 抽取 + 合并 + 检索 | 从对话中抽事实、去重合并、按需检索；可选图记忆 | LOCOMO 上比 OpenAI 记忆相对 **+26%**，p95 延迟 **−91%**，token 成本 **−90%** |
| **Zep / Graphiti** | 时序知识图 | 双时态（事件时间 + 摄入时间），边带有效期 | DMR **94.8% vs MemGPT 93.4%**；LongMemEval 最高 **+18.5%**，延迟 **−90%** |

**对本项目的判断**：你们的用户事实（收入、资产、负债、目标）**本来就是结构化存在 SQLite 里**，
比 Mem0/Zep 那套“从自由对话里抽事实”要可靠得多。所以 L3 的正确路线是
**“结构化事实优先 + 必要时检索回填”**，而不是引入记忆抽取管线。

## 两个必须先补的前置件

在动任何 L2 策略之前，有两件结构性的事必须先解决——它们本身不是“上下文管理”，
但**没有它们，L2 做不完整甚至做不了**：

| # | 前置件 | 一句话说明 | 详见 |
| :-- | :--- | :--- | :--- |
| **①** | **历史回放展开器** | UI 形态的历史（工具结果内嵌在 `assistant.tool_calls`）必须展开成 OpenAI 协议形态（`assistant(tool_calls)` + 逐条 `tool`），且这层逻辑**应当从客户端移到服务端** | [06 §1](06-前置件详解.md) |
| **②** | **`/api/chat` 接入 `conversation_id`** | 现在历史由前端传，后端不知道会话边界 → 无预算、无法触发裁剪、且历史是**客户端可控输入** | [06 §2](06-前置件详解.md) |

> 这两件被单独写进 [06-前置件详解.md](06-前置件详解.md)，因为各自都有**必须先想清楚的边界情况**
> （断流、并发、重试、缺 result 的 tool 调用……），不是“顺手加个函数/字段”。

## 一句话提醒

**上下文管理不是一个功能，是一条贯穿三层作用域的约束。**
L1 决定“这一次花了多少钱、注意力集不集中”，L2 决定“长会话还能不能用”，
L3 决定“跨会话还有没有连续感”。

任何一层缺失，都会以**别的地方的症状**表现出来——比如 L2 缺失时最常见的表现
不是“报错”，而是“模型突然忘了三分钟前说过的话”。
