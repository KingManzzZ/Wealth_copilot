# L2 · 单会话上下文（重点）

> **作用域**：一个 conversation 内的多轮对话。
> **边界**是会话（A 会话的裁剪不能影响 B 会话），**作用点**是每一次模型调用
> （LLM 无状态，每轮都要重新组装 messages）。
> **核心问题**：轮次变多后，怎么让模型**既不失忆、又不退化**。
> **产出指标**：每轮 input tokens（应趋稳而非单调上升）、早期信息保留率、任务成功率、成本/次。

这是本次调研的重点，也是绝大多数工具型 Agent 真正卡住的地方。

---

## 1. 为什么“作用点在每次调用”

很多人把“会话上下文”想成一个持续存在的对象。但 LLM 是无状态的：

```
第 1 轮：POST messages=[sys, u1]                          → a1
第 2 轮：POST messages=[sys, u1, a1, u2]                  → a2
第 3 轮：POST messages=[sys, u1, a1, u2, a2, u3]          → a3
         ……每轮把全部历史重发一遍
```

所以 L2 的“上下文管理”本质是：**每一轮组装请求时，做一次“取多少历史、怎么压”的决策**。
唯一需要**持久化**的东西是**摘要**（否则每轮重摘既贵又不一致）。

推论：**L2 的实现位置一定在“组装 messages 的那一层”**，而不是在存储层。
存储层只负责“原始历史完整保留”（供审计与重新摘要），裁剪发生在**读取组装时**。

---

## 2. 为什么必须做：Context Rot 的实证

### 2.1 核心结论

Chroma 的 [Context Rot](https://www.trychroma.com/research/context-rot)（2025-07）测了 **18 个模型**，
包括 GPT-4.1、Claude 4、Gemini 2.5、Qwen3。实验设计的关键是
**刻意保持任务难度不变、只改变输入长度**，从而隔离“长度”这一个变量。

结论：**模型并不均匀地使用上下文，输入越长性能越不可靠。**

传统 Needle-in-a-Haystack（NIAH）为什么没发现？因为它是**纯词法检索**，
而真实任务需要**语义匹配、抗干扰、多步推理**。

### 2.2 四个具体发现

| 发现 | 细节 | 对 L2 的含义 |
| :--- | :--- | :--- |
| **信噪比决定退化速度** | needle-question 相似度低的样本，随长度增长退化更快 | 不是“塞进去就能用”，**低相关的内容比没内容更有害** |
| **干扰项影响巨大且不均** | 单个 distractor 就掉分，4 个更糟；不同 distractor 危害不同 | “看起来相关但答不了问题”的历史轮次是最坏的噪声 |
| **反直觉：结构连贯的语料更差** | 打乱顺序反而优于保持逻辑流 | 不要指望“历史天然有序”会帮上忙 |
| **位置效应** | 复述任务中，独特词出现在**开头**时准确率最高 | 早期目标/约束应放前面，而不是指望它“还在窗口里” |

### 2.3 最有力的一组对比：LongMemEval

Chroma 用 LongMemEval 做了个直接对应 L2 的实验：

- **Full input**：把**完整** 113k tokens 的对话历史全给模型；
- **Focused input**：只给**相关片段**，平均约 **300 tokens**。

结果是**所有模型族（Claude / GPT / Gemini / Qwen）在 focused 上显著优于 full**。

原因写得很清楚：

> 全量输入要求模型**同时做两件事**——先从长历史里检索出相关部分，再推理；
> 而 focused 输入把检索这一步省掉了，模型只需推理。

**这就是 L2 一切策略的共同目标：把“检索”从模型的工作里拿走，交给系统。**

### 2.4 一个副作用值得注意

同一份报告还发现：**Claude 在歧义下倾向于“我不确定，找不到”**，
而 **GPT 系倾向于“自信地编一个”**。这意味着：

> 上下文管理做得差时，不同模型的**失败方式不同**——一个是不说话，一个是说错话。
> 后者更危险，因为它不报警。

## 3. 策略光谱：从最轻到最重

九种主流做法，按“信息损失 × 实施成本”排序：

| # | 策略 | 做法 | 成本 | 信息损失 | 实施难度 |
| :-- | :--- | :--- | :--- | :--- | :--- |
| 1 | **无管理（raw）** | 全量保留 | 最高（成本翻倍以上） | 无 | 零 |
| 2 | **工具结果清理 / 观察掩码** | 旧工具输出 → 占位符 | **极低** | 中（丢细节、留结构） | **低** |
| 3 | **滑动窗口** | 只保留最近 N 轮 | 低 | 高（丢早期目标） | 低 |
| 4 | **Compaction / 递归摘要** | 接近上限时摘要 + 重开 | 中（要调摘要模型） | 中 | 中 |
| 5 | **分层摘要** | 轮次摘要 → 会话摘要 | 中高 | 中 | 高 |
| 6 | **结构化笔记** | 外部 NOTES / todo 文件 | 低（少量写） | 低 | 中 |
| 7 | **子代理隔离** | 子 agent 用干净窗口，只回摘要 | 中 | 高（细节不回传） | 高 |
| 8 | **历史检索（RAG over history）** | 历史向量化，按需取 | 中 | 取决于召回质量 | 高 |
| 9 | **Just-in-time 引用** | 只存标识符，运行时再取 | 低 | 基本无（但要再取一次） | 中 |

下面逐个展开。

---

### 3.1 策略 2 · 工具结果清理 / 观察掩码（**建议最先做**）

**做法**：保留完整的推理链与动作历史，只把**旧**的工具输出替换成占位符。

```
原始：  [sys, u1, a1(tool_call), tool(15,000 tokens 的检索结果), a2, u2, ...]
掩码后：[sys, u1, a1(tool_call), tool("[较早的 15,000 字符输出已省略]"), a2, u2, ...]
```

形式上（来自 JetBrains 论文的 Eq. 4）：给定窗口大小 `M`，
对第 `i` 个 turn 的观察 `o_i`：

```
o'_i = placeholder    if i < t − M
       o_i            if i ≥ t − M
```

**为什么它特别有效**：因为上下文体积的大头不是对话，是工具输出。
JetBrains 实测 **观察 token 约占一个典型 turn 的 84%**。

**Anthropic 的独立佐证**：他们把 tool result clearing 称为
**“最安全、最轻触的 compaction 形式”**：

> “One of the safest lightest touch forms of compaction is **tool result clearing** —
> once a tool has been called deep in the message history, why would the agent need
> to see the raw result again?”

**关键设计点**：掩码的是**输出**，不是**动作**。
模型仍然能看到“我在第 3 步调用了 `search_knowledge`，query 是 X”，只是看不到那 15k 的原文。
这保住了“我做过什么”的连续性，只丢掉了“当时返回了什么细节”。

---

### 3.2 策略 3 · 滑动窗口

**做法**：只保留最近 N 轮（或最近 N tokens），更早的直接丢。

**优点**：极简、无额外模型调用、成本可预测。

**致命缺点**：**丢掉的是最早的东西，而最早的往往是最重要的**——
用户最初的目标、约束、已经确认过的事实。

**改进**：不要纯截断，至少配合“锚点保留”：

```
[system]
[锚定的原始目标与约束]   ← 从第 1 轮抽取，永不参与滚动
[最近 N 轮原文]
[当前输入]
```

这是最小成本的“不失忆”版本。

---

### 3.3 策略 4 · Compaction / 递归摘要

**做法**（Anthropic 的定义）：对话接近窗口上限时，把它**摘要压缩**，然后用摘要**重新开一个窗口**。

> “Compaction distills the contents of a context window in a high-fidelity manner,
> enabling the agent to continue with minimal performance degradation.”

**工业界的具体参数**：

| 系统 | 保留策略 |
| :--- | :--- |
| **Claude Code** | 摘要 + 额外保留**最近访问的 5 个文件** |
| **Claude 平台** | 支持三种触发：**阈值触发** / **按需触发** / **后台压缩**；可配置 `keep recent turns` |
| **JetBrains 实验设置** | 一次摘要 **21 轮**，尾部保留 **10 轮原文**（`N=21, M=10`） |
| **OpenHands** | 滚动摘要 + 保留少量最近 turn |

Claude Code 的官方描述（[agent loop 文档](https://code.claude.com/docs/en/agent-sdk/agent-loop)）：

> “When the context window approaches its limit, the SDK **automatically compacts the conversation**:
> it summarizes older history to free up space.”

**注意“recursive”这个词**：摘要会**再次**成为被摘要的输入，这就是策略 5 的问题来源。

---

### 3.4 策略 5 · 分层摘要

**做法**：多级结构，例如

```
会话级摘要（每 ~20 轮更新一次）
  ├─ 轮次摘要 1（第 1-10 轮）
  ├─ 轮次摘要 2（第 11-20 轮）
  └─ 最近 N 轮原文
```

**收益**：可以只把“最相关的几段摘要”放进上下文，而不是全部。

**代价与风险**：

- **摘要的摘要会漂移**：每一层压缩都丢一次细节，几层之后可能完全变形；
- **成本更高**：要多次调用摘要模型；
- **调试困难**：出问题时很难定位是哪一层摘要丢的信息。

**缓解手段**：锚定（见 §6.3）—— 原始目标与硬约束永远不进入摘要链，而是独立保留。

---

### 3.5 策略 6 · 结构化笔记 / Agentic memory

**做法**：Agent 主动把关键状态写到**上下文之外**（文件、DB），后续再读回来。

Anthropic 的描述：

> “**Structured note-taking**, or agentic memory, is a technique where the agent regularly
> writes notes persisted to memory outside of the context window. These notes get pulled
> back into the context window at later times.”

典型形态：

- Claude Code 的 **todo list**；
- 自定义 Agent 的 `NOTES.md`；
- 官方发布的 **memory tool**（文件系统形态，公开 beta）。

**为什么这招在长任务里不可替代**：它是**唯一能跨 compaction 存活**的机制。
摘要会丢细节，但笔记是原文级别的持久化。

**对本项目的映射**：你们的「财务规划闭环」（理解现状 → 定目标 → 执行 → 复盘 → 调整）
天然适合笔记形态——**目标、已确认事实、待办**这三类恰好是需要跨轮稳定存在的东西。

---

### 3.6 策略 7 · 子代理隔离

**做法**：主 Agent 只保留高层计划，把“重度探索”交给子 agent；子 agent 有**自己干净的窗口**，
只把**压缩后的结论**回传给主 Agent。

Anthropic 给出的量级：子 agent 可能烧掉数万 token 探索，但**只回传 1,000–2,000 token 的摘要**。

**收益**：主 Agent 的上下文几乎不增长，且“污染的细节”被隔离在子代理里。

**代价**：架构复杂度陡增；子代理的摘要本身也可能丢关键信息；调试链路变长。

**适用判断**：任务可以**并行分解**（研究、多文件分析）时才值得。
你们的场景（单用户、单对话、结构化数据查询）暂时不适用。

---

### 3.7 策略 8 · 历史检索（RAG over history）

**做法**：把历史轮次切块、向量化，按当前 query 检索最相关的 K 段注入。

这正是 LongMemEval 里 “focused input” 的工业化实现——**把检索从模型手里拿走**。

**优点**：理论上可以保留任意久的历史，且上下文恒定。

**缺点**：

- 引入**召回失败**这一新错误源（检索不到 = 凭空失忆，且模型不知道自己漏了什么）；
- 对“全局摘要类”问题（“我们一共聊过几个目标？”）很不友好；
- 需要额外存储与索引。

**建议**：L2 的早期**不要**上它。它更适合作为 L3（跨会话）或超长会话的兜底。

---

### 3.8 策略 9 · Just-in-time 引用

**做法**：不在上下文里放内容，只放**标识符**（文件路径、记录 ID、查询语句），
需要时用工具再取。

这是 Anthropic 明确推荐的方向：

> “maintain **lightweight identifiers** (file paths, stored queries, web links, etc.)
> and use these references to dynamically load data into context at runtime using tools.”

**对本项目的映射很自然**：你们的财务数据本来就存在 SQLite 里，**工具就是“按需取”的通道**。
所以“把用户画像塞进 prompt”其实是不必要的——`get_financial_profile` 已经是更好的形态。

**代价**：多一次工具调用（多一轮延迟）；依赖模型“知道该去取”。

## 4. 实证对决：掩码 vs 摘要 vs 裸奔

这是本次调研**最有决策价值**的一组数据。JetBrains 在 SWE-agent + SWE-bench Verified 上，
对 5 种模型配置做了同尺度对比（[The Complexity Trap](https://ar5iv.labs.arxiv.org/html/2508.21433)）：

| 模型 | 策略 | Solve Rate (%) | 单实例成本 ($) |
| :--- | :--- | :--- | :--- |
| Qwen3-32B | Raw | 17.0 ±3.3 | 1.12 ±0.18 |
| | 掩码 | 15.0 (−11.8%) | **0.55 (−50.9%)†** |
| | 摘要 | 16.0 (−5.9%) | 0.50 (−55.4%)† |
| Qwen3-32B (thinking) | Raw | 23.0 ±3.7 | 0.51 ±0.07 |
| | 掩码 | **24.6 (+7.0%)** | 0.46 (−9.8%) |
| | 摘要 | 24.8 (+7.3%) | 0.51 (0.0%) |
| Qwen3-Coder 480B | Raw | 53.4 ±4.3 | 1.29 ±0.26 |
| | **掩码** | **54.8 (+2.6%)** | **0.61 (−52.7%)†** |
| | 摘要 | 53.8 (+0.7%) | 0.64 (−50.4%)† |
| Gemini 2.5 Flash | Raw | 32.8 ±4.1 | 0.41 ±0.08 |
| | 掩码 | 35.6 (+8.5%) | **0.18 (−56.1%)†** |
| | 摘要 | **36.0 (+9.8%)** | 0.24 (−41.5%)† |
| Gemini 2.5 Flash (thinking) | Raw | **40.4 ±4.3** | 0.56 ±0.10 |
| | 掩码 | 36.4 (−9.9%)† | **0.24 (−57.1%)†** |
| | 摘要 | **31.4 (−22.3%)†** | 0.25 (−55.4%)† |

### 三个可操作的结论

**① 做任何管理都比不管好。** 5 个配置里，两种策略都大幅降本，多数情况下降幅 > 50%。
裸奔的代价是**成本翻倍以上**，而且“更多上下文”在 3/5 的配置里**反而降低了 solve rate**。

**② 掩码在 4/5 的配置里是最便宜的**，且 solve rate 与摘要持平、有时更好。
Qwen3-Coder 480B 上掩码比摘要**又便宜 $0.03/实例**（500 个实例省 $15）。

**③ 摘要有反例**：Gemini 2.5 Flash（thinking）上，摘要把 solve rate 从 40.4% 打到 **31.4%（−22.3%）**，
掩码也降了 9.9%。论文的说法是“至少在这个范围内，最有效也最高效的上下文管理可以是最简单的”。

### 所以推荐顺序

```
1. 先做观察掩码（成本极低、无额外模型调用、几乎不会更差）
2. 再加滑动窗口 + 锚点保留（解决"掩码不解决无限增长"的问题）
3. 最后才考虑 compaction/LLM 摘要（需要 A/B 验证，且有反例）
```

**不要**跳过 1 直接上 3 —— 那是把最简单稳妥的收益换成了最复杂有风险的东西。

## 5. 触发时机

三种主流触发方式（Claude 平台把这三者都做成了独立能力）：

| 方式 | 触发条件 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **阈值触发**（threshold） | 达到窗口的 X%（如 70~80%）自动压缩 | 无需人工干预 | 压缩时机可能不好（正忙着解题时被打断） |
| **按需触发**（on demand） | 用户/开发者显式请求 | 可控 | 需要人判断 |
| **后台触发**（background） | 异步压缩，不阻塞当前轮 | 不打断对话 | 实现复杂、要处理竞态 |

**关键约束：必须留出压缩本身的预算。**

压缩要调一次摘要模型，那次调用**也要吃 token**。所以触发阈值不能设成 95%——
设成 70~80%，留出余量做压缩，也留出余量给模型作答。

**第二个约束：不要在工具循环中间压缩。**

如果模型正在多步工具推理中（已经调了 2 个工具、正要调第 3 个），此时压缩会把
“我刚才查到了什么”抹掉，直接毁掉这一轮。**压缩只应在轮次边界发生。**

## 6. 摘要怎么写才不会写坏

这是 L2 里最容易做错、且失败最隐蔽的部分。Anthropic 给了一条非常实用的工程建议：

> “We recommend carefully tuning your prompt on complex agent traces.
> Start by **maximizing recall** to ensure your compaction prompt captures every relevant
> piece of information from the trace, then iterate to improve **precision** by eliminating
> superfluous content.”

即：**先求全，再求精**。反过来（先精简）会不知不觉丢关键信息，而且很难发现。

### 6.1 必须保留的四类

| 类别 | 例子 | 为什么不能丢 |
| :--- | :--- | :--- |
| **目标与约束** | “想 5 年内攒够 50 万首付”“不考虑股票” | 丢了就会给出方向错误的建议 |
| **已确认的事实** | “月收入 3 万”“有 80 万房贷” | 丢了会重复询问，体验极差 |
| **决策与理由** | “选了方案 B，因为 A 风险太高” | 丢了会重复讨论同一件事 |
| **未解决的问题** | “还差一个税率数据没查” | 丢了任务就静默中断 |

### 6.2 优先丢弃的三类

| 类别 | 例子 |
| :--- | :--- |
| **冗余的工具输出** | 15k 的检索原文（保留“查过什么”即可） |
| **重复的探索** | 同一工具试了 5 次不同参数的失败记录 |
| **客套与元对话** | “好的”“明白了”“让我想想” |

注意“失败的尝试”**不能无脑丢**：模型需要知道“这条路试过了、不通”，否则会重试。
建议保留为一句摘要：“试过 X、Y 两种方式，都因 Z 失败”。

### 6.3 锚定：原始目标不参与摘要

**这是防漂移的关键设计。**

多层递归摘要后，早期的目标会被反复压缩、逐渐变形。解决办法是把**原始目标与硬约束**
从摘要链里**拿出来**，作为独立字段永久保留：

```
[messages]
  system: ...
  user:   【会话目标（锚定，原文）】想 5 年内攒够 50 万首付，不接受高风险产品
  ...
  assistant: 【历史摘要】前 20 轮：梳理了收支，确认月结余 1.2 万，讨论过 3 种方案...
  ...（最近 N 轮原文）
  user:   【本轮】那如果我提前还贷呢
```

Anthropic 在别处也强调了同一件事：**目标与约束是“必须保留”的那一档**。

### 6.4 递归摘要的漂移

必须意识到：**摘要的摘要是不可逆的有损压缩**。

| 轮次 | 内容 |
| :--- | :--- |
| 原始 | 200 轮，约 400k tokens |
| 第一次摘要 | 约 2k tokens（丢了 99.5%） |
| 第二次摘要 | 约 2k tokens（又基于已损内容压缩） |
| 第 N 次 | 可能只剩“大概在聊理财” |

**缓解**：

- 摘要**基于原文**重算，而不是在旧摘要上叠（代价是 token，但保真）；
- 或分层保留：旧摘要不删，只是不再放进上下文（存档，必要时回取）；
- 锚定字段独立于摘要链。

### 6.5 摘要提示词的最小结构

```
请把以下对话压缩为结构化摘要，用于后续推理。必须保留：
1. 用户的原始目标与所有约束（逐条列出，不要概括）
2. 已确认的事实与数值（保持精确，不要取整）
3. 做过的决策及其理由
4. 未解决的问题 / 待办
5. 试过但失败的路径（各一句）
可丢弃：冗长的工具返回原文、重复的寒暄。
输出用 Markdown，分节。
```

## 7. 保真度与可复现

摘要是**有损且不确定**的操作。同一段历史，两次摘要的结果可能不同，任务结果也可能不同。

**必须做的记录**（否则线上出问题无法归因）：

| 记录项 | 用途 |
| :--- | :--- |
| 压缩发生的轮次 | 定位“从哪一轮开始变笨” |
| 压缩前的 token 数 | 判断是否为窗口压力所致 |
| 压缩前后的完整内容 | 可回放、可对比 |
| 使用的摘要提示词版本 | 提示词一改，行为就变 |

**建议**：把每次 compaction 的 `{轮次, 前摘要, 后摘要, prompt_version}` 落一张表。
这和我此前在工具幻觉调研里强调的“埋点”是同一个道理——**没有记录就没有优化**。

## 8. 本项目专属坑：tool 中间态回放

你们的 `messages` 表是**为 UI 折叠设计的，不是为模型回放设计的**：

- 只允许 `user` / `assistant` 两种角色
  （[`conversations.py:109`](../../backend/core/services/conversations.py#L109)：
  *“tool 中间态已内嵌在 `assistant.tool_calls`”*）；
- 工具结果、状态全部塞在 `assistant.tool_calls` 这个 JSON 列里
  （[`conversations.py:115-116`](../../backend/core/services/conversations.py#L115-L116)）。

**如果直接把 DB 行映射成 `messages` 发给模型，会缺 `role="tool"` 消息**：

```
DB:   assistant(content="我查一下", tool_calls=[{id: "call_1", name: "get_assets", result: {...}}])
直接映射 → messages 里只有 assistant(tool_calls)，没有 tool 应答
→ OpenAI 协议报 400（tool_calls 里的 id 找不到对应的 tool 消息）
```

**必须有一层「回放展开器」**：

```
DB 一行 assistant(tool_calls)
   ↓ 展开
assistant(tool_calls=[{id: "call_1", ...}])
tool(tool_call_id="call_1", content="<result 的 JSON 序列化>")
   ↓ 每个 tool_call 一条 tool 消息
```

这是 L2 的**前置件**，无论你选哪种裁剪策略都绕不开。
而且它和工具幻觉加固里那条“重复调用跳过时仍要回填 tool 消息”是**同一条协议规则**
（见 [问题文档/Agent-工具调用可靠性.md §T2-1](../../问题文档/Agent-工具调用可靠性.md)）。

**顺带的好处**：有了展开器，`messages` 表就能继续服务 UI 折叠，
而模型侧拿到的是标准协议形态——**两种用途各自最优，不必二选一**。

## 9. 度量

L2 的效果不能只看“成本降了”，要看“有没有变笨”。

| 指标 | 算法 | 期望方向 |
| :--- | :--- | :--- |
| **每轮 input tokens** | `usage` | **趋稳**。若单调上升，说明裁剪没生效 |
| **压缩次数 / 会话** | 埋点 | 与轮次比值，过高说明裁剪太轻 |
| **早期信息保留率** | 固定 probe 集：会话第 1 轮给一个约束，第 30 轮问它 | 应保持高位 |
| **任务成功率** | 端到端 | **不能下降**（这是底线） |
| **成本 / 会话** | 累计 token × 单价 | 下降 |
| **重复询问率** | 模型问“你的收入是多少”的次数（已知却再问） | 应下降 |

### 建议做一个「遗忘探针」回归集

固定 5~10 条长会话，每条在第 1~3 轮埋一个**关键约束**（如“不接受股票类产品”），
然后在第 30+ 轮问一个只有记住该约束才能答对的问题。

```
Q1: 我想 5 年攒 50 万，不接受高风险产品
...（20 轮无关对话 + 工作流操作）
Q21: 这个方案里配 30% 股票基金行吗？
期望: 拒绝并引用最初约束"不接受高风险产品"
```

**没有这个探针，你无法知道裁剪有没有伤到记忆。** 这是 L2 最值得先建的基础设施。

## 10. 反模式

| # | 反模式 | 后果 |
| :-- | :--- | :--- |
| 1 | **只按轮数硬截断** | 丢掉第 1 轮的目标与约束 → “聊着聊着就忘了要干嘛” |
| 2 | **等窗口满了才压缩** | 没有余量做压缩本身；且模型已在退化区工作 |
| 3 | **摘要在工具循环中间触发** | 抹掉“刚查到什么”，直接毁掉当前推理 |
| 4 | **摘要不带原始目标** | 递归压缩后目标漂移，子摘要与真实意图脱节 |
| 5 | **一上来就上 LLM 摘要** | 成本高、可更差（Gemini thinking 上 −22.3%）、且引入新故障源；而掩码几乎免费 |
| 6 | **摘要后不留记录** | 线上“变笨”无法归因，不可复现 |
| 7 | **只压 token 不测记忆** | 成本降了、任务成功率暗降，且**没有报警** |
| 8 | **在旧摘要上反复叠加摘要** | 不可逆的漂移，几轮后只剩“大概在聊理财” |
| 9 | **把检索当万能** | 召回失败 = 静默失忆，模型不知道自己漏了什么 |
| 10 | **直接回放 UI 形态的历史** | 缺 `tool` 消息 → API 400 |

## 11. 决策清单（怎么选）

给一个可直接照做的判断流程：

```
① 会话平均轮次 < 10 且工具输出不胖？
   → 先什么都别做，但把"每轮 input tokens"埋上点，观察趋势。

② 工具输出是体积大头（几乎总是）？
   → 做「观察掩码」。这是唯一"几乎不会更差"的策略。
   → 同时做 L1 的工具结果字段裁剪。

③ 掩码后 token 仍在单调上升？
   → 加「滑动窗口 + 锚点保留」（锚定原始目标，永不滚动）。

④ 单会话经常 > 50 轮 / 触及窗口上限？
   → 上「compaction + 摘要」。但必须先做 A/B：
     对比"掩码+窗口"与"掩码+窗口+摘要"的成功率与成本。
   → 摘要提示词按「先 recall 后 precision」调。

⑤ 任务跨多天、需要"上次聊到哪"？
   → 上 L3（结构性笔记 / 结构化事实），不是继续加强 L2 摘要。
```

> 本项目为**单用户**，不涉及多租户隔离，故无第 ⑥ 步。
